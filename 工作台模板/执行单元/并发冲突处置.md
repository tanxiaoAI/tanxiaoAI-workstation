# 并发冲突处置

同一工作区可能同时跑多个会话。本协议规定：**什么算并发冲突、怎么确认、确认后怎么办**。
所有会写正式 CSV 的流程遇到写入失败时，一律按本协议归因，不得自行发明恢复方式。

一句话原则：**其他报错停下来如实报告；只有「外部会话改动」且「本轮尚无正式写入」才等待重试。**

## 1. 先归因，判据只有一条

看到写入失败时，先问：**本轮是否已经执行过正式写入？**

- **本轮已有正式写入**：判为**本轮自身的顺序错误**（比如同一轮里重复提交、跳过了前置步骤）。
  停止并如实报告，不得用重试掩盖顺序错误；确实需要重跑时，由用户确认后重新发起。
- **本轮尚无任何正式写入**：判为**外部会话改动**。本轮还没写过任何东西，共享文件却和本轮读到的不一样，
  只可能是别的会话写的。此时按第 2、3 节等待并重试。

判断「本轮是否已写过正式写入」，看本轮有没有拿到过 `status = committed` 一类的成功回执，
以及本轮产生的正式文件是否已落盘。**只有候选稿、暂存文件、内存结果不算正式写入。**

### 算并发冲突的错误

| 错误码 | 出现位置 | 含义 |
| --- | --- | --- |
| `source_hash_mismatch:<路径>` | `账号分析证据分块执行器.py` | 建证据时记录的共享文件哈希，与当前文件不一致 |
| `concurrent_source_change:<路径>` | 账号概要 / 账号详细 / 选题分析 / 对标内容 的正式化执行器 | 正式写入前的读写一致性检查未通过 |
| `concurrent source change: <路径>` | `csv安全写入.py`（账号链路各批处理的提交阶段） | 写盘前发现共享表已被改动 |
| `stale_analysis_input:content_row:<字段>` | `对标内容分析正式化执行器.py` | 目标行字段与输入快照不一致 |
| `content_library_changed_after_analysis_commit` | `对标内容分析正式化执行器.py` | 目标行在分析提交之后被改过 |
| `target_content_conflict:changed_since_prepare` | `对标内容数据建档执行器.py`（对标内容数据获取 `2.9` 的 `--phase commit`） | 目标行在 `2.4` `local-prepare` 之后被改过 |
| `target_content_conflict:target_missing` | 同上 | `local-prepare` 判定为 `update` 的那一行，提交时已不存在 |
| `target_content_conflict:merge_ambiguous` | 同上 | `local-prepare` 判定为 `create`，提交时却匹配到同身份的行，且无法确定性合并 |
| `target_content_conflict:identity_match_count` | 同上 | 提交时同一身份匹配到多行 |

匹配错误码时按**子串**判断，不要求从行首开始。例如提交阶段的真实报错可能是
`CSV transaction serialization failed: concurrent source change: <路径>` 或
`csv_transaction_failed:concurrent source change:...`，其中 `concurrent source change` 就是判据。

### 不算并发冲突的错误

字段缺失、内容身份不符、章节结构错误、鉴权失败、路径越界、网络错误等，一律**停止并如实报告**，
不得归为并发冲突去等待重试。

`target_content_conflict:content_id_missing`（匹配到的行没有 `内容ID`）也归在这一类 —— 它是共享表里存在半成品行，
属数据问题而非并发时序问题，重跑不会改变结果。

## 2. 等待共享文件稳定

判为外部会话改动后，先等共享文件稳定，再动手重试：

1. 对相关的共享表（对标链路通常包括 `对标资料/对标账号库.csv`、`对标资料/对标内容库.csv`，账号链路还包括该账号的 `内容列表.csv`）采样 sha256；
2. 间隔 `30` 秒重新采样，**连续两次一致**视为稳定；
3. **单轮最多等 `10` 分钟**，超时按本轮失败处理。

等待期间不得改动任何正式文件，不得绕过执行器自行写入，也不得修改上一轮记录下来的哈希。

## 3. 按冲突发生的阶段执行恢复动作

稳定后按下面这张表恢复。**重试上限两轮**，两轮后仍失败就停止并如实报告。

| 冲突发生在 | 恢复动作 |
| --- | --- |
| 证据分块校验 | 重跑 `账号分析证据分块执行器.py --phase build` 并追加 `--reset-output-dir`（旧证据目录整体改名归档，不删数据），然后重新正式写入 |
| 账号链路提交（明细 / 封面 / 转写 / ASR / 总结 / 衍生字段） | 重新执行同一步骤：执行器会重新读取共享表并重新合并本轮结果再写盘。**不要重跑取数**，单条结果本身仍在暂存目录里 |
| 对标内容正式化（分析 / 特征候选） | 重跑 `对标内容分析前置检查.py` 拿新快照，再按《对标内容分析流程》`2.4.2` 的「并发冲突与恢复」重提交 |
| 对标内容数据获取提交（`2.9` 的 `--phase commit`）报 `target_content_conflict:changed_since_prepare / target_missing / merge_ambiguous / identity_match_count` | **回到 `2.4` 重跑 `local-prepare`**（参数与首次一致，刷新冻结的行指纹与路径），再重跑 `2.9`。**只重跑 `2.9` 无效** —— 冲突判据用的就是 `local-prepare` 冻结的那份行指纹，快照不刷新会原样再报一次。**不要重跑取数**：基础数据、封面、正文、评论都还在本轮 run 目录里 |
| 账号概要 / 账号详细正式化 | 按其流程文档中同名小节的步骤重出证据并重新提交 |

重试必须走原来的执行器入口，不得手工改 CSV，也不得把两轮结果手工合并。

## 4. 重试结束后要说清楚

恢复完成后，在结果里说明本轮发生过并发冲突，并说明重试后用的是重读的数据还是复用的候选稿。
不得把并发冲突直接报成本轮失败，也不得在重试未结束时宣称已完成。
