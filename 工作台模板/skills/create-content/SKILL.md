# 内容生产

## 入口确认

**开始前先执行一次使用统计上报**（静默脚本，失败不影响任何流程，也不必向用户提及）：

```bash
python3 执行单元/使用统计上报.py --kind skill --name create-content --phase start
```

新建内容生产时，先确认从哪一种入口开始：

1. **选题分析后生产**：当前上下文有用户已经确认的正式选题分析和 `topic_id`。
2. **对标内容分析后生产**：当前上下文有用户已经选择“直接做内容”的对标内容，以及正式对标分析路径（借鉴判断从 `内容分析.md` 的「借鉴判断」表读；特征卡已退役）。
3. **独立内容生产**：没有正式 `topic_id` 或对标参考。用户至少要说明想做什么，可以是一句话需求或临时主题；如果用户只说“开始做内容”而没有说明主题，先补问这一项。

上游流程已经明确提供入口和必要输入时，不重复让用户选择；无法唯一判断时才向用户确认。独立生产的临时主题或一句话需求只用于建立本次内容身份，媒介形式和内容目标在内容定位阶段再向用户确认。

## 主链路说明

新建内容生产时，先向用户展示以下固定说明：

```text
内容会依次经过 3 步：

1. 内容定位：确定这条内容讲什么、写给谁、从哪里切入。
2. 内容初稿：一次生成内容框架和完整初稿，可以反复修改。
3. 内容终稿：你确认后形成唯一终稿，可直接用于拍摄和发布。

内容审查是可选的：需要检查结构、措辞或平台规范时再手动发起，只出报告不改稿，也不挡你定稿。
```

用户不需要选择生产模式。内容定位确认后直接生成框架和完整初稿。

用户已经明确说明入口时不要重复询问；继续、确认或修改已有任务时，先确认要继续哪一条内容，再携带明确的 `content_id` 或状态文件恢复正式状态。不能因为工作区只有一条“生产中”内容就静默恢复。

## 调度

入口和最小内容身份确认后，调用本地内容生产阶段协调器：

- **选题分析后生产**：传入已确认的 `--topic-id`。不要把选题分析中的标题当作独立生产的 `--topic-name`。**一个选题只对应一条内容记录**：该选题已经生产过内容时不再新建，改为携带 `--content-id` 或 `--state-file` 从已有内容继续。这种情况与选题结论是 `建议做` 还是 `暂缓` 无关，只看该选题下是否已有内容。
- **对标内容分析后生产**：传入 `--reference-content-id` 和正式的 `--reference-analysis-path`。上游已经提供这些参数时，不再重复询问入口。不得传对标内容的 `content_id`，也不得传 `--topic-id`。协调器核验参考路径后新建一条选题 ID 为空的我方内容。
- **独立内容生产**：传入用户已经说明的临时主题或一句话需求作为 `--topic-name`。首次建档不要求传 `--media-form`；媒介形式和内容目标由内容定位流程询问并确认。只有用户已经明确给出媒介形式时，才一并传入 `--media-form`。
- **继续已有内容**：传入用户确认的 `--content-id` 或 `--state-file`，不要根据工作区里唯一一条未完成记录自行恢复。若返回 `needs_selection`，先让用户选择具体内容，再用确认后的参数重新调用。

```text
python3 "<当前工作区根目录>/执行单元/内容生产阶段协调器.py" --workspace-root "<当前工作区根目录绝对路径>" --action prepare <入口确认后的参数>
```

`prepare` 可能返回以下几种需要你回应用户的状态，按状态处理，不要自行猜测：

- `needs_production_input`：没有任何入口信息。按 `message` 引导用户给选题ID，或直接说要做的东西。
- `needs_topic_evaluation`：用户给了 `--topic-id`，但这条选题的「当前状态」还不是 `已完成分析` / `已生产`。告诉用户**这条选题还没有正式的分析结论，要先完成选题分析再回来**；不要让他再提供一次选题ID。
- `needs_production_decision`：这条选题已经分析完，但结论是 `暂缓` 或 `不建议做`。把回执 `message` 原文展示给用户，等他在「继续内容生产 / 讨论原因」里二选一；选继续就按 `decision_contract.continue_request` 原样重新调用 `prepare`（不要自己拼 `--nonrecommended-decision`），选讨论就回到选题分析重新走一轮。
- `needs_selection`：工作区里有多条可恢复的内容，或有多条已分析的选题可选。把候选展示给用户，让他选一条，再用确认后的参数重新调用。
- `needs_intake`：入口已确定但还缺建档必需的字段，按回执的 `required_fields` 补齐后继续。
- `status=ready`：输入已冻结，转入下面的流程文档执行。

`ok=false` 时说明真实原因并停止。注意：**本链路的错误回执在 stderr，成功回执在 stdout**（其他链路的执行器不保证如此，回执请 stdout 与 stderr 都读）。

协调器返回后，只使用回执中的 `current_stage.flow_file`、冻结 `inputs` 和动作合同。先完整读取该本地流程文档，再严格按文档执行；当前阶段为内容定位时只读取本地文件，不依赖远程语义包或运行时下发资源。不能因为阶段名称相同就自行换用其他流程文件；`current_stage.name` 与 `flow_file` 不一致或流程文件无法读取时，报告合同错误并停止。

## 内容审查

用户明确要求检查当前稿件（结构、措辞、平台规范等）时，读取 `执行流程/内容审查流程.md` 并按其中步骤执行。内容审查不改变生产状态，也可以直接跳过并确认终稿。

## 已完成终稿的后续修改

- 用户已经知道要改什么（改措辞、标题、局部表达）：读取 `执行流程/内容终稿流程.md` 的 `2.6`，用协调器 `--action reopen-final` 重新打开当前终稿。
- 用户要求重新审查或整体再改：读取同一节的 `2.6`，用 `--action transition --transition-action rework-stage --target-stage 内容初稿` 回到内容初稿。
