# 自我账号详细诊断流程

**本流程开始前先执行一次使用统计上报**（静默脚本，失败不影响任何流程，也不必向用户提及）：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 自我账号详细诊断流程 --phase start
```

## 1. 总流程说明

1. 前置步骤
   - 进入 `2.1 判断诊断起点`，确定本轮唯一账号、批次身份和诊断任务类型。
   - 进入 `2.2 检查资料并分流`，调用前置检查并冻结本轮诊断输入快照；不满足条件时按返回的真实原因停止。
2. 准备证据与生成候选稿
   - 进入 `2.3 准备并校验内容证据`，生成并验证本轮稳定证据分块。
   - 进入 `2.4 生成诊断候选稿`，一次性生成完整诊断正文候选。
3. 正式提交
   - 进入 `2.5 校验并保存正式结果`，仅在候选通过校验后提交正式诊断。
   - 只有返回 `ok = true`、`status = committed`、`formal_path` 和 `formal_sha256` 才算正式保存成功。
   - 进入 `2.6 生成账号改进行动清单`：从诊断的关键问题和其他已确认依据出发，按动作方向库筛选当前最值得执行的 0-3 条动作，产出 `<账号目录>/<YYYY年M月D日>账号改进行动清单.md`。失败不改变已保存的诊断。
   - 进入 `2.7 生成账号内容规律分析`：按本账号切片现算打法画像与标签效果，产出 `<账号目录>/<YYYY年M月D日>账号内容规律分析.md`。这是本流程的收尾步骤，**失败或跳过都不改变已保存的诊断，也不算整轮失败**。
4. 反馈结果
   - 进入 `2.8 反馈结果`，反馈正式文件、证据边界和信息不足项。反馈完即结束本轮。
   - 本流程是一次性流水线，不含多轮讨论。

本流程直接读取本地流程、执行单元和提示词。

### 本轮运行合同

本流程使用入口已经确认的唯一账号和本轮 `run_id`；`run_id` 只能由《我方账号基础数据获取流程》的 `账号分析本地批次初始化执行器.py` 分配一次，基础数据、详细数据和诊断三个阶段原样沿用，没有 `run_id` 时不进入本流程，也不重新选择账号或重新分配、改写 `run_id`。

本轮暂存目录固定为 `<当前工作区根目录>/.meiling/staging/self-account-diagnose/<run_id>/`；正式诊断文件只由 `执行单元/` 下的本地脚本写入。本流程不读取、不创建任何调度器任务状态；账号的正式阶段状态只写入 `<账号目录>/过程记录/当前阶段状态.json`，由 `2.2` 的前置检查执行单元读写，其余步骤不直接改动它。

本流程没有等待用户或等待其他流程的阶段状态分支：`2.2` 写入的阶段状态恒为进行中，不记录等待状态。

## 2. 具体流程说明

### 2.1 判断诊断起点

本步骤只确定本轮诊断对象、批次身份和任务类型，不检查资料是否充足，也不执行数据补齐。

固定读取 `我方资料/我方账号库.csv`，按 `账号ID + 平台` 唯一确定本轮账号。同一个创作者通常有多个平台的账号记录，因此按下列三档处置，本步骤不自行猜测账号：

- **1 条记录**：直接作为本轮账号，保留 `账号ID`、`账号名`、`平台`、`内容列表路径`、`过程记录路径`，供 `2.2` 直接取用。
- **多条记录**：把候选逐条列给用户（账号名 + 平台），请用户指定本轮诊断哪一个；用户确认后按该条保留上述字段，再进入 `2.2`。用户未确认时停在本步骤，不调用 `2.2`。
- **0 条记录**：说明账号库当前没有已建档的账号，停止本流程并告知需要先走 `我方账号基础数据获取流程.md`；不调用 `2.2`。

只有在前两档取得确定的 `账号ID` 与 `平台` 后，才调用 `2.2` 的前置检查。

先明确：

- 本轮诊断的 `平台 + 账号ID`；
- 本轮 `run_id`；
- 用户是否要求在现有正式诊断基础上修改。

上一阶段的详细数据交接（`canonical-detail-report.json`）是否成立、账号是否存在可用的最新正式诊断，均由 `2.2` 的前置检查统一判定，本步骤不预先检查，也不自行拼接交接路径。

按下面规则确定任务类型：

1. 默认按 `新一轮诊断` 处理，包括刚完成详细数据流程、用户要求重新诊断，以及账号已有历史诊断但用户未明确要求改旧稿的情况。
2. 只有用户明确要求在当前正式诊断基础上修改、且 `2.2` 前置检查返回了可用的最新正式诊断时，才按 `基于最新正式诊断重新生成一版` 处理；`2.4` 把最新正式诊断正文作为额外输入，其余输入不变。用户要求修改但没有可用的最新正式诊断时，不能假装修订旧稿，仍按 `新一轮诊断` 处理并告知用户。

本流程只接受按 `基础数据 -> 详细数据 -> 诊断` 固定顺序进入的本轮交接。工作区存在本账号的多份正式诊断时，`基于最新正式诊断重新生成一版` 只读取按正式文件名日期最新的那一份。

### 2.2 检查资料并分流

#### 输入

- 本地入口已经确认的工作区、账号、平台、批次身份（`run_id`）、阶段状态路径和账号内容列表；
- 本轮内容范围：存在本轮范围时传 `--selected-content-ids`，未指定时不传；默认使用 `--visibility-scope public`，只分析公开内容；私密、仅自己可见、草稿、审核中、未通过和其他/未知状态一律排除。
- 正文级样本仍按本轮范围取最近 N 条；`2.4` 的「目标与实际」定位判断使用快照里的公开面全量，不受 N 限制。两者在诊断里必须分开表述，不得把 N 条样本当成整个公开面。

#### 调用前置检查

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/自我账号诊断前置检查.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --account-id "<账号ID>" \
  --platform "<平台>" \
  --flow-type self_account \
  --run-id "<run_id>" \
  --stage-state-path "<账号目录>/过程记录/当前阶段状态.json" \
  --task-content-list-path "<账号内容列表路径>" \
  --output-json ".meiling/staging/self-account-diagnose/<run_id>/诊断输入快照.json"
```

- `--stage-state-path` 必须与 `--task-content-list-path` 指向同一个账号目录，即 `<账号目录>/过程记录/当前阶段状态.json`；两者不一致时执行器按 `stage_state_path_mismatch` 直接失败。
- `--output-json` 非空时，同一条命令除写出 `诊断输入快照.json` 外，还会校验并写入 `<账号目录>/过程记录/当前阶段状态.json`。附加链路失败时整条命令返回失败，但快照可能已经写出；此时停在本步骤说明真实错误，不得把已写出的快照当作可用输入。
- 概要缺失或固定部分不完整时不停等用户选择，直接按通用账号诊断继续；概要完整时不受影响。
- 执行单元负责检查账号库、内容库、内容列表、当前概要和逐条内容证据，并返回 `status = checked`、`next_route`、`route_reason`、`warnings`、`facts`、`content` 下的内容与证据计数、输入文件路径与 SHA-256 以及最新正式诊断路径。模型只解释返回结果，不重新计算证据门槛；不得绕过前置检查读取旧快照继续。

#### 输入快照冻结

前置检查成功并返回 `status = checked` 时，`--output-json` 写出的 `诊断输入快照.json` 即为本轮唯一冻结输入。快照内 `input_snapshot.files` 已记录账号库、内容库、内容列表、`我方当前概要.md` 和 `我方自媒体规划.md` 的路径与 SHA-256，由 `2.5` 提交时自行重算比对；上述任一文件在快照生成后发生变化，`2.5` 都必须判定输入过期并要求从 `2.2` 重跑。

`2.5` 的 `--input-sha256` 取的是 `诊断输入快照.json` **文件自身**的 SHA-256，不是快照内的文件哈希；该值不由前置检查返回，必须在提交前自行计算。

#### 判断规则

按执行器返回的 `next_route` 分流；`route_reason` 和 `facts` 是唯一原因来源，不自行推断。

1. `next_route = basic_data` / `detail_data`
   - 说明对应阶段未完成或资料不可用，停止本流程；本流程不代替上游补数据。
   - `basic_data`（账号库不存在，或账号未能在账号库中唯一定位）：按固定顺序回到 `我方账号基础数据获取流程.md` 完成建档，不重跑本步骤。`2.1` 已取得确定的账号身份后仍返回本值时，先与用户核对 `账号ID / 平台` 是否确实是本轮账号。
   - `detail_data`（内容库或内容列表不可读、样本不足、本轮详细数据未正式交接，或本轮选定内容缺失、可见性与范围不符）：核对 `账号ID / 平台`、`--selected-content-ids`、`--visibility-scope` 后重跑本步骤，不重跑基础数据。
   - 0 条可用内容证据时不得继续生成只有账号层或方法层的正式诊断。
2. `next_route = continue_diagnosis`
   - 进入 `2.3`。
   - `warnings` 非空时先向用户说明真实证据边界，但不机械增加暂停点。
   - 没有完整正文级证据但仍有降级证据时可以继续。

### 2.3 准备并校验内容证据

执行器按剥字段后的证据总量自动分流，build 回执有两种形态，必须按 `detail_delivery_mode` 区分：

- **`direct`（直读）**：证据量在阈值以内，不分块，直接产出合并可读证据；回执 `chunk_count = 0` 并带 `direct_evidence_path`。此时**跳过下面的「生成分块并写摘要」小节、不读取摘要提示词**，直接进入「校验摘要」。
- **`chunked`（分块）**：证据量超阈值，回执带分块清单与 `chunk_count`，按下面两小节完整执行。

阈值由执行器的 `--direct-read-max-chars` 控制（默认 `60000` 字符），不要在流程里自行换算或改写这条判定。

#### 生成分块并写摘要

调用根目录执行单元生成稳定的证据分块：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号分析证据分块执行器.py" \
  --phase build \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --account-type self \
  --account-id "<账号ID>" \
  --platform "<平台>" \
  --mode detail \
  --selected-content-ids "<2.2 返回的 content.selected_content_ids，逗号分隔>" \
  --output-dir ".meiling/staging/self-account-diagnose/<run_id>/账号诊断证据"
```

- 必须原样传入 `2.2` 返回的 `content.selected_content_ids`，不得省略参数、挑选、增删、改序或改写内容 ID。显式传入后执行器逐条校验：为空或重复报 `selected_content_ids_invalid`，任一 ID 不在内容列表内报 `selected_content_ids_missing`。
- 输出目录已存在且非空时（上一轮中断后重跑、或补采到新证据要重出分块），执行器默认报 `output_dir_not_empty`。确认旧分块可以作废重出时，在原命令上追加 `--reset-output-dir`：它会把旧目录整体改名归档（不删除数据）再重建。不得手工删除或搬动旧分块。
- 本轮可见性范围由 `2.2` 统一确定为 `public`，只分析公开内容；本步骤沿用同一次前置检查返回的 ID 列表。本步骤执行器没有 `--visibility-scope` 参数，不得在本步骤自行改写可见性范围。
- 执行单元在模型上下文外读取我方内容列表、我方内容库和本轮视频文案，生成稳定分块清单。历史 `内容画像与特征卡` 是旧分析产物，不是本轮证据，不参与分块，也不得作为诊断依据。主对话不得先加载全部原始证据。
- 分块清单必须记录 `total_content_count`（账号内容总数）、`selected_content_count`（本次选择数）、`selected_body_evidence_content_count`（正文级证据数）和 `selected_basic_only_content_count`（仅基础数据数）；这四个计数由执行单元机械生成，模型不得改写。

**仅当回执为分块形态时**：读取 `提示词/账号分析-分块证据摘要提示词.md`，按清单逐个生成摘要并写入清单指定的 `summary_path`；每份摘要必须包含 `分布与模式证据`、`差异与反例`、`代表性证据索引`、`信息不足` 四个固定章节，且 `分布与模式证据` 不得为空或占位，否则执行器按 `summary_body_invalid` 拒绝。全部摘要写完后进入校验。

#### 校验摘要

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号分析证据分块执行器.py" \
  --phase verify \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --output-dir ".meiling/staging/self-account-diagnose/<run_id>/账号诊断证据"
```

只有返回 `status = verified` 才进入 `2.4`；`2.4` 读取的已验证证据摘要路径以回执 `verified_evidence_path` 为准。失败时停止并说明失败位置，现有正式诊断保持不变。

### 2.4 生成诊断候选稿

#### 输入

1. `提示词/自我账号诊断成稿提示词.md`：写作规则与输出结构的唯一来源；
2. `分析框架/自我账号诊断方法论.md`：分析规则、字段口径和推导边界，不是账号事实证据；
3. 本轮目标基准按账号是否有历史正式诊断分档：该账号没有历史正式诊断时默认用 `我方资料/调查问卷.md` 的原始回答，`我方资料/我方自媒体规划.md` 不参与本轮目标判断；如果本轮指令明确说明规划刚刚按同一份新问卷更新，并要求以新规划为判断基准，则改用 `我方资料/我方自媒体规划.md`；该账号已有正式诊断时优先 `我方资料/我方自媒体规划.md`，规划不存在或不可用时回退调查问卷；两者都不可用时写 `判断基准不足`；`我方资料/我方当前概要.md` 只是规划摘要，不作为判断基准；
4. `2.3` 已验证的证据分块摘要及其统计信息；`2.2` 快照里的 `content.public_face`（公开面全量）和 `content.new_since_previous_diagnosis_ids`（上次诊断后的新增内容）；
5. `<账号目录>/过程记录/批处理报告/本轮账号基础建档结果.json` 的 `content_list_status` 和采集停止原因（`source_results[].停止或失败原因`，兼容顶层 `内容列表停止原因`）；**不读 `data_limitations`**，那是资料缺口总表，含截图失败等与内容列表无关的条目；
6. 创作者中心最新采集：`<账号目录>/创作者中心数据/最新采集.json` 及其指向的账号概览、内容分析、采集报告；缺失时写 `未获取`；
7. 评论原文：本轮选中内容目录下的 `评论.md` / `评论.json`；没有就写 `未采集`；
8. 这段时间变化的三个输入：快照里的 `previous_diagnosis`（上一版正式诊断）、`previous_action_list`（上一次 `账号改进行动清单`）和 `content.new_since_previous_diagnosis_ids`（上次诊断日之后新增的公开内容）。三样东西分工固定：上一版诊断告诉你上次的问题，上一次行动清单告诉你上次给的动作，新增内容和指标告诉你这次实际发生了什么；没有历史诊断时写 `首次诊断`；
9. `2.1` 判定为 `基于最新正式诊断重新生成一版` 时，额外加入最新正式诊断正文。

#### 生成

按第 1 项提示词生成完整诊断正文候选，固定写入：

```text
.meiling/staging/self-account-diagnose/<run_id>/诊断候选.md
```

#### 补充说明

- 候选必须是完整正文，不输出局部补丁，不直接覆盖正式诊断；章节结构按提示词固定，`2.5` 会逐项校验。
- 第 3 项是本轮目标基准；新一轮诊断必须读取规划的关键结论（当前结论、现实约束、产品供给边界、内容主线、待验证事项）；首次诊断直接读调查问卷的原始回答；实际使用的基准不可用时按另一份的原始回答，不能只读概要。
- 样本口径按快照固定：目标与实际使用 `content.public_face` 的公开面全量（标题、发布时间、互动分布）判断定位，历史存量只给处置建议；这段时间的变化使用 `content.new_since_previous_diagnosis_ids`，只算上次正式诊断日之后发布的公开内容，指标也只统计这批新增，不混入历史内容、不展示全量基线；正文级证据仍只限本轮选中内容。
- 这段时间的变化按「一句话总结 + 2 到 4 条变化」写：每条变化由 `方面`、`结论`、`文案` 组成，`结论` 只能取 `变好`、`变差`、`没变`、`仍然差`、`无法比较`，`文案` 用一段完整的话先说结论再给关键证据；不得再拆成「哪里变了 / 证据 / 说明什么」三行，也不得只陈述发布条数这类用户自己知道的事实而不给判断。上一版诊断没有同口径数据时 `结论` 只能写 `无法比较`，文案里说明当前实际水平。不写「上次行动核对」，上次行动清单只用于判断问题有没有变化。不得再按「已改善 / 仍存在 / 新增问题」分三类归档，也不得把本轮行动清单当成本次变化的依据。
- 创作者中心和评论缺失时继续生成，但必须在第 5 节「本轮依据与边界」和对应正文写 `未获取` 或 `未采集`，不得写 0 或用推测补齐。
- “内容列表完整性”取值固定为 `完整` / `可能未抓全` / `未知`，只能按第 5 项判定，判据与对标账号链路共用同一套规则，单点实现在 `执行单元/内容列表完整性判据.py`：只有采集侧在停止原因里明确声明已到达列表末尾时才写 `完整`；`content_list_status` 为 `部分成功` / `失败`、或停止原因没有声明已到达末尾时写 `可能未抓全`；报告缺失、不可读或状态无法识别时写 `未知`。`成功` 只表示已取得可识别内容，不得单独解释为“完整”。不得由模型自行估计，也不得根据内容数量推断。
- 只有账号、内容证据或基准文件本身不可用（读不到、样本不足、身份不一致）时停止并说明真实原因，不进入 `2.5`；判断基准与账号实际方向完全不一致不属于停止条件，必须照常生成诊断并进入 `2.5`。

### 2.5 校验并保存正式结果

#### 输入

1. `2.4` 写出的诊断候选：`.meiling/staging/self-account-diagnose/<run_id>/诊断候选.md`；
2. `2.2` 写出的诊断输入快照及其**文件自身**的 SHA-256（前置检查不返回该值，提交前自行计算）；
3. 本轮 `run_id` 和账号、平台。

#### 调用保存执行器

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/自我账号诊断正式保存.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --account-id "<账号ID>" \
  --platform "<平台>" \
  --candidate-file ".meiling/staging/self-account-diagnose/<run_id>/诊断候选.md" \
  --diagnosis-input-file ".meiling/staging/self-account-diagnose/<run_id>/诊断输入快照.json" \
  --run-id "<run_id>" \
  --input-sha256 "<诊断输入快照 sha256>"
```

- 执行器负责候选文档标题校验、页面数据区（`self-account-diagnosis-v2` 摘要）校验、五个章节及子章节顺序校验、输入快照身份与 SHA-256 复核、账号与内容范围复核、正式文件定位、原子写入和回读校验。缺章节、缺字段、摘要版本不符时拒绝保存。
- 模型不得手工写入正式文件，也不得自行拼接章节。
- 正式文件名固定为 `<账号目录>/<YYYY年M月D日>账号详细诊断.md`。同一天再次保存会**覆盖当天已有的正式诊断**，每天只保留一份；跨天的历史诊断不受影响。`formal_path` 返回的是本轮实际写入路径。

#### 保存判断

- 只有执行单元返回 `ok = true`、`status = committed`、`formal_path` 和 `formal_sha256`，才算正式保存成功并进入 `2.6`。
- 候选文档标题校验失败：正式文件保持不变，回到 `2.4` 修正候选。
- 输入快照过期、账号不一致、内容范围缺失或路由不再可用：正式文件保持不变，回到 `2.2` 重新检查。
- 正式写入或回读失败：不得报告保存成功；原正式诊断和账号阶段状态保持保存前状态，停在本步骤说明真实错误。

### 2.6 生成账号改进行动清单

本步骤在诊断正式保存成功后执行。它读取诊断的综合诊断、目标与实际、关键问题、这段时间的变化和本轮依据与边界，先判断问题属于哪一层，再从动作方向库中选择或组合动作，按影响、紧急程度、证据强度、可执行性和依赖顺序筛选，最终生成 0-3 条当前最值得执行的行动。没有关键问题时，可以只写 1 条维持型行动，也可以写 0 条并说明原因，不硬造整改任务。它不重新诊断，不生成选题任务，也不修改规划。

#### 输入

- `2.5` 返回的正式诊断路径及其页面数据区；
- 本轮正式诊断第 5 节写明的判断基准（调查问卷 / 我方自媒体规划）；不得自行重新优先选规划；`我方资料/我方当前概要.md` 仅作背景参考；
- 本轮创作者中心、评论和上一版《账号改进行动清单》（如有）；
- 本步骤先检索出的《行动参考候选》。

#### 检索参考候选

在生成行动候选前，先从内容特征实例里检索本轮可用的参考做法候选：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/行动参考候选检索.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --output-json ".meiling/staging/self-account-diagnose/<run_id>/行动参考候选.json"
```

- 候选只来自 `沉淀结论/内容特征实例.csv` 中已分析、当前有效、实际采用的对标内容，并已按特征小类和数据水平排序。
- 检索失败或候选为空时，行动候选里所有 `参考做法` 都写 `无`，不得改用其他来源或凭记忆补写。

#### 生成候选

调用 `提示词/账号改进行动清单提示词.md`，把 `行动参考候选.json` 一并作为输入，一次生成完整候选，写入：

```text
.meiling/staging/self-account-diagnose/<run_id>/账号改进行动清单候选.md
```

候选标题固定为 `# <账号名>账号改进行动清单`，动作 0-3 条。每条必须写清方向、对应问题或依据、具体做法、完成标准和验证指标；动作数量按筛选结果确定，不凑数。每条 `参考做法` 只能取 `行动参考候选.json` 里的作品，候选里没有合适项时写 `无`。

#### 保存

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号改进行动清单正式保存.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --account-id "<账号ID>" \
  --platform "<平台>" \
  --candidate-file ".meiling/staging/self-account-diagnose/<run_id>/账号改进行动清单候选.md" \
  --diagnosis-file "<2.5 返回的正式诊断路径>" \
  --reference-candidates-file ".meiling/staging/self-account-diagnose/<run_id>/行动参考候选.json"
```

- 只有返回 `ok = true`、`status = committed`、`formal_path` 才算保存成功。
- 参考做法不在候选清单里时执行器会拒绝保存，必须改回候选内的作品或写 `无` 后重跑，不得绕过校验。
- 正式文件名固定为 `<账号目录>/<YYYY年M月D日>账号改进行动清单.md`；同一天重跑覆盖当天文件。
- 失败不改变已保存的诊断，在最终反馈写明真实原因，继续执行 `2.7`。

### 2.7 生成账号内容规律分析

本步骤是收尾步骤，只在 2.5 的正式诊断保存成功后执行。**跳过或失败都不改变已保存的诊断，也不算整轮失败**——内容太少的账号就是出不了这份分析。

它读的是 `沉淀结论/内容特征实例.csv` 按本账号切出来的行、本账号 `内容列表.csv` 的互动数，以及 `沉淀结论/内容特征词典.csv`；**与 2.3 的证据分块、2.4 的诊断候选稿没有依赖**。本步骤**不写任何共享资产**。

#### 第一步：准备机器数据

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容规律分析准备执行器.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --source "我方内容" \
  --account-id "<账号ID>" \
  --platform "<平台>" \
  --output-file ".meiling/staging/self-account-diagnose/<run_id>/账号内容规律分析准备结果.json"
```

- 返回 `status = skipped_no_instances`：该账号完成特征识别的内容数为 0，**跳过本步骤**（不是失败）。直接进入 2.8，反馈时在状态行写明「内容规律分析未生成：该账号完成特征识别的内容不足 1 条」。
- 返回 `status = ready`：取其中的 `analysis_scope_label`、`active_sample_count`、`rule_count`、`rules`、`markdown`、`rank_comparison`，继续第二步。

#### 第二步：生成候选稿

调用 `提示词/账号内容规律分析提示词-我方.md`，一次生成完整的 `账号内容规律分析候选.md`，写入本轮暂存目录（`.meiling/staging/self-account-diagnose/<run_id>/账号内容规律分析候选.md`）。

报告固定 4 节，顺序为：`1. 分析范围`、`2. 内容打法`、`3. 表现比较`、`4. 与上期相比`。第 1 节五项与第 3 节的四组表格必须逐字取自准备结果；第 2 节的打法由准备结果的 `rules` 整理。

第 4 节另需在 `<账号目录>` 下找**日期早于本期、最近一份**《账号内容规律分析》作为上期基线（同日文件已是本期，不算），只读取它的「按环节看」表比较做法篇数；没有上期、或上期没有该表时，按提示词写一句不可比说明。除此之外不读任何其他历史文件。

整篇不得出现「新特征」「候选」「入库」，也不写学习启发、内容方向、代表作品、正文补充和行动建议。

#### 第三步：校验并保存正式结果

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容规律分析正式保存.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --source "我方内容" \
  --account-id "<账号ID>" \
  --platform "<平台>" \
  --candidate-file ".meiling/staging/self-account-diagnose/<run_id>/账号内容规律分析候选.md" \
  --preparation-result-file ".meiling/staging/self-account-diagnose/<run_id>/账号内容规律分析准备结果.json"
```

正式文件名固定为 `<账号目录>/<YYYY年M月D日>账号内容规律分析.md`。同一天再次保存会**覆盖当天已有的那一份**，每天只保留一份；跨天的历史不受影响。只有返回 `status = committed`、`formal_path` 和 `formal_sha256` 才算写完。

保存校验四条，任一不符即拒绝写入、正式文件保持原有内容：

1. 报告标题必须是 `# 账号内容规律分析`，全篇只出现一次；
2. 4 个节名与顺序必须逐字一致；
3. 第 1 节的生成时间、纳入内容数、规律数量、对比基线，以及第 3 节表格的共性占比、三档条数与比例、判定词，都必须与准备结果完全一致；
4. 第 2 节必须有按环节表、五个机制齐全、非空小结；第 3 节必须有「暂时无法判断」，且其中的标签只能是机器判为样本不足或区分不出好坏、出现 2 篇以上的做法；第 4 节不得为空。

本步骤**不改** `<账号目录>/过程记录/当前阶段状态.json`，也不回写我方账号库。

### 2.8 反馈结果

保存成功后，向用户给出状态、结论、资料说明和工作台地址，不再展示正式文件路径、账号 ID、账号档案链接和账号方向链接（用户要文件时再单独给）。

```text
## 自我账号诊断结果

- 账号：<账号名>（<平台>）
- 状态：<已完成；有步骤未完成时写明哪一步、什么原因>

### 结论
<本轮诊断结论：这个账号实际处在什么状态、最要命的问题是什么、下一步从哪入手>

### 资料说明

### 工作台
```

状态行只写完成情况，不另起小节：全部跑完写 `已完成`；2.6 行动建议失败或 2.7 内容规律分析未生成时，写成 `已完成（内容规律分析未生成：…）` 这类带原因的写法。

结论必须来自本轮已保存的正式结果，至少落到一个具体数字或一条具体证据，不做推测。证据边界（纳入几条内容、哪些没有纳入、哪些维度没参与结论）只写在「资料说明」里，结论里不复述。

`<dashboard_base_url>` 只能替换为工作台启动后返回的本地基础地址，取址方式固定按 `执行单元/工作台地址获取.md` 执行；工作台未打开或未返回地址时写“工作台未打开”，但不阻断正式结果反馈。不得猜测端口或基础地址。

占位符只能替换为正式保存回执和本轮已验证资料中的真实值，不得猜测或补写。默认不展示暂存路径、内部内容 ID、JSON 字段、正式文件路径和账号 ID。

反馈完本轮即结束，不进入任何后续流程。
