# 账号基础数据获取流程

**本流程开始前先执行一次使用统计上报**（静默脚本，失败不影响任何流程，也不必向用户提及）：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 账号基础数据获取流程 --phase start
```

## 1. 总流程说明

1. 前置确认
   - 进入 `2.1 检查账号链接`；只有链接或账号无法唯一确定时才向用户确认。
   - 进入 `2.2 读取取数方式配置`，按设置页配置直接确定来源，不再询问用户。
2. 获取与建档准备
   - 确定来源后，先调用 `账号分析本地批次初始化执行器.py` 创建本轮唯一 `run_id`（见「固定路径」）。
   - 进入 `2.3 获取账号基础信息并立即落盘`。
   - 进入 `2.4 执行 --prepare-only 查重`。
   - 进入 `2.5 获取账号内容原始列表并立即落盘`。
3. 正式建档
   - 进入 `2.6 正式建档并验证产物`。
   - 只有 `formal_commit.validated = true`、`complete = true` 且 `validation_status = accepted` 时，才算基础建档成功。
   - `verified_empty = true` 时，账号基础信息建档成功，但当前没有可用于详细分析的内容；说明情况后结束本轮。
4. 自动交接
   - 进入 `2.7 自动交接到账号详细数据获取`。
   - 只读取 2.6 写入的正式建档回执及其中的 `base_handoff`。
   - `base_handoff.status = ready` 时，直接进入《账号详细数据获取流程》的 `2.1 入口判断与承接基础数据结果`；不向用户单独汇报基础建档结果，也不等待确认。
   - `base_handoff.status = blocked` 时，说明真实阻断原因并结束本轮。

本流程为开源版本地流程。所有流程文档、执行单元和提示词均直接从当前工作区读取，不使用 semantic bundle、流程管理器或远程执行单元。

固定路径：

- `<当前工作区根目录>`：当前工作区根目录
- `<本轮暂存目录>`：`当前工作区/.meiling/staging/benchmark-account-diagnose/<run_id>/`
- `<账号基础信息JSON>`：`<本轮暂存目录>/账号基础信息.json`
- `<账号内容原始列表JSON>`：`<本轮暂存目录>/账号内容原始列表.json`

`<run_id>` 是本轮唯一的批次身份，由本流程创建，并在详细数据、详细分析两阶段原样复用；各阶段不得自行新建。确定取数方式、进入 `2.3` 之前，必须先调用：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号分析本地批次初始化执行器.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --flow-type benchmark_account
```

只使用返回的 `run_id`，并在本轮后续所有命令中原样传递。返回 `ok = false` 时立即停止并说明真实原因（`run_id_collision` 表示已存在同名批次，此时应确认是否恢复该批次而不是新建）；不得由模型自行编造或改写 `run_id`。

本轮候选 JSON、Chrome 中转文件、截图和网络响应均写入本轮暂存目录或其 `chrome-inbox/` 子目录。Chrome Network 兜底必须使用 `prepare` 返回的 `network_response` 路径；内容列表候选 JSON 和主页截图必须通过 `finalize` 校验后才能进入正式建档。正式 CSV、报告和阶段状态只能由 `执行单元/` 下的本地脚本写入，禁止手工修改或绕过校验。

## 2. 具体流程说明

### 2.1 检查账号链接

先检查当前任务中的用户消息是否包含账号链接。

如果用户消息包含账号链接：

- 只有 1 条链接时，直接使用该链接，不再要求用户重复确认；
- 有多条链接时，停止并让用户选择目标账号；用户选择后只处理选中的一条。

如果用户消息没有包含账号链接，再读取当前工作区的 `对标资料/对标账号库.csv`，只根据账号库中的候选数量处理：

- 没有账号库记录：停止并向用户索要账号链接；
- 只有 1 条账号库记录：停止并展示该账号，让用户确认；
- 有多条账号库记录：停止并展示候选账号，让用户选择。

确定唯一候选输入后（用户提供的链接，或用户确认、选择的账号库记录），严格复用 `执行单元/账号链接规范化与判断.md`，输入固定为：

- `原始输入 = <本轮唯一候选链接或分享文案>`
- `self 链接处理 = 直接拒绝`
- `当前工作区根目录 = <当前工作区根目录>`

只消费协议返回的状态和真实原因：

- `ok`：把返回的标准主页链接冻结为本轮唯一 `<账号主页链接>`，继续执行 `2.2`。账号库中已经登记的链接同样必须经过本次规范化，不得直接沿用账号库中的原始文本。
- `不适用于本流程`、`非主页链接`、`规范化失败`、`状态不可用`：停止并告知用户协议返回的真实原因和对应平台正确示例，不再读取账号库，也不进入 `2.2`。

`<账号主页链接>` 是本轮唯一账号身份；`2.3` 至 `2.5` 的取数动作只能使用它，不得改用用户原始输入、分享文案或账号库中的原始文本。

### 2.2 读取取数方式配置

取数方式由工作台「设置 → 取数方式」决定，统一保存在工作区根目录的 `本地配置.txt`（`DATA_SOURCE_PREFERENCE`）。本流程不再向用户展示选择题，判断规则与《对标内容数据获取流程》完全一致。

```bash
python3 "<当前工作区根目录>/执行单元/对标内容数据建档执行器.py" \
  --phase resolve-source \
  --workspace-root "<当前工作区根目录>"
```

只读取返回的 `ok / selected_source / selection_rule / reason`，规则固定为：

- 用户设了首选：始终使用首选来源；
- 只配置了一种：自动使用那一种；
- 两种都可用但没设首选：默认本机 Chrome，避免意外产生接口费用；
- 首选 `justoneapi` 但没填 Token：`status = source_unavailable`，停止并提示到设置页补 Token；
- 选定来源不可用或执行失败：立即停止，不自动切换另一个来源，也不再询问是否换源或是否继续付费。

来源可用性检查只检查选定来源本身，不再把两种来源摆给用户选：

- `chrome_devtools`：检查连接可用性与工作区写权限（写探针 → 读回比对 → 删除）；不可用时按 `执行单元/取数环境搭建.md` 自动装好配好，重跑一次检查，不重复询问用户。
- `justoneapi`：按 `本地配置.txt` 的 `JUSTONEAPI_TOKEN` 判定，已在 `resolve-source` 中校验。

检查不通过时，用一句话说明缺什么、去哪里补，然后停止本轮；不展示选择题，也不提供换源选项。正常情况下只在结果里说明本次用了哪个来源。ASR 不参与本步选择，按 `2.6` 的规则处理。

### 2.3 获取账号基础信息并立即落盘

本轮来源为 `chrome_devtools` 时，本流程后续使用的 MCP 服务名固定为 `chrome_devtools`，不得把客户端生成的工具命名空间（如 `mcp__chrome_devtools`）当成服务名。具体工具、调用顺序和调用上限以当前子流程的阶段合同为唯一依据；父流程不再重复列出工具清单。不得调用子流程未授权的工具，也不得自行发现其他 MCP 或浏览器。

#### `chrome_devtools`

1. 在调用任何 Chrome 工具前，先创建本轮唯一的中转清单：
   ```bash
   python3 "<当前工作区根目录>/执行单元/Chrome采集临时文件中转.py" prepare \
     --staging-dir "<本轮暂存目录>"
   ```
   必须保存返回的 `manifest_json`、`stage1_json`、`screenshot_png` 和 `network_response`。`--staging-dir` 必须是**本轮暂存目录本身**，不得传它下面的 `chrome-inbox` 子目录——执行器会在该目录下再建一层 `chrome-inbox`，传子目录会得到 `chrome-inbox/chrome-inbox/...` 的重复嵌套（按 `staging_dir_must_be_run_dir` 拒绝）。`prepare` 失败时立即停止，不得进入 Chrome 采集。
2. 完整读取并执行 `<当前工作区根目录>/执行单元/获取账号基础信息.md`，输入为账号主页链接、本轮暂存目录和上述中转清单。当前 AI 直接使用 `chrome_devtools`，在同一 Chrome 会话中取得账号信息并写入 `<账号基础信息JSON>`；基础字段需要 Network 兜底时，只能使用中转清单中的 `network_response` 路径。保持账号主页标签页，暂不采集作品。

#### `justoneapi`

调用：

```bash
python3 "<当前工作区根目录>/执行单元/JustOneAPI账号基础抓取执行器.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --account-url "<账号主页链接>" \
  --account-info-json "<账号基础信息JSON>" \
  --preflight-only
```

账号基础信息至少要有真实的 `平台 / 账号ID / 账号名 / 主页链接`。缺失时按同一来源补抓一次；仍缺失就说明情况并停止。

本步骤结束前必须确认 `<账号基础信息JSON>` 真实存在、可以解析，且 `基础数据获取方式` 与用户选择一致。没有落盘就不得继续。

### 2.4 账号查重

调用：

```bash
python3 "<当前工作区根目录>/执行单元/账号基础数据建档批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --account-type benchmark \
  --account-info-json "<账号基础信息JSON>" \
  --prepare-only
```

只接收脚本返回的 `status / account_exists / account_dir / expected_platform / expected_account_id / suspected_duplicates / user_confirmation_required`。

`status = duplicate_confirmation_required` 时展示疑似重复账号并停止，等待用户确认。用户确认仍按新账号建档后，在正式调用中增加 `--allow-suspected-duplicate`。其他情况继续，不由 AI 自行读取整张账号库或判断目录。

本步骤只检查账号和目标目录，不创建正式目录，不写正式业务文件。

### 2.5 获取账号内容原始列表并立即落盘

本步骤开始前读取 `本地配置.txt` 的 `BENCHMARK_ACCOUNT_BASE_LIMIT`（留空、非法或不在 `1`—`2000` 内时按默认 `200`），冻结为本轮 `<基础内容上限>`：

- 本步骤最多保留 `<基础内容上限>` 条；账号不足上限时按实际条数处理。
- 达到上限即停止继续滚动、翻页和逐条补取，不再请求下一页。
- 达上限时必须在 `内容列表停止原因` 写明「达到本轮内容数量上限 N 条」；内容列表完整性按「可能未抓全」处理，不得宣称已获取账号全部内容。
- 本轮的「全部内容」只指本轮基础清单内的全部内容，不代表账号历史全部作品。

#### `chrome_devtools`

1. 先完整读取当前工作区根目录下的 `执行单元/获取账号内容原始列表.md`，以该文件的输入、处理和输出契约作为本步骤唯一执行依据。
2. 按子流程的输入契约组装本步骤执行上下文：
   - `账号基础信息`：使用 2.3 已落盘并校验通过的账号基础信息；
   - `本轮暂存目录`：继续使用 2.3 和 2.4 使用的同一暂存目录；
   - `内容数量上限`：使用本步骤冻结的 `<基础内容上限>`；
   - 不再传入内容可见性过滤策略；所有获取到的内容都保留，由子流程写入统一的 `公开状态`。
3. 复用 2.3 已创建的唯一中转清单，并将其作为 `获取账号内容原始列表.md` 的输入上下文；继续使用 2.3 保留的同一 Chrome 标签页，执行该文件定义的内容列表采集和滚动规则。Chrome 采集阶段只能向中转清单中的 `chrome-inbox/` 路径写入完整结构化阶段结果和主页截图，不得直接向 `<本轮暂存目录>` 写入。
4. 内容列表和截图采集结束后，调用中转脚本完成校验和转存：
   ```bash
   python3 "<当前工作区根目录>/执行单元/Chrome采集临时文件中转.py" finalize \
     --manifest-json "<manifest_json>"
   ```
   截图工具失败时增加 `--screenshot-error "<真实失败原因>"`。网络响应原文 `.txt` 只作为可选调试日志，不作为进入 2.6 的必要条件。
5. 只接受 `finalize` 返回的结构化结果。必须确认 `<账号内容原始列表JSON>` 存在且可以解析，确认其中的 `基础数据获取方式` 与本轮用户选择一致；`主页长截图状态 = 成功` 时，还必须确认截图文件和截图结果 JSON 真实存在。中转失败、JSON 校验失败或截图校验失败时，保留失败状态和真实原因。
6. 通过上述校验后返回本流程的 2.6；没有经过 `finalize` 的结果不得直接交给正式建档脚本。

#### `justoneapi`

复用已经取得的账号基础信息，调用：

```bash
python3 "<当前工作区根目录>/执行单元/JustOneAPI账号基础抓取执行器.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --account-url "<账号主页链接>" \
  --account-info-json "<账号基础信息JSON>" \
  --raw-list-json "<账号内容原始列表JSON>" \
  --reuse-account-info \
  --max-items "<基础内容上限>" \
  --acquisition-attempt 1
```

必须传入本步骤冻结的 `--max-items <基础内容上限>`，执行器在翻页过程中达到上限即停止请求下一页，不抓完再截断；不自行补写 API 返回字段。执行器必须在接口返回 `has_more = true` 时使用返回的游标继续请求；游标缺失、重复、后续页失败或达到安全上限时，必须记录“可能未抓全”和真实停止原因。只要存在有效内容，正式建档脚本仍按“已取得内容”处理，不因列表可能未抓全而把本轮改判为失败；但报告必须保留该数据边界，详细分析不得把 `内容列表获取状态 = 成功` 自动解释为“完整”。没有有效内容才按失败处理。执行器不得删除非公开内容，必须为每条内容写入统一的 `公开状态`。

本步骤结束前必须确认 `<账号内容原始列表JSON>` 真实存在并且可以解析。`<账号基础信息JSON>` 必须包含 `基础数据获取方式 / 平台 / 账号ID / 账号名 / 主页链接`；`<账号内容原始列表JSON>` 必须包含 `基础数据获取方式 / 账号内容原始列表 / 内容列表获取状态`。两份候选 JSON 的 `基础数据获取方式` 必须与本轮已确定来源一致。没有落盘就不得继续。

### 2.6 正式建档并验证产物

调用：

```bash
python3 "<当前工作区根目录>/执行单元/账号基础数据建档批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --account-type benchmark \
  --account-info-json "<账号基础信息JSON>" \
  --raw-list-json "<账号内容原始列表JSON>" \
  --data-source "<chrome_devtools或justoneapi>" \
  --acquisition-attempt 1 \
  --next-flow "执行流程/账号详细数据获取流程.md"
```

刷新已有账号时增加准备结果返回的 `--expected-platform / --expected-account-id`；用户已确认疑似重复时增加 `--allow-suspected-duplicate`。

将 2.3 和 2.5 已验证的候选 JSON 原样交给建档脚本；AI 不得手工补写、覆盖或修改正式建档输入。账号查重、目录创建、头像和截图保存、内容去重、内容 ID 分配、旧字段保留、正式 CSV 原子写入、写后校验、报告和阶段状态，全部由该脚本负责。

建档脚本完成核心正式 CSV、账号目录和内容列表的落盘及写后校验后，再将本轮结果写入账号目录过程记录中的 `本轮账号基础建档结果.json`。账号库和内容列表由脚本分别执行原子写入与写后校验；结果报告、阶段状态和正式业务文件不是一个跨文件事务，任一文件写入或校验失败都不得宣称建档完成。头像、主页截图按实际状态记录，缺失或失败不单独阻断基础建档。报告中的 `base_handoff` 是基础数据流程交给详细数据流程的最小入口合同，只包含：

- `status / blocking_reason`
- `platform / account_id`

账号名、正式文件路径、内容列表完整性和截图状态均由详细数据流程从当前正式资料重新读取，不在交接对象中复制。

只回读脚本输出和 `本轮账号基础建档结果.json`：

- `formal_commit.validated = true`、`complete = true`、`validation_status = accepted` 且 `base_handoff.status = ready`：核心正式资料建档成功，可自动进入详细数据获取；头像和主页截图状态只作为交接信息，不要求必须成功
- `verified_empty = true` 时，脚本必须返回 `base_handoff.status = blocked` 及真实原因；账号基础信息已建档，但当前没有可用于详细分析的内容
- 仅当首次尝试、目标账号尚未存在正式账号记录，且内容列表获取失败并没有有效内容时，脚本才会返回 `retry_required = true`；此时保持同一数据源，根据真实失败原因集中补抓一次，并以 `--acquisition-attempt 2` 重跑取数和建档
- 第二次仍未通过、脚本返回失败，或 `base_handoff` 缺失、不可解析：停止并如实说明原因，不得进入详细数据获取

当执行器最终判定为“失败”且没有有效内容时：新账号只把本轮失败报告写入暂存目录，不创建正式账号目录、不新增正式账号库记录，也不写入正式 `内容列表.csv`；已有账号则保留原有正式内容列表，可按脚本规则更新账号基础信息，并在报告中记录真实失败原因。执行器判定为“成功”时，即使存在数据边界或部分抓取告警，也按返回的正式校验结果处理，不由 AI 自行把“部分成功”改写为失败。

### 2.7 完成并返回结果

只读取当前正式 `本轮账号基础建档结果.json` 中的 `base_handoff`；不得从兼容阶段快照、暂存候选文件或自然语言结果重新拼接交接信息。

- `base_handoff.status = ready`：将整个 `base_handoff` 作为机器输入，直接进入《账号详细数据获取流程.md》的 `2.1 入口判断与承接基础数据结果`。详细数据流程随后必须重新读取正式账号库、正式内容列表和正式建档报告；不得把 handoff 当作分析证据。
- `base_handoff.status = blocked`：向用户说明 `blocking_reason` 后结束本轮。
- `base_handoff` 缺失、不可解析，或缺少 `status / platform / account_id` 中任一字段：视为交接失败，说明真实错误并结束本轮。`status = blocked` 时还必须提供非空 `blocking_reason`。

缺少结束记录本身就是「卡在这一步」的信号，补报反而会把卡点抹掉。
