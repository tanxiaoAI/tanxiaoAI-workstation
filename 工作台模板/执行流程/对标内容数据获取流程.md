# 对标内容数据获取流程

**本流程开始前先执行一次使用统计上报**（静默脚本，失败不影响任何流程，也不必向用户提及）：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 对标内容数据获取流程 --phase start
```

## 1. 总流程说明

1. 前置步骤
   - 进入 `2.1 检查链接`。
   - 进入 `2.2 确定取数方式`：按设置页的首选读取，不再询问用户。
2. 获取与准备资料
   - 依次进入 `2.3 获取基础结构化数据`、`2.4 校验结果并准备提交合同`。
   - 再进入 `2.5 下载封面图`、`2.6 获取视频文案`。
   - 再进入 `2.7 获取评论`，把评论原文写进正式内容目录。
3. 正式提交
   - 进入 `2.8 回写内容记录`。
   - 只有 `ok = true` 且 `status = committed` 才算正式提交成功。
4. 特征落表
   - 进入 `2.9 特征落表`，用本条**正文**判一次特征并落 `沉淀结论/内容特征实例.csv` 与 `沉淀结论/内容特征观察表.csv`。
   - 这一步**排在交接之前**：即使之后的交接步骤失败，特征也已经落表。
5. 返回结果
   - 进入 `2.10 完成并返回结果`，反馈正式资料路径、资料边界、**特征落表状态**和告警。
   - `analysis_handoff.status = ready` 时，不等待用户确认，自动进入 `对标内容分析流程.md` 的 `2.1 接收分析入口`。
   - `analysis_handoff.status = blocked` 时，只反馈真实阻断原因并结束本轮。

同一工作区可能同时有多个会话在跑。需要判断是否存在并发时，读  
`.meiling/staging/benchmark-content-base/<run_id>/运行身份.json` 比对 `content_id` 与 `平台原生内容ID`，  
不得靠目录名、文件名或取数方式推断（另一个 run 用的是 `JustOneAPI` 还是 `chrome_devtools`，  
与它抓的是不是同一条内容没有关系）。两类情况要分清：

- **同一条内容被重复抓**：`2.4` 的 `record_mode` 走 `update`，复用原记录与原目录，不新增行；
- **两条不同内容同时写同一张内容库**：各自建各自的档，互不覆盖。内容库按整表事务写入，  
  只要各自的目标行没被别人改，两条流程可以并行完成，不会互相打断。

报告并发情况时说明是哪一类，不要把「两条不同内容并行」说成「同一条内容被重复抓」。

## 2. 具体流程说明

### 2.1 检查链接

输入必须唯一定位到小红书、抖音或 B 站的一条已发布内容。缺失、平台不支持、无法识别为单条内容或明显是账号主页时停止并报告真实原因；不得读取内容库猜测链接，也不得用切换数据源掩盖输入错误。

本步只确认链接，不创建运行目录、不读取内容库。链接确认后交给 `2.2` 确定取数方式；平台不支持或无法定位单条内容时直接结束本轮。

### 2.2 确定取数方式（按设置页，不再询问用户）

#### 读取配置

取数方式由工作台「设置 → 取数方式」决定，统一保存在工作区根目录的 `本地配置.txt`（`DATA_SOURCE_PREFERENCE`），本流程不再向用户展示选择题。

```bash
python3 "<当前工作区根目录>/执行单元/对标内容数据建档执行器.py" \
  --phase resolve-source \
  --workspace-root "<当前工作区根目录>"
```

处理规则固定为：

- 用户设了首选：始终使用首选来源；
- 只配置了一种：自动使用那一种；
- 两种都可用但没设首选：默认本机 Chrome，避免意外产生接口费用；
- 首选 `justoneapi` 但没填 Token：`status = source_unavailable`，停止并提示到设置页补 Token；
- 选定来源不可用或执行失败：立即停止，不自动切换另一个来源，也不再询问是否换源或是否继续付费。

#### 来源可用性检查

确定来源后，只检查该来源本身，不再把两种来源都摆给用户选：

- `chrome_devtools`：检查连接可用性与工作区写权限（写探针 → 读回比对 → 删除，两项各判各的）。连接可用但写权限不可用时，按「不可用」处理；能按 `执行单元/取数环境搭建.md` 自动装好配好就直接装好，装好后重跑一次检查，不重复询问用户。
- `justoneapi`：按 `本地配置.txt` 的 `JUSTONEAPI_TOKEN` 判定是否已配置；已在 `resolve-source` 中校验。

检查不通过时，用一句话说明缺什么、去哪里补，然后停止本轮。不得暗中切换来源，也不得把失败包装成“需要用户选择”。

ASR 不参与本步选择：默认开启，免费额度用尽或转写失败时按 `2.6` 的规则处理，不影响取数来源。

#### 反馈给用户

正常情况下**不展示数据源选择题**，只在结果里用一句话说明本次用了哪个来源（例如「本次用本机 Chrome 取数」）。

只有检查不通过时才反馈，且只说明真实原因和下一步，不提供换源选项：

```text
当前取数方式不可用：<真实原因>

可以这样处理：<具体配置动作或链接>
```

### 2.3 获取基础结构化数据

先调用既有 `对标内容数据建档执行器.py` 的 `local-start` 阶段创建本轮暂存目录。

```bash
python3 "<当前工作区根目录>/执行单元/对标内容数据建档执行器.py" \
  --phase local-start \
  --workspace-root "<当前工作区根目录>" \
  --source-url "<2.1 已确认的内容链接>" \
  --selected-source "<2.2 已确认的 chrome_devtools|justoneapi>"
```

只接受 `ok = true`、`status = local_started` 及非空 `run_id / run_dir`。`run_dir` 必须位于 `.meiling/staging/benchmark-content-base/<run_id>`；基础数据候选、原始详情和执行回执写入该目录。封面图、视频文案和评论在 `prepare` 冻结正式目录后直接写入正式内容目录。

只执行 `2.2` 确定的数据源。本步骤不重新选择来源、不自动重试，也不合并两个来源的结果。

#### `chrome_devtools`

先查询既有建档执行器提供的唯一 Chrome canonical 输出合同：

```bash
python3 "<当前工作区根目录>/执行单元/对标内容数据建档执行器.py" \
  --phase chrome-canonical-contract \
  --workspace-root "<当前工作区根目录>"
```

输入：仅有 `--workspace-root`。输出：`ok = true`、`status = chrome_canonical_contract`，以及 `canonical_output.template / canonical_output.required_when_success`。字段类型、完整必填规则、Chrome 读取边界和旧格式兼容别名由执行器内部及《Chrome 内容详情取数协议》维护，不在本步重复展开。

流程执行者再使用当前 Chrome 会话读取 `2.1` 的链接，严格执行 `执行单元/Chrome内容详情取数协议.md`。本协议的输入固定为：

- `target_url = 2.1` 已确认的内容链接；
- `candidate_output_path = <本轮暂存目录>/内容基础结构化数据-Chrome.json`；
- `canonical_contract = 上一步查询返回的精简 Chrome 输出合同`；
- `raw_detail_output_path = <本轮暂存目录>/current-note-detail.json`，仅在需要保存小红书原始详情或平台字幕证据时提供。

协议负责完成当前单条内容的 Chrome 探索，并通过 `JSON文件写入执行器.py` 直接写入 candidate。只有收到 `ok = true`、`status = written` 且 `output_path` 与 `candidate_output_path` 完全一致的回执后，才将该路径记为本轮 `<基础数据结果路径>`，直接进入 `2.4`；本流程不再次生成、校验或读取 candidate。

#### `justoneapi`

用户在 `2.2` 选择 `justoneapi` 后调用：

```bash
python3 "<当前工作区根目录>/执行单元/JustOneAPI单条内容抓取执行器.py" \
  --workspace-root "<当前工作区根目录>" \
  --source-url "<2.1 已确认的内容链接>" \
  --output-json "<本轮暂存目录>/内容基础结构化数据-JustOneAPI.json"
```

只读取该执行器返回的 JSON 结果，并将其中的结构化字段作为后续基础数据输入；不得根据日志、自然语言或猜测补字段。结果失败时结束本轮，不重复尝试或切换来源。

#### 本步完成条件

已选来源的输出路径必须位于 `<本轮暂存目录>`，且文件真实存在；否则停止并报告真实原因。只把这一份 JSON 作为 `<基础数据结果路径>`，不得拼接两个来源。互动数据允许为空。下一步只调用 prepare 执行器并按其真实合同处理结果；校验失败时停止，AI 不自行补字段或降低校验要求。来源失败或用户选择停止时结束本轮，正式资料保持不变。

### 2.4 校验结果并准备提交合同

调用：

```bash
python3 "<当前工作区根目录>/执行单元/对标内容数据建档执行器.py" \
  --phase local-prepare \
  --workspace-root "<当前工作区根目录>" \
  --source-json "<基础数据结果路径>" \
  --selected-source "<2.2 已确认的 chrome_devtools|justoneapi>"
```

基础数据结果路径必须位于本轮暂存目录；`prepare` 将准备回执写入该目录的 `资料准备结果.json`。当前来源不是 `chrome_devtools` 或 `justoneapi`、或与基础数据的既有 `基础数据获取方式` 不一致时停止，不自动换源。

仅当本轮由 Chrome 小红书详情请求实际下载并已落盘 `<本轮暂存目录>/current-note-detail.json` 时，在上面的命令末尾追加 `--raw-detail-json "<本轮暂存目录>/current-note-detail.json"`。JustOneAPI、非小红书或 Chrome 未取得原始详情时必须省略该参数。此时 `prepare` 仍然冻结基础数据合同；平台字幕不可用时，后续视频文案来源再按规则回退一次本地 ASR。

只接受 `ok = true`、`status = prepared`，并且以下字段与本轮合同一致：

- `content_id`：本轮内容身份；
- `content_dir`：正式内容目录目标，prepare 阶段不创建；
- `native_content_id`：后续校验平台字幕或正文证据的原生内容身份；
- `expected_cover_result_path / expected_transcript_result_path`：本轮执行结果文件路径；
- `expected_staged_cover_path / expected_staged_transcript_path / expected_staged_summary_path / expected_staged_comments_path`：兼容旧 `commit` 参数名；本地流程实际返回正式内容目录中的业务文件路径。其中 `expected_staged_comments_path` 指向本轮正式 `评论.md`，供 `2.8` 的 `--staged-comments-path` 使用。

prepare 只返回冻结后的身份、路径和版本快照，不创建正式目录、不写正式资产或 CSV。失败时停止；AI 不补字段、不判断重复、不生成内容 ID、不拼接正式目录。

prepare 还会做两件与本步相关的事：

1. 在 `<本轮暂存目录>/运行身份.json` 写入本轮运行的可读身份：`content_id`、`平台`、`平台原生内容ID`、  
   `标题`、`媒介形式`、`记录模式`、`取数方式`、`对外页面链接`、`写入时间`。  
   需要判断「另一个 run 是不是同一条内容」时，**读取这个文件**，不得靠目录名、文件名或时间顺序猜。  
   暂存目录里其他文件名（如 `内容基础结构化数据-JustOneAPI.json`）只反映取数方式，不反映内容身份。
2. 在回执里补充重复抓取提示字段：

```yaml
record_mode: <create|update>
existing_record_source: <原记录的取数方式；create 时为空>
existing_assets_updated_at: <原内容目录内最近一次资产写入时间；create 时为空>
```

`record_mode = update` 表示本轮命中了内容库里的既有记录，会复用原记录与原内容目录（不新增行、不新建目录）。  
这两个字段只用于向用户说明，不改变提交行为。

### 2.5 下载封面图

`封面图原链接` 来自 `2.3` 生成并写入暂存目录的基础数据候选，经 `2.4` 的 `prepare` 解析后作为 `source` 字段使用。下面命令的 `content-id / title / platform / cover-url` 均来自该基础数据和 prepare 回执；`output-path` 使用 prepare 冻结的正式内容目录路径，`result-output-json` 仍写入本轮暂存目录。

有 `封面图原链接` 时调用：

```bash
python3 "<当前工作区根目录>/执行单元/下载封面图执行器.py" \
  --content-id "<prepare.content_id>" \
  --title "<基础数据.标题>" \
  --platform "<基础数据.平台>" \
  --cover-url "<基础数据.封面图原链接>" \
  --output-path "<prepare.expected_staged_cover_path>" \
  --result-output-json "<prepare.expected_cover_result_path>" \
  --workspace-root "<当前工作区根目录>"
```

没有原链接或下载失败时保留真实结果并继续；不重试，不修改或删除已有正式封面。提交时仍传入 `2.4` 返回的预期结果路径和暂存路径。

### 2.6 获取视频文案

调用既有视频文案执行器，将平台字幕或本地 ASR 结果写入 prepare 已冻结的正式 `视频文案.md`。平台字幕和 ASR 的身份校验由执行器及共用证据选择器完成；标题、摘要和搜索片段不得冒充视频文案。

B站视频获取平台字幕时，必须在当前 Chrome 页面会话中重新请求 `x/player/v2`，从本次响应取得最新 `subtitle_url`，并立即读取该地址的完整 `body`。不得复用上一次运行、旧页面快照或历史暂存目录中的字幕 URL。

将本次实际获取到的完整字幕文本写入 `<本轮暂存目录>/视频文案输入.json`。该文件必须是一次完整 JSON，包含以下字段；字段缺失或身份与本轮对不上时执行器会直接拒绝：

- `content_id`：本轮的正式内容 ID，与 prepare 结果一致
- `run_id`：本轮暂存目录名
- `source`：取值只能是 `formal_transcript` / `platform_caption` / `asr` / `unavailable`
- `status`：取值 `success` / `failed` / `unavailable`
- `text`：字幕或文案正文
- 平台字幕（`source = platform_caption`）额外需要 `video_url` 或 `url_hash`，其地址必须与本轮 `基础数据.json` 的「视频下载链接」一致
- ASR 失败时额外需要 `failure_reason`：写明服务端返回的真实状态码与原始消息

再调用：

```bash
python3 "<当前工作区根目录>/执行单元/对标内容数据建档执行器.py" \
  --phase local-write-transcript \
  --workspace-root "<当前工作区根目录>" \
  --prepare-json "<本轮暂存目录>/资料准备结果.json" \
  --transcript-json "<本轮暂存目录>/视频文案输入.json"
```

视频不存在可用平台字幕时，调用：

```bash
python3 "<当前工作区根目录>/执行单元/对标内容数据建档执行器.py" \
  --phase local-asr \
  --workspace-root "<当前工作区根目录>" \
  --prepare-json "<本轮暂存目录>/资料准备结果.json" \
  --asr-provider volcengine
```

只将生成的 `本地ASR结果.json` 作为 `视频文案输入.json` 提交。ASR 默认开启：先用托管免费额度（新用户按设备 1 小时），额度耗尽或托管失败时自动回退用户本地的火山 Key。托管和本地回退都不可用时**不阻断整条流程**：保留失败原因，按“没有视频文案”跳过正文，继续 `2.7` 抓评论和 `2.8` 提交；分析阶段按有限报告处理，正文相关结论写“信息不足”。

同一内容最多尝试 3 次（首次 + 两次重试），且只对可恢复失败重试（网络超时、火山服务繁忙一类服务端错误）；鉴权失败、资源未授权（如状态码 `45000030`）、参数错误等重试不会改变结果的情况立即停止，不换模型、不换服务、不自动切换资源。失败时必须写明服务端返回的真实状态码与原始消息，不得用笼统的 HTTP 状态描述代替。图文内容不调用 ASR。

`local-write-transcript` 成功后生成唯一 `正文获取结果.json`（其中的 `text_path` 指向已写入的正式 `视频文案.md`），正文直接写入正式 `视频文案.md`；确认没有可用视频文案时生成明确的空文件标记。平台或正文结果明确标记“确认无正文”时，`视频文案.md` 写入该标记，分析阶段按“确认无正文”处理，不把标记当作作者正文。结果缺失或身份不一致时停止，不提交资料。

### 2.7 获取评论

进入本步前，先取本轮基础数据里的 `评论数`（即 `2.3` 生成的基础数据候选中的 `<基础数据.评论数>`，平台声明口径）。**本轮还没回写内容库，不要试图从内容库读这一列。**

- `评论数 = 0`：**不发起抓取**，调用执行器并把 `--comment-count` 取 `0`。命令照下方对应数据源的示例写，只做两处调整：`--comment-count` 填 `0`；`chrome_devtools` 支**去掉** `--raw-input-json` 一行（不发请求，也就没有原始响应文件）。`justoneapi` 支本来就不带该参数，无需改动；
- `评论数 ≥ 1`、或该值为空：照常抓取。**空值表示未知，不等于 0**，不得当成 0 跳过。

评论数为 0 时平台本来就没有评论可抓；小红书侧页面不会发出评论请求（见下方取数口径），硬抓必然失败。

两种情况都会产出正式 `评论.md` 与 `评论.json`：抓取时写实际内容，跳过时写明「平台声明该内容评论数为 0，未发起抓取」。**跳过不是失败**，按正常结果继续 `2.8`。

评论原文与封面图、视频文案一样，直接写入 `2.4` 冻结的正式内容目录：`<prepare.content_dir>/评论.md`（人读）与 `<prepare.content_dir>/评论.json`（机读全量），与 `视频文案.md` 平级，不开子目录。只有抓取回执写入本轮暂存目录。

本步只取一级评论。一级评论响应里自带的那几条二级回复随该条一并保存，不额外请求楼中楼。

取数方式沿用 `2.2` 确定的来源，本步不重新选择来源，也不自动换源。

#### `chrome_devtools`

**评论接口不会随页面加载自动发出，必须先触发。** 打开 `2.1` 的链接后，页面只会请求详情、点赞收藏这些接口，评论接口一条都不会发。此时在请求列表里搜不到评论请求，**既不等于平台没有评论，也不等于抓取失败**，只说明还没触发。没触发就去判定「未取得」，是本步最容易犯的错（2026-11-01 实测：抖音作品页加载完成后评论请求为 0，主动调用评论接口立刻返回 `status_code = 0`、`total = 101`）。

触发方式二选一：

1. 点开评论区（抖音在播放器右侧评论按钮、B 站在下方评论区、小红书在笔记下方），把评论列表滚动到覆盖所需页数；
2. 在已登录的当前页会话里直接请求评论接口：抖音、B 站可行；小红书自行构造的裸请求会被平台挡下，只能用方式 1。

抖音直连示例（在作品页的页面上下文里执行，自动带 Cookie）：

```text
GET /aweme/v1/web/comment/list/?device_platform=webapp&aid=6383&channel=channel_pc_web
    &aweme_id=<平台原生内容ID>&cursor=<0,50,100...>&count=50&item_type=0
    &pc_client_type=1&version_code=170400&version_name=17.4.0&cookie_enabled=true
    &platform=PC&browser_language=zh-CN&browser_platform=MacIntel
```

响应里取 `comments[]`、`total`、`cursor`、`has_more`；`count` 固定 `50`，游标按返回的 `cursor` 前进。

触发之后，读取该内容评论接口的原始响应，取 3 页，合并写入：

```text
<本轮暂存目录>/评论原始响应.json
```

该文件是一次完整 JSON，包含 `platform`、`native_content_id` 和 `pages`（每页原始响应对象的数组）。身份与本轮对不上或结构不完整时，执行器直接拒绝。

各平台的页大小、请求方式和排序固定，不得自行调大或更改：

- 抖音：直接请求评论接口，`count` 固定 `50`，游标每次加 `50`。传更大的 `count` 仍只返回 50 条，但返回的游标会按请求值前进，把未返回的评论跳过。
- B 站：直接请求评论接口，`ps` 固定 `30`，排序固定 `mode=3`（热度）。`ps` 传 50 或 100 同样只返回 30 条。
- 小红书：只能读取页面自身发出的评论请求，每页 10 条；自行构造的裸请求会被平台挡下。需要后续页时滚动评论区，再读取页面随之发出的同类请求。

取完先自检，三项都要写清楚：平台声明的 `total`、本次累计去重条数、最后一页的 `has_more`。`has_more = true` 但已到 3 页上限，写明「按页数上限停止」；`has_more = false` 但累计条数明显少于 `total`（平台只开放部分评论、或需要登录），写明真实差距。两种情况都不补造、不说成已抓全。

#### `justoneapi`

调用：

```bash
python3 "<当前工作区根目录>/执行单元/内容评论抓取执行器.py" \
  --workspace-root "<当前工作区根目录>" \
  --platform "<基础数据.平台>" \
  --native-id "<基础数据.平台原生内容ID>" \
  --comment-count "<基础数据.评论数>" \
  --content-dir "<prepare.content_dir>" \
  --source justoneapi \
  --pages 1 \
  --output-json "<本轮暂存目录>/评论抓取结果.json"
```


本支由执行器按 `--pages` 自行翻页，流程执行者不构造评论请求。小红书固定 `sort=like_count`（取热评）；B 站和抖音的接口不提供排序参数，只能取平台默认序。

用户要求继续抓取时，重新走 `2.1` 至 `2.4` 取得本轮冻结路径，再执行本步并追加 `--continue`，页数参数照旧；`2.4` 会命中既有记录（`record_mode = update`），复用原记录与原目录。执行器按评论 ID 去重合并后重写正式文件，不回退已抓到的内容。

继续抓取必须与已存档的数据源一致：执行器读到 `评论.json` 头部记录的是另一个来源时直接报错停止，不得静默混源。同一条内容在两个来源下的排序与批次并不相同，混源会让存档失去可比性。

只接受 `ok = true`，且 `status` 为 `written` 或 `skipped_zero_comments`；回执里的 `output_path` 指向正式 `评论.md`、`json_path` 指向正式 `评论.json`。`status = skipped_zero_comments` 表示平台声明评论数为 0、本步未发起抓取（评论数未知时不会走到这个状态）。回执至少包含 `platform`、`source`、`fetched`（本次新增条数）、`deduped`（去重丢弃条数）、`cumulative`（去重后累计条数）、`total`（平台声明的评论总数）、`has_more`、`next`（继续抓取状态）和 `warnings`。

评论抓取失败或平台未返回评论时不阻断本轮提交：继续 `2.8`，由提交结果返回 `asset_status.comments = missing` 或对应告警。评论数为 0 时本步已产出「未发起抓取」的正式存档，正常继续 `2.8`，不按失败处理。已经写好的 `评论.md` / `评论.json` 不得因本轮失败被删除或覆盖。

### 2.8 回写内容记录

调用：

```bash
python3 "<当前工作区根目录>/执行单元/对标内容数据建档执行器.py" \
  --phase commit \
  --workspace-root "<当前工作区根目录>" \
  --source-json "<基础数据结果路径>" \
  --prepare-json "<本轮暂存目录>/资料准备结果.json" \
  --cover-result-json "<本轮暂存目录>/封面图获取结果.json" \
  --transcript-result-json "<本轮暂存目录>/正文获取结果.json" \
  --staged-cover-path "<prepare.expected_staged_cover_path>" \
  --staged-transcript-path "<prepare.expected_staged_transcript_path>" \
  --staged-comments-path "<prepare.expected_staged_comments_path>" \
  --output-json "<本轮暂存目录>/资料提交结果.json"
```

这是唯一正式 CSV 写入阶段。封面图、视频文案和评论已经在前置步骤直接写入 prepare 冻结的正式目录；本阶段只校验这些文件并回写内容库。`--staged-comments-path` 的取值来自 `prepare` 冻结的路径，指向本轮正式 `评论.md`；本轮评论抓取失败时该文件可能不存在，此时返回 `asset_status.comments = missing`，不算提交错误（评论数为 0 时 `2.7` 会产出「未发起抓取」的正式存档，文件存在，走 `committed`）。只消费执行器返回的 `ok / status / content_id / content_dir / committed_files / asset_status / warnings`。

提交结果：

- `ok = true` 且 `status = committed`：进入 `2.9`。
- 结果缺失、不可解析、`status != committed` 或提交异常：先判断是不是并发冲突，再决定停还是重试。
  - 报 `concurrent source change: <路径>`：属于外部会话改动，按 `执行单元/并发冲突处置.md` 处置。  
    **本轮尚无正式写入时**，等待共享文件稳定（`对标资料/对标内容库.csv` 与当前账号的 `内容列表.csv`）  
    后原样重跑本步，最多两轮；执行器会重新读取共享表再合并本轮结果，不需要重跑取数。
  - 报 `target_content_conflict:changed_since_prepare / target_missing / merge_ambiguous / identity_match_count`：  
    同样是外部会话改动（`2.4` 冻结的那一行在提交前被改过、已消失，或被别的会话抢先建了同一条）。  
    **本轮尚无正式写入时**，等待共享文件稳定后，**回到 `2.4` 重跑 `local-prepare`**（参数与首次一致，刷新行指纹与冻结路径），  
    再重跑本步，最多两轮。**只重跑本步无效** —— 冲突判据就是 `2.4` 冻结的那份行指纹，快照不刷新会原样再报。
  - 报 `target_content_conflict:content_id_missing`：匹配到的行没有 `内容ID`，属共享表的数据问题，不是并发时序问题。  
    直接停止并如实报告，不要重试。
  - **本轮已有正式写入，或其他任何错误**：停止并报告真实错误；用户修正后以新运行重新提交。  
    `--cover-result-json` 与 `--staged-cover-path` 必须始终传入，取值来自 `prepare` 冻结的路径。本轮没有封面原链接、`2.5` 因此未执行时同样要传：命令本身不区分「有没有下载封面」，路径留空会直接报错，错误码会指明缺失的参数名（如 `staged_cover_path_missing`）。封面文件本身不存在不算错误，按下一条返回 `asset_status.cover = missing`。
- `asset_status.cover / summary = retained_existing`：旧文件保留但不算本轮成功，必须报告告警。
- `asset_status.cover / summary = missing`：正式记录可完成，但必须报告缺失。
- `asset_status.transcript = retained_existing_blocked | missing_blocked`：基础记录可已提交，但必须报告本轮正文不可用。
- `asset_status.comments = missing`：本轮评论抓取失败或正式评论文件不存在。正式记录可完成，但必须报告本轮评论不可用，不得把它说成已完成。（评论数为 0 不属于此项：`2.7` 会产出「未发起抓取」的正式存档，走 `committed`。）

### 2.9 特征落表（实例 + 观察）

**作用**：把本条内容的**正文**交给模型判一次特征，直接落两张表。**本步不依赖内容分析** —— 它读的是内容自己的正文，不是分析报告，也不产出任何分析报告。

#### 输入

- 本条内容的**正文**（`<内容目录>/视频文案.md`；非视频内容取其对应的正文文件）；
- `沉淀结论/内容特征词典.csv`。

#### 执行

**1) 生成候选**：读本条正文，按 `提示词/内容特征提取提示词.md` 生成一份候选，写进 `<本轮暂存目录>/<内容ID>-特征候选.md`。

候选三节固定为 `1. 核心标准特征`、`2. 候补标准特征`、`3. 待补充标签`；**标准标签、所属层级、特征小类一律不写**，由执行器按词典补齐。

**正文缺失或不可读时跳过本步**（不落表、不算失败），在 `2.10` 的反馈里说明"本条无正文，未落特征"。

**2) 落表**：

```bash
python3 "<工作区根目录>/执行单元/内容特征落表执行器.py" \
  --workspace-root "<工作区根目录>" \
  --source 对标内容 \
  --content-id "<内容ID>" \
  --candidate-path "<本轮暂存目录>/<内容ID>-特征候选.md"
```

不加 `--action` 即**单条落表**；加 `--validate-only` 只校验、不写任何文件。

#### 成功条件与失败处理

- 返回 `status = committed` 才算落表完成；反馈里的实例条数与观察条数取回执的 `core_feature_count` / `observation_count`。
- `内容ID` 在 `对标资料/对标内容库.csv` 里匹配不到唯一一条：停止，报真实错误。
- 候选结构不合规、或特征 ID 不在正式词典里：停止，如实反馈 `error`，**不改写候选反复重试**。
- **本步失败不阻断 `2.10`**：正式资料已经保存，如实说明"资料已保存，特征未落表"。

### 2.10 完成并返回结果

读取当前 `<本轮暂存目录>/资料提交结果.json`；评论条数从 `2.7` 的 `<本轮暂存目录>/评论抓取结果.json` 取。

特征落表状态取 `2.9` 的回执：写明本条落了几条实例（`core_feature_count`）和几条观察（`observation_count`）；`2.9` 因无正文跳过时写「本条无正文，未落特征」；`2.9` 失败时照实说明「资料已保存，特征未落表」和真实错误。本步同时反馈正式资料路径、资料边界和前面各步的告警。

如果 `2.4` 的 `record_mode = update`，必须在结果里写明本篇此前已经抓过：用  
`existing_assets_updated_at` 说明上次写入时间、用 `existing_record_source` 说明上次的取数方式，  
并说明本轮复用了原记录与原目录。这条提示只是让用户自己判断要不要重跑，不阻断流程。

评论情况必须一并反馈：这条内容共多少条评论、本次抓到多少条、去重后累计多少条、还有多少条没拉。`status = skipped_zero_comments` 时说明该内容评论数为 0、本轮未发起抓取，**不要写成抓取失败**；`asset_status.comments = missing` 时说明本轮评论不可用；还没拉完时说明可以继续抓取，并写明继续抓取仍是同一个数据源。评论是否拉完不影响本步的交接判断，也不得因此改变交接行为。

提交成功后继续读取回执中的 `analysis_handoff`：

- `status = ready`：将整个 `analysis_handoff` 作为机器输入交给 `对标内容分析流程.md` 的 `2.1 接收分析入口`；不得询问用户是否继续，不得读取本轮暂存目录中的业务文件代替正式资料，也不得自行拼接正式路径。回执带 `transcript_missing = true` 时照常进入分析，由分析流程按有限报告处理。
- `status = blocked`：不进入分析，固定说明 `资料已保存，但当前不能开始分析：<blocking_reason>`，并保留本轮回执路径。
- `analysis_handoff` 缺失、不可解析，或 `status = ready` 却缺 `content_id` / `platform` / `title` / `media_type` / `content_dir`：视为交接失败，固定说明 `资料已保存，但分析入口交接失败：<真实错误>`，不得声称分析已经开始。`status = blocked` 时字段少不算交接失败，走上面 `blocked` 分支。

`analysis_handoff` 在 `status = ready` 时至少包含：`status`、`content_id`、`platform`、`title`、`media_type`、`content_dir`、`transcript_path`、`missing_identity_fields`、`blocking_reason`；正文缺失时额外带 `transcript_missing` 和 `transcript_warning`。`status = blocked` 只用于内容尚未建档等真正无法分析的情况，不再因为缺正文或 ASR 失败而阻断。
