# 内容定位流程

**本流程开始前先执行一次使用统计上报**（静默脚本，失败不影响任何流程，也不必向用户提及）：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 内容定位流程 --phase start
```

## 1. 总流程说明

1. 确认媒介形式和内容目标
   - 进入 `2.1 确认媒介形式和内容目标`；
2. 生成方案并写入
   - 使用协调器回执中的输入，进入 `2.2 生成方案并写入`；
   - 首次进入时生成并写入第一版正式定位；
3. 展示方案并选择
   - 进入 `2.3 展示方案并选择`，展示当前正式定位；
   - 用户可以继续、讨论，或提出修改；
   - 对标内容直达生产不走这一步：定位六项全部逐项继承对标分析，保存后直接进入 `2.5`；
4. 讨论和修改方案
   - 用户提出讨论或修改意见时进入 `2.4 讨论和修改方案`；
   - 仅修改定位内容时，直接写入新版后回到 `2.3`；
   - 修改媒介形式或内容目标时，回到 `2.1`；
5. 确认并交接下一阶段
   - 用户明确确认当前定位并继续后，进入 `2.5 确认并交接`；
   - 对标内容直达生产在 `2.2` 保存成功后直接进入 `2.5`，不等用户回话；
   - 协调器确认定位并返回下一阶段后，直接交给内容初稿流程。

### 协调器使用规则

Skill 已经完成入口识别、最小参数收集和首次 `prepare` 调用。协调器已经读取、校验并冻结本次入口对应的上游业务资料；流程不再设置“读取上游信息”业务步骤，也不重新判断入口。这里的“已经读取”只指上游输入文件，不包括后面才按需读取的内容生产方法论和定位提示词。

流程只使用当前协调器回执中与当前步骤有关的字段：

- `current_stage.flow_file`：必须是 `执行流程/内容定位流程.md`；
- `state_file`：本次内容生产状态文件；
- `inputs`：协调器已经校验并冻结的上游资料；
- `action_contract`：仅在 `2.2` 生成并写入时使用，提供候选文件的精确路径和保存请求；
- `decision_contract`：仅在 `2.3` 展示后确认继续、以及 `2.5` 确认交接时使用；
- `display_identity`：仅在 `2.3` 展示已保存版本时使用。

进入 `2.1` 至 `2.4` 时，回执的当前阶段必须是“内容定位”；`2.5` 成功后，当前阶段必须是“内容初稿”。回执为 `ok = false`、当前步骤所需字段缺失或状态为 `blocked` 时，说明真实原因并停止。流程不自行扫描文件、不自行拼接路径、不直接调用底层状态执行器。

`inputs` 中可能出现的具体资料由入口决定。首次准备会返回完整冻结输入并同时生成本轮 `输入快照.json`；后续回执对大块资料可只返回 `snapshot` 引用。读取引用时必须校验快照路径、SHA-256、状态文件、内容ID和阶段版本，不重新扫描正式资料或从聊天上下文补齐：

- 选题分析：`topic_analysis`，来源是选题库登记的正式选题分析路径；
- 对标直达生产：`reference_content_analysis`，来源是我方内容库登记的正式对标分析路径；
- 对标借鉴判断：取自内容分析（`reference_content_analysis`）的「借鉴判断」表（原 `reference_content_card*` 已退役）。输入侧只提供**整份**内容分析，不再按维度切分；定位阶段需要哪几个维度由本流程与提示词自行取用，缺失时如实说明，不得自行补写；
- 开头标签范围：`opening_label_options`，来源是正式 `沉淀结论/内容特征词典.csv` 中「特征小类=开头」的启用特征，只包含标签、定义、适用边界和排除边界；定位阶段只把它作为判断切入方式的参考，不得直接当成切口文案，也不得输出特征 ID；
- 内容类别范围：`content_category_options`，来源是正式 `沉淀结论/内容特征词典.csv` 中「特征小类=内容类别」的启用特征，只包含标签、定义、适用边界和排除边界；它是「内容类别」唯一的取值来源，定位阶段必须逐字选用其中一项 `label`，不得自造类型名称、不得改写，也不得输出特征 ID。词典里没有贴合标签、或该输入为空时，`内容类别` 写 `信息不足` 并在方案边界说明；不得因为拿不到范围就跳过建档；
- 独立生产：用户临时主题和需求，不要求选题分析文件；
- `current_summary`：对标直达生产时不参与主题、目标用户、核心痛点、收益承诺、核心命题和切口的判断，也不得作为我方事实、案例、经历或结果的证据；关联选题生产和独立生产时只用于判断我方适配性和长期方向。缺失时仅在后两类入口的方案边界中说明，不额外启动其他 Skill。

### 协调器命令

```bash
python3 "<当前工作区根目录>/执行单元/内容生产阶段协调器.py" --workspace-root "<当前工作区根目录绝对路径>" --action prepare --state-file "<state_file>"
python3 "<当前工作区根目录>/执行单元/内容生产阶段协调器.py" --workspace-root "<当前工作区根目录绝对路径>" --action save --state-file "<state_file>" --stage-candidate-file "<stage_candidate_file>"
python3 "<当前工作区根目录>/执行单元/内容生产阶段协调器.py" --workspace-root "<当前工作区根目录绝对路径>" --action decide --state-file "<state_file>" --decision confirm
```

## 2. 具体流程说明

### 2.1 确认媒介形式和内容目标

如果回执已经有媒介形式和内容目标，向用户展示当前值并请其确认；**本次指令里已经写明这两项时（例如工作台生成的指令写着「媒介形式：视频 / 内容目标：流量，建档时一起带上」），视为用户已经确认，直接采用，不再单独请确认**；缺少任一项时，使用下面的固定话术询问：

```text
开始做内容前，先确认两个设置：

1. 媒介形式：视频、图文、文章，还是其他？
2. 内容目标：这条内容主要想要流量、涨粉，还是交易？

这两个设置会影响后面的内容定位和写法。请直接告诉我你的选择。
```

媒介形式必须归一为 `视频 / 图文 / 文章 / 其他`，内容目标必须在 `流量 / 涨粉 / 交易` 中选一个。

确认后按两种情况处理：

1. 用户确认原设置不变：直接进入 `2.2`，不重复调用 `prepare`。
2. 用户补充或修改设置：沿用当前回执的 `prepare_input_contract` 重新调用 `prepare`，并同时带上本次内容的内容身份。独立生产首次建档后再补媒介形式或内容目标时，内容库里已有同标题的「生产中」记录；此时不带内容身份会被判为重复建档并直接拒绝（回执消息：`独立内容<内容ID>已存在生产中记录；补充媒介形式或内容目标时必须提供原state_file或content_id，拒绝重复建档`）。
   1. `media_form` 只对应 `--media-form`
   2. `content_task` 只对应 `--content-task`。
   3. 内容身份用 `state_file` 对应 `--state-file`，值用当前回执的 `state_file`。这是更新设置的正式路径：内容定位已经生成、流程处于「等待用户确认」时，只有带 `--state-file` 才会走设置更新分支，并且必须同时给出有效的媒介形式和内容目标。
   4. 内容定位尚未生成时（例如独立生产首次进入定位），`content_id` 对应 `--content-id`、值用本次内容的 `内容ID`，也可以替代；但内容定位已经生成后要修改设置，只能用 `--state-file`。
   5. 本次调用只更新媒介形式和内容目标，不重新建档、不生成新的内容ID。本次调用不带 `--topic-name`。后续只使用新的回执和候选，不复用旧候选。

### 2.2 生成方案并写入

冻结输入缺少我方当前概要时，在定位结果中说明“缺少我方当前概要”，只按已提供的选题或主题判断，不阻断生成。

#### 生成

首次进入本节时，按以下顺序生成本轮定位候选：

1. 先读取协调器 `inputs` 中本入口实际提供的资料，并按入口确定使用范围：对标直达生产时，主题、目标用户、核心痛点、收益承诺、核心命题、切口六项必须逐项继承 `reference_content_analysis` 中的完整定位画像。除用户明确修改某项外，不得强化、收窄、替换或重组，也不得用 `current_summary`改写六项定位。关联选题生产和独立生产时，按各自冻结资料判断定位，`current_summary`只用于适配性和长期方向。
2. 再读取 `分析框架/内容生产方法论.md` 的 `### 5.1 内容定位`；有参考内容分析时，只读取其「借鉴判断」表里 `选题`、`切口` 两行的正式结论。
3. 基于上述资料和 `content_category_options`，调用 `提示词/内容生产-内容定位提示词.md`，生成一个完整、唯一、自洽的内容定位方案；`内容类别` 必须从 `content_category_options` 里逐字取一个标签。
4. 把生成的方案写入本轮候选文件。

如果本轮 `prepare` 是因媒介形式或内容目标变更产生，必须以本轮冻结的媒介形式和内容目标为约束，重新调用定位提示词生成完整内容定位。

候选文件必须按当前 `action_contract.required_outputs` 的要求生成：

`stage_candidate_file` 只包含一个 `## 内容定位` 区块和完整定位方案，不写分类、分类ID或特征ID。

候选只是本轮临时结果，尚未成为正式内容定位版本。

#### 保存

按 `action_contract.submit_request_schema` 调用协调器 `save`，提交本轮 `stage_candidate_file`，将临时定位候选写为正式版本。

只有协调器返回 `ok = true`、`status = waiting_for_user` 和新的 `decision_contract`，才算本次定位已保存。

保存成功后按入口分流：

- **对标内容直达生产**：定位六项（主题、目标用户、核心痛点、收益承诺、核心命题、切口）全部逐项继承对标分析，都是刚拆完的既有结论，没有需要用户再拍板的新判断 —— 保存成功后**直接进入 `2.5 确认并交接`**，不停在 `2.3` 等确认，也不问“继续”。
- **关联选题生产、独立生产**：进入 `2.3` 展示本次正式版本并等用户确认。

保存失败时，上一版正式定位保持不变；本轮候选仍是临时结果，不能展示为正式版本。

### 2.3 展示方案并选择

用户可见结果固定使用以下展示结构：

```text
## 内容定位候选

- 内容名称：<内容名称>
- 内容ID：<内容ID>
- 媒介形式：<视频 / 图文 / 文章 / 其他>
- 内容目标：<流量 / 涨粉 / 交易>

### 工作台查看
- 内容生产：<dashboard_base_url>/index.html#creation-board

### 当前版本
<定位提示词生成的完整定位方案>

### 下一步
如果还需要修改，请直接告诉我；
如果当前定位已经明确，请回复“继续”，进入内容初稿。
```

展示字段来源：

- `内容名称`、`内容ID`、`媒介形式`、`内容目标`：使用保存或更新成功回执中的 `display_identity`；
- `当前版本`：使用本轮刚保存的正式定位版本；
- `dashboard_base_url` 只能使用工作台启动后返回的本地基础地址，取址方式固定按 `执行单元/工作台地址获取.md` 执行；取不到地址时写“工作台未打开”，不阻断正式结果反馈。

必须展示本轮刚保存的完整定位方案；不得用变化点、摘要或“其余保持不变”替代当前版本。

展示后：

- 用户提出讨论或修改意见：进入 `2.4`；
- 用户明确确认当前定位并要求继续（如“继续”“按当前定位进入下一步”“定位可以了”）：进入 `2.5` 确认并交接；
- 用户没有明确选择：停在本节，等待用户决定。

### 2.4 讨论和修改方案

用户在 2.3 看到当前版本后，在本节讨论问题或提出修改意见。

- 用户只是在讨论标题、开头、结构、互动或机制技巧：说明这些属于后续内容初稿、初稿或终稿阶段，不在本阶段提前决定；
- 用户没有明确修改范围：继续讨论，不生成新方案，也不写入；
- 用户明确要修改的问题：记录具体调整要求；这句话本身就是本轮修改指令，不再单独请求“修改授权”，未提出修改的部分保持不变；

按修改内容分两种情况处理：

1. 只修改定位方案：读取当前正式定位方案和当前阶段版本，基于用户反馈重新调用定位提示词，生成完整的新方案。然后调用协调器 `update-positioning`：
   ```bash
   python3 "<当前工作区根目录>/执行单元/内容生产阶段协调器.py" \
     --workspace-root "<当前工作区根目录绝对路径>" \
     --action update-positioning \
     --state-file "<当前状态文件>" \
     --positioning-content "<重新生成的完整定位方案>" \
     --expected-stage-version <当前阶段版本>
   ```
   `--expected-stage-version` 取当前回执 `route.当前阶段状态.版本`；传错版本会被拒绝（用于防止并发覆盖）。只有协调器返回 `ok = true`、`status = waiting_for_user` 和新的 `decision_contract` 后，才回到 `2.3` 展示新版；保存失败时保留上一版正式定位。
2. 修改媒介形式或内容目标：不重复展示 2.1 的固定询问话术，直接执行 2.1 的“用户补充或修改设置”分支。沿用当前回执的 `prepare_input_contract` 重新调用 `prepare`：传入用户修改后的设置，并按 2.1 带上 `--state-file`（本分支下内容定位已经展示，只能用这个）；用户只修改其中一项时，另一项沿用当前值。本次调用不重新建档、不生成新的内容 ID。获得新回执后进入 2.2 生成并写入新版，再进入 2.3 展示新版。

不能用多个并列方案掩盖受众、痛点、收益、命题或切口之间的冲突。信息不足但可以形成带边界的方案时先给出暂定判断，只有无法形成任何可执行方案时才补问一个问题。

### 2.5 确认并交接

确认使用当前回执的 `decision_contract`：

```bash
python3 "<当前工作区根目录>/执行单元/内容生产阶段协调器.py" --workspace-root "<当前工作区根目录绝对路径>" --action decide --state-file "<state_file>" --decision confirm
```

两条路都用同一份 `decision_contract` 提交 `decision = confirm`：用户在 `2.3` 明确确认后提交；对标内容直达生产在 `2.2` 保存成功后直接提交，不等用户回话。不再重复生成或保存同一版本，也不要求额外确认。

对标直达这次提交不需要铺 `2.3` 那整段展示，也不写“回复继续”，用一句话交代即可（例如「定位按这条对标的六项继承，不再问你；接着出内容框架和初稿」），紧接着进入内容初稿。

只有协调器最终回执同时满足以下条件，才把整份回执交给内容初稿流程：

1. `ok = true`；
2. `status = ready`；
3. `completed_stage = 内容定位`；
4. `next_stage = 内容初稿`；
5. `current_stage.name = 内容初稿`。

这份回执已经包含内容初稿所需的 `state_file`、`inputs` 和 `action_contract`；内容初稿流程直接使用，不再重复 `prepare`。

确认提交失败时，当前定位保持“等待用户确认”。如果定位已确认、但媒介形式同步或内容初稿准备失败，协调器会返回 `status = blocked`：停止交接，向用户说明返回的真实原因，并按回执提供的恢复动作继续；不重复确认当前定位。

---

**本流程结束后执行一次使用统计上报**（静默脚本，失败不影响任何流程）：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 内容定位流程 --phase end --status ok
```

正常走完用 `--status ok`；按阻断分支收尾用 `--status blocked`。**没走到这一步就不用补报** ——  
缺少结束记录本身就是「卡在这一步」的信号，补报反而会把卡点抹掉。
