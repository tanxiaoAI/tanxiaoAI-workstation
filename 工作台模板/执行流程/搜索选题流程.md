# 搜索选题流程

**本流程开始前先执行一次使用统计上报**（静默脚本，失败不影响任何流程，也不必向用户提及）：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 搜索选题流程 --phase start
```

## 1. 总流程说明

1. 冻结账号方向、平台和数据源：进入 `2.1`。
2. 生成并冻结 3—6 个搜索关键词：进入 `2.2`。
3. 完成一轮平台搜索：进入 `2.3`。
4. AI 判断每条搜索结果与账号方向的相关性：进入 `2.4`。
5. 对 AI 选中的内容补正文和评论：进入 `2.5`。
6. AI 对执行器初筛后的评论再做语义筛选：进入 `2.6`。
7. 一次生成 9 条推荐选题：进入 `2.7`。
8. 正式保存并反馈：进入 `2.8`。

本流程只有一轮内容搜索。同一批结果同时用于归纳选题、查看来源和提取评论证据；选题形成后不再发起第二次对标搜索。

### 执行器使用规则

- `搜索选题流程协调器.py`：冻结上下文和查询计划，校验并保存恰好 9 条推荐。
- `搜索选题数据执行器.py`：执行 JustOneAPI 搜索或归一化 Chrome 结果，并补正文与一级评论。
- `Chrome搜索选题取数协议.md`：Chrome 数据源下搜索页、详情和评论原始响应的读取规则。
- 所有暂存文件只写入 `.meiling/staging/topic-search/<run_id>/`；正式结果只写入 `我方资料/搜索选题/<run_id>/`。
- 协调器或数据执行器返回 `ok=false`、命令失败、合同不完整时，说明真实原因并停止，不手工改产物绕过。

## 2. 具体流程说明

### 2.1 冻结账号方向与取数方式

#### 输入

- 账号方向默认读取 `我方资料/我方当前概要.md`；用户明确指定其他正式方向文件时使用用户指定路径。
- 平台支持 `小红书`、`抖音`、`B站` 三个渠道。默认全部渠道；用户在「搜索选题」弹窗里勾了几个，就只搜这几个，指令里会写明本轮渠道。用户口头指定渠道时按用户指定，两者不一致时以本轮指令和用户当次说法为准。
- 用户只勾了一个渠道时，整轮只搜那一个渠道，不要顺手把其他渠道补上；搜索计划里每个 query 的 `platforms` 只能是本轮渠道的子集。
- 数据源只接受 `chrome_devtools` 或 `justoneapi`。当前对话没有明确选择时，先按 `执行单元/公开数据获取环境检查与数据源选择.md` 检查真实环境，再让用户明确选择；不得默认推荐或静默切换。B站只有 Chrome 取数，`justoneapi` 不支持，遇到 `platform_not_supported_by_justoneapi` 时按该渠道未取到处理并在结果里说明。
- 用户额外提供的关键词或竞品表达可以作为补充输入，不替代账号方向。

#### 调用

```bash
python3 "<当前工作区根>/执行单元/搜索选题流程协调器.py" \
  --workspace-root "<当前工作区根>" \
  --action prepare \
  --overview-path "<账号方向文件>" \
  --platforms "<本轮渠道，逗号分隔：小红书,抖音,B站>" \
  --data-source "<用户确认的数据源>"
```

只接受 `ok=true、status=prepared`。协调器会冻结账号方向快照，返回 `run_id`、`context_file` 和 `搜索计划候选.json` 的精确路径。后续必须复用同一上下文。

### 2.2 生成并冻结搜索计划

读取 `分析框架/搜索选题方法论.md` 和冻结的账号方向，生成 3—6 个关键词。关键词围绕目标人群、具体问题、使用场景、任务或结果，不把同一个词换种写法重复占用名额；每个本轮平台至少被一个关键词覆盖。

将候选写入 `2.1` 指定的 `搜索计划候选.json`：

```json
{
  "schema_version": "1",
  "queries": [
    {
      "query_id": "Q001",
      "keyword": "具体搜索词",
      "platforms": ["小红书", "抖音"],
      "rationale": "为什么该词符合账号方向"
    }
  ]
}
```

随后冻结：

```bash
python3 "<当前工作区根>/执行单元/搜索选题流程协调器.py" \
  --workspace-root "<当前工作区根>" \
  --action freeze-queries \
  --context-file "<context_file>" \
  --query-plan "<搜索计划候选.json>"
```

只接受 `status=queries_frozen`。之后不得改词、加词或更换平台；确需改变时重新开启一轮。

### 2.3 完成一轮平台搜索

#### JustOneAPI

```bash
python3 "<当前工作区根>/执行单元/搜索选题数据执行器.py" \
  --workspace-root "<当前工作区根>" \
  --action search \
  --plan-file "<搜索计划.json>"
```

每个关键词、每个平台只取第 1 页。单查询失败时保留真实错误和其他已经成功结果；全部无法归一化时停止。不得为了凑结果自动改词或追加付费页。

#### Chrome

打开每个平台的搜索页后先判断真实登录态；不要默认用户已经登录，也不要把登录墙当成“没有搜索结果”：

- **已登录**：直接读取，不再询问用户。
- **未登录或跳转登录页**：保持搜索页开在他自己的 Chrome 里，用一句话告诉用户“请在你平时用的那个 Chrome 里登录这个平台，登录成功后会自动继续”，然后每 5 秒重新判断一次登录态。
- 最多等 60 轮（约 5 分钟）。登录成功后自动继续，不要求用户回复“登录好了”。
- 等待期间出现扫码、滑块、短信验证等需要用户操作的环节，继续等，不自动处理、不换路径。
- 超过上限仍未登录：停止本轮，说明“等了约 5 分钟仍未检测到登录”，不得改用其他来源假装已经完成该平台搜索。

先按 `执行单元/Chrome搜索选题取数协议.md` 完成搜索页读取。三个渠道的取数方式不一样，不要套用同一个：

- **小红书**：读结果页卡片，整理成统一合同 `{"contents":[...]}`，写进本轮 `Chrome搜索原始结果.json`，走下面的 normalize。
- **抖音**：不要直接开 `/search/<关键词>`（会被拦成 502）。先开 `https://www.douyin.com/jingxuan`，在搜索框输入关键词回车，进入 `/jingxuan/search/...` 后等卡片渲染；再用 `get_network_request` 把 `/aweme/v1/web/general/search/single/` 的响应原文写到本轮 `raw/抖音-<query_id>.json`，交给执行器解析。
- **B站**：打开 `https://search.bilibili.com/all?keyword=<关键词>`，同样把页面自身搜索接口的响应原文写到 `raw/B站-<query_id>.json`，交给执行器解析。

抖音、B站走平台响应直解，不用手工抄字段：

```bash
python3 "<当前工作区根>/执行单元/搜索选题数据执行器.py" \
  --workspace-root "<当前工作区根>" \
  --action normalize \
  --plan-file "<搜索计划.json>" \
  --raw-input "<raw/抖音-Q001.json>" \
  --query-id "Q001" \
  --platform "抖音"
```

`--platform` 可填 `抖音` 或 `B站`；小红书仍用 `--raw-input <Chrome搜索原始结果.json>`，不传 `--query-id / --platform`。多次 normalize 会按 `平台:原生ID` 合并去重。

两步成功产物都是本轮 `搜索结果.json` 和 `选题证据.json`。搜索结果不足时不得用旧选题或旧内容补齐。某个渠道整组取不到时，保留其他渠道的结果继续往下走，并在最终反馈里写清是哪个渠道、什么原因没取到（例如未登录、平台拦截、评论接口不可用），不得把它说成「这个平台没有相关内容」。

### 2.4 AI 相关性筛选

搜索结果只是平台召回，不代表适合当前账号。执行器返回的 `relevance_hint` 只是关键词命中提示，**不能替 AI 做相关性判断**。

读取本轮 `搜索结果.json`、冻结的账号方向快照和 `分析框架/搜索选题方法论.md`，对每条内容逐条判断：

- `relevant`：直接服务当前账号的人群、问题域、内容主线或阶段目标；
- `weak`：主题沾边，但需要正文或评论进一步确认；
- `irrelevant`：品类、受众或任务明显跑偏，例如只有 ComfyUI、AI 生图、短剧、带货、直播等，且不服务当前账号。

将判断写入本轮 `相关性筛选结果候选.json`：

```json
{
  "schema_version": "1",
  "workflow_id": "topic-search",
  "run_id": "<本轮 run_id>",
  "decisions": [
    {
      "content_id": "<真实内容ID>",
      "decision": "relevant | weak | irrelevant",
      "reason": "为什么适合或不适合当前账号",
      "use_for_enrich": true
    }
  ]
}
```

- 必须覆盖 `搜索结果.json` 中的每一条内容，不能漏项或编造 ID；
- `irrelevant` 不得 `use_for_enrich=true`；
- 至少选 1 条 `use_for_enrich=true` 进入下一步。

AI 是相关性判断的唯一决策者；协调器只校验结构、覆盖和出口，不替 AI 判断相关性。

```bash
python3 "<当前工作区根>/执行单元/搜索选题流程协调器.py" \
  --workspace-root "<当前工作区根>" \
  --action filter-relevance \
  --context-file "<context_file>" \
  --filter-json "<相关性筛选结果候选.json>"
```

只接受 `status=relevance_filtered`。回执中的 `enrich_content_ids` 是下一步唯一允许补正文和评论的范围，不得另行挑选。

### 2.5 补正文和评论

将 `2.4` 回执的 `enrich_content_ids` 逗号分隔传入：

```bash
python3 "<当前工作区根>/执行单元/搜索选题数据执行器.py" \
  --workspace-root "<当前工作区根>" \
  --action enrich \
  --plan-file "<搜索计划.json>" \
  --content-ids "<enrich_content_ids>"
```

- JustOneAPI：执行器只对正文缺失项补详情，并按现有接口取一页一级评论；评论数为 0、未取到和失败分别记录。
- Chrome：先按 `Chrome搜索选题取数协议.md` 为选中内容保存 `评论原始/<原生ID>.json`，再执行同一命令；缺少原始响应时如实标记未采集，不伪造评论。
- 执行器只做机械初筛：只索取“蓝皮书、提示词、资料、模板、链接”等资料、纯表情、纯赞美、互赞互关和重复刷屏会被剔除；提出具体问题的评论先保留，并记录 `原始评论条数 / 评论条数 / 低信息评论条数`。
- 评论补取失败不删除已经获得的标题、正文和互动数据，后续只能按实际证据等级使用。

### 2.6 AI 评论筛选

执行器的机械初筛只能识别固定模式，不能判断语义。读取 `选题证据.json` 中已经保留的评论，逐条做第二轮判断：

- 保留：具体问题、真实经历、明确反对或质疑、具体使用场景、对内容有用的补充；
- 剔除：泛泛自述、只表达情绪、重复刷屏、与内容无关的闲聊，以及没有被执行器规则命中但依然没有信息量的互动。

将结果写入本轮 `评论筛选结果候选.json`：

```json
{
  "schema_version": "1",
  "workflow_id": "topic-search",
  "run_id": "<本轮 run_id>",
  "contents": [
    {
      "content_id": "<真实内容ID>",
      "kept_comment_ids": ["<保留的评论ID>"],
      "dropped_comment_ids": ["<剔除的评论ID>"],
      "reason": "本轮保留和剔除的判断依据"
    }
  ]
}
```

- 必须覆盖 `选题证据.json` 中所有带评论的内容；
- `kept_comment_ids` 与 `dropped_comment_ids` 不能重叠，并集必须等于该内容当前全部评论 ID；
- 可以使用空数组，但不能编造评论 ID。

```bash
python3 "<当前工作区根>/执行单元/搜索选题流程协调器.py" \
  --workspace-root "<当前工作区根>" \
  --action filter-comments \
  --context-file "<context_file>" \
  --filter-json "<评论筛选结果候选.json>"
```

只接受 `status=comments_filtered`。后续选题只能引用 `kept_comment_ids` 中的评论。

### 2.7 一次生成 9 条推荐

读取：

- `分析框架/搜索选题方法论.md`；
- `提示词/搜索选题成稿提示词.md`；
- 本轮 `搜索计划.json`、`选题证据.json`、`相关性筛选结果.json`、`评论筛选结果.json`；
- 冻结的账号方向快照。

一次生成恰好 9 条，写入本轮 `选题推荐候选.json`。每条必须包含：

- 排名、选题标题、推荐角度、目标用户、用户问题、账号匹配理由；
- 证据类型： `评论证据 / 正文证据 / 标题与互动`；
- 1—3 个本轮真实 `reference_content_ids`，且只能来自 `2.4` 中未被判为 `irrelevant` 的内容；
- 实际使用的 `evidence_comment_ids`，只能来自 `2.6` 的 `kept_comment_ids`；没有则为空数组；
- 五项评分，各为 1—5 的整数：`score_account_fit`、`score_demand`、`score_reference`、`score_differentiation`、`score_production`。

评分口径按 `提示词/搜索选题成稿提示词.md` 的评分表执行。总分由协调器按固定权重（30 / 25 / 20 / 15 / 10）计算，候选里不写总分，也不输出“推荐、备选”等标签。

先按问题聚类再形成选题，不强制一条内容对应一个题，不复制来源标题凑数。无法形成 9 条不同且符合账号方向的推荐时，说明真实原因并停止；不得减少数量或编造第 9 条。

### 2.8 校验、保存与反馈

```bash
python3 "<当前工作区根>/执行单元/搜索选题流程协调器.py" \
  --workspace-root "<当前工作区根>" \
  --action save \
  --context-file "<context_file>" \
  --candidate "<本轮选题推荐候选.json>"
```

协调器依次校验：

- 恰好 9 条、排名为 1—9、标题不重复；
- 每条有 1—3 条本轮来源内容；
- 来源内容必须通过 `2.4` 的 AI 相关性筛选，不能引用 `irrelevant` 内容；
- 评论 ID 必须真实存在于本题来源内容，且必须通过 `2.6` 的 AI 评论筛选；
- 五项评分齐全且均为 1—5 的整数；
- 缺少 `相关性筛选结果.json` 或 `评论筛选结果.json` 时拒绝保存；
- 正文证据必须有真实正文；标题与互动不得冒用评论。

协调器按固定权重计算每条总分，并按总分从高到低重排为 1—9（同分保持候选顺序），不做主题去重。输出去掉“推荐、备选”标记，由前端自行按总分处理。

校验失败时根据真实错误修正同一候选后重跑本步骤，不手工修改正式文件。只有返回 `status=completed、commit_status=committed、topic_count=9` 才算完成。

正式结果：

- `我方资料/搜索选题/<run_id>/搜索选题结果.json`
- `我方资料/搜索选题/<run_id>/搜索选题结果.md`

推荐结果不直接写入 `我方资料/选题库.csv`，也不自动进入内容生产。用户选中某一条后，再把该题交给 `topic-evaluate` 做正式选题分析。

反馈时直接展示 `ranked_topics` 中的 9 条标题、综合总分及对应来源数量，并给出上述两个正式路径；不声称这些题已经验证必爆或已经完成正式选题分析。
