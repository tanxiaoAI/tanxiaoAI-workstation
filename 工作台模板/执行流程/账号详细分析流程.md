# 账号详细分析流程

**本流程开始前先执行一次使用统计上报**（静默脚本，失败不影响任何流程，也不必向用户提及）：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 账号详细分析流程 --phase start
```

## 1. 总流程说明

1. 前置步骤
   - 进入 `2.1 判断分析起点`，确定本轮唯一分析对象和详细数据交接。
   - 进入 `2.2 检查资料与异常分流`，确认资料、交接和证据边界；不满足条件时反馈真实原因并结束本轮。
2. 准备证据与生成候选稿
   - 进入 `2.3 准备并校验内容证据`，生成并验证本轮稳定证据分块。
   - 进入 `2.4 生成详细分析候选稿`：先读取并固定本轮方法论约束，再生成单份候选稿（页面数据区 + 综合结论 + 账号表现 + 六个模块）。
3. 正式提交
   - 进入 `2.5 校验并保存正式结果`，仅在单份候选稿通过全部校验后一次性提交正式报告。
   - 证据或正式写入报 `source_hash_mismatch` 时，按 `2.4` 的「`source_hash_mismatch` 的归因与处置」处理：属外部会话改动且本轮尚无正式写入时，等待共享文件稳定后自动重试；其余情况停止并如实报告。
   - 只有返回 `status = committed`、`formal_path` 和 `formal_sha256` 才算正式提交成功。
   - 进入 `2.6 生成账号内容规律分析`：按本账号切片现算打法画像与标签效果，产出 `<账号目录>/账号内容规律分析.md`。这是主链路必跑的收尾步骤；**因内容不足或执行失败而未生成时，不改变已提交的详细分析，也不算整轮失败，但必须在最终结果中写明原因**。
   - 进入 `2.6.1 生成行动建议`：两份主分析都有效且我方规划存在时，结合规划生成 `<账号目录>/行动建议.md`。这也是主链路自动步骤；不满足前置条件或执行失败时，最终结果必须写明是缺规划、缺内容规律分析还是生成失败。
4. 返回结果
   - 进入 `2.7 反馈结果`，反馈正式报告路径、证据边界和信息不足项。
   - 当前流程不自动进入后续流程；用户需要结合对标结论调整自身规划时，由公开入口另行进入 `自媒体规划分析流程.md` 的对标启发入口。

## 2. 具体流程说明

### 2.1 判断分析起点

本步骤只确定本轮分析对象和本地详细数据交接，不检查内容证据是否充足，也不执行数据补齐。

固定读取 `对标资料/对标账号库.csv`，按以下规则确定唯一账号：

1. 从详细数据流程进入时，校验本轮交接中的 `账号ID`、平台、已选内容 ID 清单和详细数据报告路径与账号库一致后沿用该账号；保留该本地交接文件路径。
2. 本流程只接受固定顺序中的本轮详细数据结果；不接受讨论阶段的意图升级或没有明确账号及详细数据报告的独立跳入。
3. 账号已有可读详细分析时，本次一键分析即表示生成最新结果：直接重新生成并刷新工作台当前使用的报告，不再询问是否覆盖；不额外做历史版本管理。
4. 用户要结合已有结论判断如何调整自身规划时，结束本流程；由公开入口另行执行 `自媒体规划分析流程.md` 的对标启发入口。

本步骤成功后固定保留：`账号ID`、账号名、平台、简介、粉丝数、获赞数、标签、主页链接、内容列表路径、图片说明路径和人工先验说明路径。

同时保留本轮的两个路径占位符，本流程后续所有命令只能使用这两个值：

- `<run_id>`：取自本轮 canonical report 的 `run_id` 字段，与交接路径里的暂存目录名逐字一致。
- `<当前流程>`：交接路径 `.meiling/staging/<当前流程>/<run_id>/...` 中 `<run_id>` 的上一级目录名（对标账号链路固定为 `benchmark-account-diagnose`）。

两者都不得自行生成、改名或简化；记录缺失时停止并说明交接缺口，不得用近似值代替。

### 2.2 检查资料与异常分流

本步骤只判断是否具备开始详细分析的资料条件，并决定是否停止本轮。

先检查内容列表路径、内容列表可读性和至少一条有效内容 ID。缺失、不可读或为空时：

1. 说明基础资料缺失并停止；
2. 修复后从 `base_data -> detail_data -> detail_analysis` 的固定顺序重新进入，不在本流程内跳转。

内容列表可用时，读取本轮详细数据流程交付的唯一 `canonical-detail-report.json`。只读取其 `status`：

- `stage = detail_data` 且 `status = completed` 或 `partial`；
- `failed` 直接停止，其他状态不接受；
- 交接账号、平台和范围由本轮交接文件与 canonical report 校验；
- 当前运行已经按详细数据完成结果自动进入本步骤。

交接缺失、状态无效、账号或平台不一致时，说明详细数据交付缺口并停止；修复后必须重新经过详细数据流程，不得从旧暂存文件恢复。

交接其余条件已满足时直接继续本流程；详细数据阶段已经按设置默认范围锁定清单。本流程不再询问用户或修改阶段顺序。

交接满足时，按以下规则处理证据边界：

- 图文标题或发布时间缺失时继续分析，并在输入中通过 `missing_deliverables` 内的 `标题`／`发布时间` 标签标明缺口，写入 2.4 各模块的依据与边界；ASR 缺失不阻断账号级分析。
- 图片说明、人工先验说明或头像文件缺失时可以继续；涉及图片的结论必须写明 `信息不足`，头像原链接和头像路径不得传入分析提示词也不得阻断分析。`图片说明路径` 为空表示本轮没有登记图片材料，按图片说明缺失处理，不得改用封面图或头像充当图片说明。
- 脚本或交接校验失败时停止，不生成候选稿或正式报告。

### 2.3 准备并校验内容证据

先调用根目录执行单元生成稳定的证据分块：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号分析证据分块执行器.py" \
  --phase build \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --account-type benchmark \
  --account-id "<账号ID>" \
  --platform "<平台>" \
  --mode detail \
  --selected-content-ids "<本轮 canonical report 的 requested_content_ids，逗号分隔>" \
  --output-dir ".meiling/staging/<当前流程>/<run_id>/账号详细分析证据"
```

执行单元在模型上下文外读取内容列表、内容库、作品正文和已有特征实例，生成稳定分块清单。对标侧和我方都读取 `视频文案路径` 的原文。主对话不得先加载全部原始证据。

正文缺失才是本步骤的资料缺口。

执行器按剥字段后的证据总量自动分流，build 回执有两种形态，必须按 `detail_delivery_mode` 区分：

- **`direct`（直读）**：证据量在阈值以内，不分块，直接产出合并可读证据；回执 `chunk_count = 0` 并带 `direct_evidence_path`。此时**不生成任何分块摘要、也不读取摘要提示词**，直接进入下面的 `--phase verify`。
- **`chunked`（分块）**：证据量超阈值，回执带分块清单与 `chunk_count`，才需要按下一段逐块生成摘要。

阈值由执行器的 `--direct-read-max-chars` 控制（默认 `60000` 字符），不要在流程里自行换算或改写这条判定。

输出目录已存在且非空时（上一轮中断后重跑、或补采到新证据要重出分块），执行器默认报 `output_dir_not_empty`。确认旧分块可以作废重出时，在原命令上追加 `--reset-output-dir`：它会把旧目录整体改名归档（不删除数据）再重建。不得手工删除或搬动旧分块。

对标账号的详细证据范围以本轮 `canonical-detail-report.json` 的 `requested_content_ids` 为准；该清单已由详细数据阶段按 `BENCHMARK_ACCOUNT_DETAIL_LIMIT`（默认 `20` 条）或用户本次明确要求锁定。本步骤不得自行扩大或缩小范围，清单必须记录账号内容总数、本次选择数、正文级证据数和仅基础数据数。

**仅当回执为分块形态时**：读取本地 `提示词/账号分析-分块证据摘要提示词.md`，按清单逐个整理证据并写入清单指定的 `summary_path`。整理必须保留条件、反例、数字和可回查位置，不能只留支持结论的部分。全部完成后调用：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号分析证据分块执行器.py" \
  --phase verify \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --output-dir ".meiling/staging/<当前流程>/<run_id>/账号详细分析证据"
```

只有返回 `status = verified` 才进入下一步。`2.4` 读取的已验证证据路径以本步骤回执的 `verified_evidence_path` 为准，不得用分块文件、候选摘要或旧运行产物替代。失败时停止并说明失败位置，现有正式报告保持不变。

#### 2.3.1 准备账号表现程序统计

证据校验通过后，生成同一轮的程序统计，供「账号表现」和数据表现使用：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号表现统计执行器.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --account-id "<账号ID>" \
  --platform "<平台>" \
  --output-file ".meiling/staging/<当前流程>/<run_id>/账号表现统计.json"
```

只接受 `ok = true`、`status = ready`。返回的 `作品总数`、`互动`、`账号内分档`、`发布`、`限制说明` 是本轮唯一数字真源；后续提示词、正式报告和页面都不得重算。

### 2.4 生成详细分析候选稿

#### 输入

1. `分析框架/账号分析方法论.md`：分析规则、字段口径和推导边界，不是账号事实证据；本轮读取一次并固定。
2. `2.2` 保留的账号基础字段、可读图片和人工先验说明。
3. `2.3` 已验证的证据路径及其统计信息，路径以 `2.3` 回执的 `verified_evidence_path` 为准。
4. `2.3.1` 的 `账号表现统计.json`，作为账号表现和统计依据的唯一数字来源。
5. `提示词/账号详细分析提示词.md`。

#### 固定本轮证据范围

生成任何候选稿之前，必须先通过正式化执行器的 `prepare` 接口取得本轮唯一的 `evidence_scope`：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号详细分析正式化执行器.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --phase prepare \
  --account-id "<账号ID>" \
  --platform "<平台>" \
  --evidence-dir ".meiling/staging/<当前流程>/<run_id>/账号详细分析证据" \
  --handoff-json ".meiling/staging/<当前流程>/<run_id>/detail-data/canonical-detail-report.json"
```

- 返回的 `evidence_scope` 是 `资料范围与来源` 里证据范围说明的唯一合法取值，必须逐字复制，不得改写、补算、拆分或自行拼接。
- 该调用必须在 `2.3` 证据校验通过之后、本轮任何正式写入之前执行。正式写入会更新账号库；账号库内容因此发生变化后，再调用 `prepare` 会返回 `source_hash_mismatch`（重复提交写入相同值时账号库字节不变，不受此限）。出现该错误时按下一节处置，不得跳过校验继续生成候选稿。
- `prepare` 返回 `ok = false` 或缺少 `evidence_scope` 时，不得进入候选稿生成。

#### `source_hash_mismatch` 的归因与处置

通用判据、等待方法与重试上限见 `执行单元/并发冲突处置.md`；本节只写本流程的落点。

`prepare` 返回 `source_hash_mismatch` 时，先归因再动作。判据只有一条：**本轮是否已经执行过正式写入**。

- **本轮已有正式写入**：判为本轮自身的顺序错误。停止并如实报告，不得用重建证据或重跑取数掩盖顺序错误；确实需要重试时，按 `2.5` 的重试规则由用户重新发起。
- **本轮尚无任何正式写入**：证据清单记录的 `source_sha256` 与当前文件不一致只可能来自其他会话，判为**外部会话改动**。此时等待共享文件稳定后自动重试，最多两轮；两轮后仍失败时停止并如实报告。

判为外部会话改动时，每轮按以下顺序执行：

1. **等待共享文件稳定**：对 `对标资料/对标账号库.csv` 和 `对标资料/对标内容库.csv` 采样 sha256，间隔 `30` 秒重新采样，连续两次一致视为稳定；单轮最多等 `10` 分钟，超时按本轮失败处理。
2. **重出证据分块**：按 `2.3` 重跑 `build` 并追加 `--reset-output-dir`；旧目录由执行器自行改名归档，不得手工删除或搬动。
3. **核对并复用摘要**：新清单中每块的 `input_sha256` 与旧清单逐块一致时，已写好的分块摘要仍然有效，可复制到新清单的 `summary_path`；存在不一致的块必须按 `2.3` 重新生成并重新 `verify`。不得整目录照搬。
4. **继续原路径**：重新执行本节的 `prepare` 取证据范围，再生成单份候选稿，最后一次性 `commit`。

等待期间不得改动证据清单里的哈希，也不得跳过 `prepare` 继续生成候选稿。等待与重试全部在本地完成，不重跑取数、不重复计费。重试结束后必须在 `2.6` 说明本轮发生过并发冲突。

`2.5` 的 `commit` 返回同类错误时使用同一套归因判据：本轮尚无正式写入时按本节等待重试，本轮已有正式写入时按 `2.5` 的重试规则由用户重新发起。

#### 生成

加载 `提示词/账号详细分析提示词.md`，一次生成单份候选稿。输入只包括：账号基础字段、可读图片、人工先验说明、已验证证据、账号表现统计和方法论约束。

图片目录存在可读图片时，由当前 AI 实时查看；账号库中的 `头像原链接` 和 `头像路径` 不得传入分析提示词，也不得作为判断证据。未实际读图时，按提示词要求写 `信息不足` 和 `视觉未参与结论`。

候选稿固定写入：

```text
.meiling/staging/<当前流程>/<run_id>/账号详细分析候选.md
```

候选稿必须包含：

1. 标题 `# <账号名>账号详细分析`；
2. 唯一的页面数据区（`account-insight-summary` 标记 + 一个 `json` 代码块）；
3. `## 综合结论`、`## 账号表现`；
4. 六个模块：用户画像、产品服务体系、价值主张、人设风格、差异化、成立逻辑，每个模块三个三级标题；
5. `## 资料范围与来源`，逐字包含本轮 `evidence_scope`。

不得把最近 `20` 条样本描述为账号全部内容；内容列表完整性由正式化器派生并写入 `资料范围与来源`，候选稿不得改写该结论。判据与概要分析共用同一套规则，单点实现在 `执行单元/内容列表完整性判据.py`：正式化器只读基础报告 `本轮账号基础建档结果.json` 的 `content_list_status` 和采集停止原因（`source_results[].停止或失败原因`，兼容顶层 `内容列表停止原因`）；**不读 `data_limitations`**——那是资料缺口总表，含截图失败等与内容列表无关的条目。

生成失败时立即停止，不创建或覆盖正式 `详细分析.md`。

### 2.5 校验并保存正式结果

只有单份候选稿成功后，才将本轮本地文件交给 `账号详细分析正式化执行器.py` 一次性校验和写入。正式化器必须以本地 `commit` 接口接收以下参数。使用下面的完整命令执行，不得只传参数片段：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号详细分析正式化执行器.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --phase commit \
  --account-id "<账号ID>" \
  --platform "<平台>" \
  --evidence-dir ".meiling/staging/<当前流程>/<run_id>/账号详细分析证据" \
  --handoff-json ".meiling/staging/<当前流程>/<run_id>/detail-data/canonical-detail-report.json" \
  --candidate ".meiling/staging/<当前流程>/<run_id>/账号详细分析候选.md" \
  --stats-file ".meiling/staging/<当前流程>/<run_id>/账号表现统计.json"
```

正式化器命令行支持 `prepare` 和 `commit`：`prepare` 已在 2.4 用于固定本轮证据范围，正式写入只调用 `commit` 接口，并使用同一组输入和 `--phase commit`；不得让模型直接写入正式文件。

正式文件固定写成 `<账号目录>/详细分析.md`，重跑直接覆盖；账号库的 `详细分析路径` 同时更新为这份文件。不再生成 `详细分析-新.md` 之类的副本。

该动作负责重新确认账号和内容证据、校验标题与九个二级标题的顺序、校验页面 JSON 与六模块子结构、校验证据 ID 和重点短语、组装完整 `详细分析.md`、回写账号库中的详细分析路径并计算正式报告 SHA256。不得先单独写正式报告或账号库，再调用正式化执行器；模型不得手工拼接 CSV 或调用第二个提交命令。

只有返回 `status = committed`、`formal_path` 和 `formal_sha256`，才算完成。任一步校验失败时不得写正式报告；正式写入失败时保留原有正式报告。候选稿或 canonical 输入在本轮写入前发生变化时必须停止并报告冲突。

需要重试时由用户重新发起，不使用旧运行自动恢复；按变化范围分两种，不得混用：

- **只有候选稿有问题**（写坏、字段不合规），账号库、内容列表及其他证据源都未变化：改好候选稿后重跑本步骤的 `commit`。`2.4` 的 `prepare` 结果和证据清单仍然有效，不需要重出。
- **账号库、内容列表或取证数据的文件内容已变化**：本轮证据清单记录的 `source_sha256` 已经过期，继续拿原 `--evidence-dir` 调用 `prepare` 只会再次返回 `source_hash_mismatch`。先按 `2.4` 的「`source_hash_mismatch` 的归因与处置」判断成因：本轮尚无正式写入时，按该节等待共享文件稳定后自动重试；本轮已有正式写入时，说明是本轮顺序错误，停止并如实报告，由用户重新发起后再回到 `2.3` 重走证据环节（用 `--reset-output-dir` 重出证据分块，旧目录整体改名归档，按新清单重新生成全部摘要并通过 `verify`，再进入 `2.4` 和 `2.5`）。不得改动清单里的哈希，也不得原地覆盖来绕过校验。

`<账号目录>/过程记录/当前阶段状态.json` 由本步骤的 `commit` 动作写入：阶段名 `账号详细分析`、`当前是否完成` 为 `true`、`updated_at` 为提交时间；`2.4` 的 `prepare` 不写该文件，`2.7` 只读取不写入。本流程其他步骤不得自行改写它，也不得把它当作正式报告的依据。

### 2.6 生成账号内容规律分析

本步骤是主链路自动执行的收尾步骤，在 2.5 的正式 `详细分析.md` 提交成功后直接执行，不再询问用户是否生成。**因内容太少而跳过或执行失败，都不改变已正式提交的详细分析，也不算整轮失败**，但必须在最终结果中写明真实原因。

机器数据读的是 `沉淀结论/内容特征实例.csv` 按本账号切出来的行、本账号 `内容列表.csv` 的互动数，以及 `沉淀结论/内容特征词典.csv`。本报告不读作品正文，也不写内容方向或代表作品。本步骤**不写任何共享资产**。

#### 第一步：准备机器数据

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容规律分析准备执行器.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --source "对标内容" \
  --account-id "<账号ID>" \
  --platform "<平台>" \
  --output-file ".meiling/staging/<当前流程>/<run_id>/账号内容规律分析准备结果.json"
```

- 返回 `status = skipped_no_instances`：该账号完成特征识别的内容数为 0，**跳过本步骤**（不是失败）。直接进入 2.7，反馈里如实写「本账号内容太少，未生成账号内容规律分析」。
- 返回 `status = ready`：取其中的 `analysis_scope_label`、`active_sample_count`、`rule_count`、`rules`、`markdown`、`rank_comparison`，继续第二步。

#### 第二步：生成候选稿

调用 `提示词/账号内容规律分析提示词.md`，只输入准备结果，一次生成完整的 `账号内容规律分析候选.md`，写入本轮暂存目录（`.meiling/staging/<当前流程>/<run_id>/账号内容规律分析候选.md`）。

报告固定 3 节，顺序为：`1. 分析范围`、`2. 内容打法`、`3. 表现比较`。第 1 节四项与第 3 节的四组表格必须逐字取自准备结果；第 2 节的打法由准备结果的 `rules` 整理。整篇不得出现「新特征」「候选」「入库」，也不写学习启发、内容方向、代表作品和正文补充。

#### 第三步：校验并保存正式结果

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容规律分析正式保存.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --source "对标内容" \
  --account-id "<账号ID>" \
  --platform "<平台>" \
  --candidate-file ".meiling/staging/<当前流程>/<run_id>/账号内容规律分析候选.md" \
  --preparation-result-file ".meiling/staging/<当前流程>/<run_id>/账号内容规律分析准备结果.json"
```

正式路径是 `<账号目录>/账号内容规律分析.md`，重跑直接覆盖，并把路径写回对标账号库的 `内容规律分析路径`。不再生成 `账号内容规律分析-新.md` 副本。只有返回 `status = committed`、`formal_path` 和 `formal_sha256` 才算写完。

保存校验三条，任一不符即拒绝写入、正式文件保持原有内容：

1. 报告标题必须是 `# 账号内容规律分析`，全篇只出现一次；
2. 3 个节名与顺序必须逐字一致；
3. 第 1 节的生成时间、纳入内容数、规律数量，以及第 3 节表格的共性占比、三档条数与比例、判定词，都必须与准备结果完全一致。

本步骤**不改** `<账号目录>/过程记录/当前阶段状态.json`。

### 2.6.1 生成行动建议

本步骤属于主链路自动步骤，在下面三条同时满足时直接执行，不再询问用户：

1. `2.5` 的正式 `详细分析.md` 已提交；
2. `2.6` 已产出新版三节 `账号内容规律分析.md`（含「2. 内容打法」「3. 表现比较」）；
3. `我方资料/我方自媒体规划.md` 可读。

任一条件不满足时跳过本步骤，不生成半成品，也不把原因写成对方账号的结论。跳过或失败都不改变已提交的详细分析和内容规律分析，不算整轮失败。

输入：

- `<账号目录>/详细分析.md`
- `<账号目录>/账号内容规律分析.md`
- `我方资料/我方自媒体规划.md`（重点读自身条件、用户与需求、产品供给边界、内容主线和待验证事项）
- 账号库中当前账号 `内容列表路径` 指向的真实作品清单（至少含内容ID、标题，以及已获取的点赞、收藏、评论等表现数据）
- 本轮用户反馈和当前重点（如有）

生成规则：

- 先从这个账号已采集的真实作品里选一条参考作品，再围绕它写一张行动卡片；不得凭记忆补作品，也不得引用其他账号的作品。
- 一张卡片只对应一条参考作品、一个核心做法；需要两部作品分别支撑两个做法时缩小卡片动作，没有合适作品时少生成卡片，不凑数。
- 每张卡片只写行动标题、参考作品、具体怎么做、发布后看什么四项；不写验证类型，不写建议来源。

加载 `提示词/行动建议提示词.md`，一次生成 `行动建议候选.md`，写入：

```text
.meiling/staging/<当前流程>/<run_id>/行动建议候选.md
```

保存：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/行动建议正式保存.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --account-id "<账号ID>" \
  --platform "<平台>" \
  --candidate-file ".meiling/staging/<当前流程>/<run_id>/行动建议候选.md"
```

只有返回 `status = committed`、`formal_path` 和 `formal_sha256` 才算写完。正式路径为 `<账号目录>/行动建议.md`，重跑直接覆盖。失败时保留已有文件，不覆盖旧建议。

我方规划变化、当前重点变化时可以单独重跑本步骤，不必重新生成两份主分析；重新生成的两份主分析如果结构或结论变化，应同步重跑本步骤。

### 2.7 反馈结果

本步骤只消费 2.5 已正式提交的 `formal_path`、`formal_sha256`、`evidence_scope`、账号库当前记录和本轮已验证的资料缺口；不得读取候选稿、临时证据或自行拼接正式路径。占位符只能替换为正式提交结果、账号库和已验证资料中的真实值，不得猜测或补写。

使用以下固定顺序向用户反馈：

```text
## 账号详细分析结果

- 当前账号档案：<dashboard_base_url>/account?kind=benchmark&id=<账号ID>

- 账号内容规律分析：<2.6 返回的 formal_path；2.6 跳过或失败时写“本次未生成（该账号完成特征识别的内容不足 1 条）”或失败原因>
- 行动建议：<2.6.1 返回的 formal_path；跳过或失败时写“本次未生成”并说明是缺规划、缺内容规律分析还是生成失败>

````

工作台链接固定定位到对标账号列表和当前账号档案。`<dashboard_base_url>` 只能替换为工作台启动后返回的本地基础地址，取址方式固定按 `执行单元/工作台地址获取.md` 执行；工作台未打开或未返回地址时，两个链接均写“工作台未打开”，但不阻断正式结果反馈。不得猜测端口、基础地址、账号档案链接或正式文件路径。

本轮不再依赖 `概要分析.md`。如果账号已有历史概要报告，且其中声明的数据边界与本轮详细数据不一致，以本轮详细数据为准，不在反馈中引用或改写旧概要文件。

结果反馈后，提供以下固定选项；用户也可以直接提出其他问题或后续诉求：

```text
接下来你可以：

**看看如何融入我的账号规划**
以这个账号的正式分析为参考，结合你现有规划讨论哪些做法值得借鉴、哪些依赖对方条件，以及是否值得写入你的规划。

**暂时到这里**
```

用户选择后的处理规则：

1. **看看如何融入我的账号规划**：以当前账号和正式 `详细分析.md` 作为对标启发入口，进入 `执行流程/自媒体规划分析流程.md` 的 `benchmark_inspiration` 模式。由该流程读取完整我方规划，判断哪些结论可迁移、需要改造或不应采用；在用户确认成稿前不得修改规划。
2. **暂时到这里**：结束本轮并保留正式详细分析报告，不追加阶段结果，不写入额外的流程状态。
3. 用户提出重新获取数据、修改分析范围或重新生成详细分析时，结束当前反馈分支，由用户重新进入对应公开流程；不得在本步骤直接复用旧暂存文件或绕过前置确认。
4. 用户提出其他问题、比较或后续诉求时，先在当前正式分析结果范围内直接回答；若明确要求调整自身规划，沿用当前账号和正式 `详细分析.md` 路径进入自媒体规划流程的 `benchmark_inspiration` 模式。不得因用户未按固定选项表述而忽略其明确诉求。

本地正式化执行器返回 `status = committed`、`formal_path` 和 `formal_sha256` 后，正式分析流程即完成；用户选择只决定是否另行进入后续流程，不改变本轮正式结果。
