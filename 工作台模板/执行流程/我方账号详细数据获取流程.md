# 我方账号详细数据获取流程

**本流程开始前先执行一次使用统计上报**（静默脚本，失败不影响任何流程，也不必向用户提及）：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 我方账号详细数据获取流程 --phase start
```

## 1. 总流程说明

1. 前置确认
   - 进入 `2.1 承接基础数据结果并确认账号`
   - 只消费本地正式资料和本轮批次上下文，不重新选择账号或公开需求
2. 确定本轮内容范围
   - 进入 `2.2 确定本轮内容范围`；数据源沿用基础数据阶段，本步按配置默认锁定最近 20 条
   - 只纳入 `公开状态 = 公开` 的内容；其他状态一律排除，不等待用户选择范围
3. 获取详细数据
   - 进入 `2.3 获取并补全内容明细`
   - 需要重试时进入 `2.4 处理失败内容`
   - 第二次仍有失败时停在 `2.4` 等待用户决定
4. 获取创作者中心数据（小红书 / 抖音，增强）
   - 进入 `2.5 获取创作者中心数据（小红书 / 抖音）`
   - 不可用、未登录或失败时记录真实原因，不阻断后续步骤
5. 处理可用内容
   - 进入 `2.6 计算衍生字段`
   - 进入 `2.7 执行固定后续处理`
6. 特征落表（实例 + 观察）
   - 进入 `2.8 特征落表（实例 + 观察）`
7. 获取评论原文
   - 进入 `2.9 获取评论原文`
   - 失败或跳过不阻断诊断
8. 确认完成并交接
   - 进入 `2.10 确认详细数据交接并进入诊断`
   - 正常交接时不单独向用户展示取数阶段的中间回执；完整结论、资料边界和信息不足项由诊断流程统一反馈，`failed` 时才在本流程说明失败原因

本流程负责确认并冻结本轮详情范围。基础数据阶段只交接正式账号、数据源、内容列表和建档报告，不负责提前取得详情范围；本流程必须在同一 `run_id` 内完成范围确认。

### 本地运行合同

进入或重新进入本流程时，只使用本轮公开入口已确认的账号、平台、数据源、正式 CSV、`run_id` 和本地批次上下文。字段缺失、身份不一致或正式文件不可读时，说明真实原因并停止，不从旧对话或其他任务拼装输入。

数据源沿用基础数据阶段已确认的来源，本流程内不重新检查环境、不重新选择来源，Chrome 和 JustOneAPI 不得自动切换。未经用户明确同意不得换源；同一任务只允许改源一次，并且只在 `2.4` 的失败处理中按用户选择执行。基础数据阶段没有留下可用数据源时，说明真实原因并停止。

本流程固定使用以下对象：

- `<当前工作区根目录>`：当前工作区根目录；所有执行单元均从本地 `执行单元/` 调用。
- `<本轮运行标识>`：由《我方账号基础数据获取流程》的 `账号分析本地批次初始化执行器.py` 一次性分配、经公开入口传入的唯一 `run_id`；基础数据、详细数据和诊断三个阶段原样沿用，不得从其他标识生成、拼接或改写。
- `<当前账号内容列表CSV>`：本轮基础数据阶段确认的正式账号内容列表。
- `<我方内容库CSV>`：工作区现有的正式我方内容库（`我方资料/我方内容库.csv`），由内容建档流程维护；它不是本轮基础数据阶段的产物。本流程按执行器规则读取它，并在明细提交时同步本阶段拥有的字段，不重新确认它的其他字段。

本流程不定位、不读取其他任务的状态文件；只读取本轮批次上下文、本轮正式文件和 canonical report。

执行单元负责输入校验、范围准备、固定路径推导、结果归一、正式写入、阶段状态和报告；本流程只决定调用顺序、用户确认点和结果分支，不解释或复制执行单元内部实现。只有执行单元返回正式提交成功，对应结果才成立。

命令或报告失败时保留已写入的正式字段和真实缺口并停止；用户重新发起时创建新的本地运行批次。

明确标为降级或非阻断的失败按对应步骤继续，不改写为失败。

先确认内容范围，再读取本轮 `Chrome结果.schema.json`。单条 `执行结果.json` 只是过程 checkpoint，`canonical-detail-report.json` 是唯一正式报告；禁止 `stage_run_id` 和独立 `stage-result`。

## 2. 具体流程说明

### 2.1 承接基础数据结果并确认账号

#### 读取

只读取基础数据阶段已确认的账号身份、数据源、`<当前账号内容列表CSV>`、正式建档报告和 `<本轮运行标识>`，以及 `<我方内容库CSV>`；建档报告同时提供 `2.2` 建立批次上下文所需的 `content_list_path`。

#### 恢复判断

本轮已有范围文件且已确认时直接复用原始范围语义；没有范围时按 `2.2` 重新准备并确认。

#### 说明基础建档结果

本轮范围尚未确认、`2.2` 要向用户提出范围问题时，先说明基础建档结论，再在同一条消息里提出范围问题；范围已确认直接复用时不重复说明。

基础建档结论只从 `<当前账号内容列表CSV>` 所在账号目录的 `过程记录/批处理报告/本轮账号基础建档结果.json` 读取 `formal_commit / complete / validation_status / content_list_status / data_limitations / final_content_count / screenshot_status`，只说明：

- 基础建档是否完成并通过校验
- 账号名与已入库作品总数，内容列表是否完整（`成功` 不等于 `完整`）
- 主页长截图状态
- 当前仍存在的限制或失败

报告缺失、不可解析或字段无法识别时，说明本轮没有可用的基础建档结论并继续范围确认。不得展示暂存候选、失败状态文件或兼容阶段快照。

#### 处理规则

- 前提通过：冻结账号、数据源、`<当前账号内容列表CSV>`、`<我方内容库CSV>` 和 `<本轮运行标识>`，进入 `2.2`。
- 账号和公开需求已经由公开入口确定，本流程不得重复询问或替换。用户确认点只有：可见性或本轮内容范围尚未确认时确认可见性和范围，第二次采集仍有失败时确认失败内容如何处理。

### 2.2 确定本轮内容范围

#### 建立批次上下文

`2.2` 之后的所有动作都按本轮批次上下文（`批次上下文.json`）读取账号、正式 CSV、数据源和范围；该文件只能由执行器创建，模型不写路径、不写内容。

本轮批次上下文尚不存在时（首次进入详细数据流程），用基础数据阶段已确认的身份创建一次：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --action init-batch \
  --flow-type self_account \
  --account-id "<2.1 已读取的账号ID>" \
  --content-list "<2.1 已读取的 content_list_path>" \
  --content-library "<当前工作区根目录绝对路径>/我方资料/我方内容库.csv"
```

- `--flow-type self_account` 声明本流程的批次归属；省略时执行器按正式 CSV 的归属目录自动判定。后续动作不再重复传入，执行器从已锁定的批次上下文读取归属。
- `--account-id` 和 `--content-list` 只使用 `2.1` 已读取的本轮正式账号身份和建档报告字段，不自行拼接或改写；`--content-library` 使用合同段的 `<我方内容库CSV>`。
- 本流程默认 `--visibility-scope public`：只处理公开内容；私密、仅自己可见、草稿、审核中、未通过以及其他/未知状态不进入批次、不取数、不分析。可见性在批次创建时固定，之后不得改写。
- 批次上下文已存在时不重复执行本步：该动作会重置已确认范围，使 `confirmed` 回到未确认状态。

#### 可见性范围

我方账号的可见性范围随批次固定，默认 `public`：只纳入 `公开状态 = 公开` 的内容；非公开状态一律不进入可见条数和推荐范围。本流程内不得改写已固定的可见性，执行器对不一致取值会直接报 `可见性范围与已锁定批次不一致`。

私密、仅自己可见、草稿、审核中、未通过和其他/未知状态一律不进入基础列表、不取详细数据、不分析；不得因为内容已在列表中而继续保留。

#### 范围准备

本轮范围固定为最近 `SELF_ACCOUNT_DETAIL_LIMIT` 条，默认 `20`；只计算公开内容。不需要用户选择范围。

只有用户在本轮明确要求其他范围时，才按用户指定的数量、最新若干条、全部内容或正式内容 ID 准备；不得使用未声明的上下文。

直接锁定本轮范围：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --prepare-content-scope --confirm-content-scope
```

- 不传 `--scope-mode / --scope-count / --content-ids` 时，执行器读取 `本地配置.txt` 的 `SELF_ACCOUNT_DETAIL_LIMIT`，按最新 N 条锁定。
- 只有范围准备返回 `confirmed = true`、非空的 `selected_content_ids`、`selected_count > 0` 和 `scope_json`，且返回的账号与运行标识与本轮一致，才算范围锁定。
- 后续只使用该有序、无重复清单和返回路径；AI 不得自行读取 CSV 排序、去重、补入、删除或改写内容 ID。
- 范围命令失败、返回为空、账号不一致或结构无法解析时，说明真实错误并停止。已经存在的正式数据保持执行单元实际状态，本流程不手工补写范围文件。

#### 处理结果

只有范围准备返回 `confirmed = true`、非空的 `selected_content_ids`、`selected_count > 0` 和 `scope_json`，且返回的任务号、运行标识和账号与本轮一致，才算范围锁定。后续只使用该有序、无重复清单和返回路径；AI 不得自行读取 CSV 排序、去重、补入、删除或改写内容 ID。

范围命令失败、返回为空、账号不一致或结构无法解析时，说明真实错误并停止。已经存在的正式数据保持执行单元实际状态，本流程不手工补写范围文件。

### 2.3 获取并补全内容明细

本步骤按已锁定范围补全公开明细字段，再由执行器统一验收和回写。明细字段（互动数、发布时间、视频地址）会随时间变化 —— `chrome_devtools` 分支对清单内内容**整体重采**，不因库中已有而跳过；`justoneapi` 分支只为仍缺失的字段发起请求（按条计费）。正文、封面图和视频文案等不随时间变化的产物，一律只补缺、已有即复用。调用 `账号内容明细补全批处理.py` 时，公开动作只传 `--run-id / --workspace-root / --action`；`2.2` 建立批次上下文时另加 `--flow-type self_account` 和账号、两份 CSV 参数，范围准备与确认用 `--prepare-content-scope / --confirm-content-scope` 加范围参数，`2.4` 的改源补抓另加 `--allow-source-switch` 和 `--data-source`。账号、CSV、内容范围和所有内部路径从批次上下文读取，不传旧报告或路径覆盖参数。

#### 已有数据的复用范围

**明细字段不作为跳过依据**：库中已有值可能是旧值，`chrome_devtools` 分支对清单内内容整体重采。以下来源只服务 `justoneapi` 分支（只为仍缺失的字段发起计费请求）：

1. `<当前账号内容列表CSV>` 已有的明细字段；
2. `<我方内容库CSV>` 中同一 `内容ID` 的字段；
3. 当前内容目录中稳定落盘的 `内容基础结构化数据.json`。

已有正式字段能够补齐时，不再调用外部接口覆盖。**不随时间变化的产物一律复用**：正文、封面图和视频文案（ASR）只补缺，已有且可读的即跳过。账号过程目录中的临时调试文件不能作为默认输入。

#### `chrome_devtools`

使用 Chrome（`data_source = chrome_devtools`）时，在同一 Chrome 会话中按以下步骤执行。页面取数按 `执行单元/Chrome内容详情取数协议.md` 的「账号批处理 item 模式」执行；批处理器负责计划、模板、整批结果和正式写入的校验。

**取数口径**：对锁定清单内的**每一条**内容整体重采明细字段，不因库里已有而跳过，也不做字段级的部分取数 —— 库中已有值可能是旧值（同一账号实测互动数可差一倍）。取数条数等于清单条数，耗时可随条数线性增长。

**互动数不从公开页取**（2026-11-01 起）：点赞、收藏、分享、评论以内容列表里的值为准 —— 那个值来自创作者中心列表接口，是平台最新统计，一次拿全、不会和页面数字打架。所以：

- 公开页只负责两件事：**正文文本**、**视频下载链接**。
- **公开页有登录墙不等于读不到**：实测未登录时 `desc`、`video`、`interactInfo`（含点赞/收藏/评论/分享四个数）全都在。看到扫码框就判断「要登录才能拿数据」是误判，不许据此要求用户登录。
- 公开页的坑是**数值为 0 时返回空字符串**，容易被当成缺失再补成 0，所以互动数一律以内容列表为准。
- 页面上互动数为空时，结果里对应字段**留空**，由提交环节保留内容列表里的原值，**不得写 0**。
- 内容列表里这几项本身是空的（旧数据）时，先按 `执行单元/创作者中心取内容列表.md` 重新取一次列表把互动数补上，不要退回公开页。
- 抖音的创作者中心作品列表直接带全部互动数，同一条规则：以列表为准。

##### 准备批次

先由批次上下文根据已确认的范围生成并锁定 Chrome 批次计划：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --action prepare-chrome
```

只读取该动作返回的本轮计划、结果模板和唯一整批结果路径；计划中的目标、顺序、身份和输出位置均已锁定。后续提交、正式明细和重试沿用同一命令格式，仅将 `--action` 改为帮助列出的 `commit-chrome`、`collect-details` 或 `retry`。

##### 采集内容

- 第一条成功完成完整探索的内容冻结当前 AI 和 Chrome 会话的方法。
- 首条目标失败时按模板写入失败 item，不得视为方法已经冻结，继续寻找首个成功探索项。
- 后续内容导航到目标页面后先按协议校验身份，再复用已冻结的方法：不重新 `list_network_requests`、不重新搜索响应式对象、不重新试探 DOM。
- 固定方法返回缺字段、ID 不匹配或结构校验失败时，才允许该目标按协议重新进行一次有界探索；仍失败时记录真实失败原因和缺失字段，不得猜值或无限探索。
- `request_url` 必须是当前地址栏的真实 URL，`observed_content_identity` 必须从当前已加载页面提取；两者不得复制计划中的预期值。
- 每个目标无论成功或失败都必须按模板写入唯一的整批结果文件，不得跳过、补入、替换或重排目标，也不得直接回写正式 CSV。小红书视频详情的 Network 响应**存在时**使用 Chrome 计划中本条 `raw_detail_json` 作为 `responseFilePath`，固定落在本轮 `detail-data/raw-note-details/<内容ID>.json`；页面结构化状态已可取全字段、页面未发出该请求时，按 `raw_detail_unavailable` 记录真实原因并继续，不得为凑出响应反复扫描 Network。抖音视频同理：把页面自己发出的 `GET /aweme/v1/web/aweme/detail/` 响应（`aweme_id` 精确等于当前目标）保存到本轮 `detail-data/raw-details/<内容ID>-detail.network-response`；请求不存在或被拦截时记录 `raw_detail_unavailable` 并继续。这份响应是 `2.7` 取抖音 H.264 视频直链的正式来源。其他网络读取使用计划预分配的路径。禁止使用 `output_path`、临时猜路径或从 MCP 内联文本抠 JSON。
- Network 响应成功后只从对应文件读取原始 JSON；页面结构化状态或 DOM 降级时，候选必须保留原始 `type / time / publish_time / create_time / timestamp`，不得投影成只有标题、封面、点赞数的窄对象。
- 每条 Chrome 结果至少保留 `内容ID / 状态 / 标题 / 媒介形式或原始 type / 发布时间或原始时间字段 / 点赞数 / 收藏数 / 分享数 / 评论数 / 封面图原链接 / 视频下载链接 / 对外页面链接 / 正文文本或正文获取状态`；`type=video` 统一交给脚本映射为 `视频`，`type=normal/image` 统一映射为 `图文`，时间戳统一交给脚本转换为系统格式。

计划和整批结果是本轮暂存文件，不是正式业务结果。Chrome 页面操作只形成批次候选，再由脚本统一验收；正式字段和报告只能由执行单元提交。导航、遮罩变化或截图失败后，旧 snapshot 的全部 `uid` 立即失效；重新 snapshot 后才能点击，失败时不得继续使用旧 UID。

##### 提交与收集

采集结束后，使用同一个 `<本轮运行标识>` 提交批次：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --action commit-chrome
```

`commit-chrome` 统一校验计划、结果条目、内容身份和工作区路径；身份失败只拒绝当前条，同批其他通过项继续提交。提交成功后，执行器写入内容结构化数据，并把已取得字段合并回本轮正式 CSV；写入目标由批次上下文绑定的路径决定，本流程不指定路径，也不手工写 CSV。

随后运行批次收集动作，生成本轮 canonical report：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --action collect-details
```

#### `justoneapi`

使用 JustOneAPI 时，直接执行同一批次收集动作：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --action collect-details
```

脚本只为缺失字段发起 JustOneAPI 请求，随后标准化数据、回写本轮正式 CSV 并生成本轮 canonical report。

#### 结果判断

命令成功后只读取标准输出返回的 `report_json`，再读取该正式报告：

- 报告中的 `run_id`、账号、数据源、范围模式或原始范围与已确认范围不一致：使用合同冲突原因说明真实错误并停止。
- 已通过明细验收的范围只取报告返回的 `validated_detail_content_ids`；后续衍生字段和固定处理分别只取对应的 `eligible_for_derived_content_ids / eligible_for_followup_content_ids`，AI 不重新筛选。
- `retry_required = true`：进入 `2.4`。
- `retry_required = false`：将当前报告作为最终明细报告，进入 `2.5`。
- 命令失败、报告缺失、无法解析或关键字段缺失：说明真实错误并停止。

执行单元已经写入的正式字段保持实际状态。流程不得回滚、补写或逐字段复验，也不得把命令退出成功等同于整批内容完整成功。

### 2.4 处理失败内容

#### 同源重试

`2.3` 返回 `retry_required = true` 时，同一数据源只自动重试一次。保持同一任务、账号、运行标识、原始范围和数据源，只重试首次报告列出的失败内容：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --action retry
```

执行器自己从本轮报告读取 `retry_content_ids` 并记录第二次采集，不重跑成功项；AI 不传内容 ID、不传上一份报告和报告路径，也不手工合并两轮结果。

Chrome 仍按 `2.3` 的计划、采集、提交和正式明细补全顺序执行；JustOneAPI 直接再次执行明细补全。只接受执行单元合并后的报告。

未经用户明确同意，不得切换数据源，也不得把公开补采结果覆盖到后台详情字段。

#### 第二次结果

- `unresolved_content_ids` 为空：以合并报告作为最终明细报告，进入 `2.5`。
- `unresolved_content_ids` 非空：先向用户说明三件事——哪些内容成功、哪些内容失败、失败的具体原因，再展示可选处理方式并停在本步等待用户选择。执行单元不得返回或决定“是否需要用户选择”。
- 重试命令或报告合并失败：说明真实错误并停止；首次报告和已经写入的正式字段保持执行单元实际状态。

这里的“失败”只表示某些内容的详细资料没有拿到，不表示整个平台账号失效。已经成功取得的内容仍然有效；失败内容不能补写成成功，也不能在没有说明的情况下从本轮结果中消失。

用户可以选择以下处理方式：

1. **改用另一个可用来源补抓未解决内容**
   - 适用情况：当前数据源持续失败，或用户认为应该改用另一种取数方式。
   - 系统处理：同一任务只允许改源一次。先按 `执行单元/公开数据获取环境检查与数据源选择.md` 确认替代来源当前可用，并取得用户对该具体来源的明确同意，再执行下方“改源补抓”。
   - 后续：只补抓最终报告的未解决内容，不重跑成功项，也不自行合并两轮结果。
2. **使用成功子集继续**
   - 适用情况：用户接受少量内容缺失，希望先完成分析。
   - 系统处理：只有最终报告的 `eligible_for_followup_content_ids` 非空时才展示。不修改原始锁定范围，冻结当前报告的成功范围并进入 `2.5`；失败内容仍记录在 `missing_deliverables` 和逐条事实中。
   - 后续：最终反馈必须明确原始范围、成功范围和未解决内容，不能描述为完整覆盖；AI 不得手工删除失败项或改写内容范围。
3. **结束本任务**
   - 适用情况：用户不再需要继续获取这个账号的数据。
   - 系统处理：使用当前真实缺口说明真实错误并停止；保留报告和已经写入的正式数据，但不保留本任务的恢复入口。
   - 之后继续：以后需要继续时，由公开入口重新发起新任务，不能自动恢复或无限重试。

#### 改源补抓

用户明确同意改源后，只重试最终报告的未解决内容，并使用与上一份报告不同的数据源：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --action retry --allow-source-switch --data-source "<新数据源：chrome_devtools 或 justoneapi>"
```

- 补抓范围由执行器从最终报告的 `retry_content_ids` 读取，AI 不传内容 ID；执行器同时校验来源确实改变且本阶段只切换一次。
- 改源只影响本轮补抓内容的来源；本流程不改写 `<当前账号内容列表CSV>` 的 `基础数据获取方式`，也不把新来源描述成基础阶段的建档来源。
- `unresolved_content_ids` 为空：将改源后的合并报告作为最终明细报告，进入 `2.5`。
- 仍有未解决内容：不再自动重试或继续换源；有后续可用内容时只提供“使用成功子集继续”或“结束本任务”，没有后续可用内容时只提供“结束本任务”。
- 改源命令失败或报告无效：说明真实错误并停止，已有报告和正式数据保持执行单元实际状态。


### 2.5 获取创作者中心数据（小红书 / 抖音）

本步骤只适用于 `self_account`、平台为小红书或抖音、且基础数据源为 `chrome_devtools` 的批次；其他情况按跳过规则记录真实原因，继续进入 `2.6`，不影响公开明细、衍生字段、文案、特征落表和诊断。

**进了这一步就不许只采内容级**：账号级那十项（账号概览）是工作台「账号档案」和首页「最近数据」的唯一数据源，缺一项就空一块。页面打不开、没登录才允许整块记 `未获取`；打得开就必须采满，缺的项当场补采一次（见下面「校验并保存正式数据」），不许用页头汇总数或内容级数字凑。

#### 前置判断

进入本步骤前，先按以下顺序判断：

| 条件 | 处理 |
| --- | --- |
| 平台不是小红书或抖音 | 跳过本步骤，记录 `平台不支持创作者中心采集`，进入 `2.6` |
| 数据源不是 `chrome_devtools` | 跳过本步骤，记录 `JustOneAPI 不提供创作者中心数据`，进入 `2.6` |
| Chrome 不可用 | 跳过本步骤，记录真实连接错误，进入 `2.6` |
| 对应创作者中心未登录或跳转登录页 | 跳过本步骤，记录 `创作者中心未登录`，进入 `2.6` |

跳过只影响增强资料，不改变 canonical report 的完成状态，也不得在最终结果里描述成已获取。

上面四种是**唯一允许跳过**的情形。计划已经生成（`status = planned`）就必须采完并 `commit`，不得以“先把链路跑完”“后面再补”为由跳过。确实因上面四种原因跳过时，最终反馈必须写明缺的是账号概览、内容数据还是评论原文，并说明工作台「账号档案」会因此为空，不得只写一句“跳过增强资料”。

#### 生成采集计划

```bash

  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --action prepare
```

- 只接受 `ok = true`、`status = planned`，并保留返回的 `plan_path`。
- 返回 `skipped_platform_unsupported` 或 `skipped_data_source_unsupported` 时，记录原因并进入 `2.6`，不得自行改写平台或数据源。
- 计划已经锁定本轮账号身份和内容清单，后续不得更换账号或内容清单。

#### 采集页面数据

严格执行 `执行单元/获取我方平台内容分析数据.md` 中与当前平台对应的分支。

小红书：

- 只打开「内容分析 → 笔记数据」当前页面第一页；看到几行就采几行。
- 不点击日期选择器、不调整时间区间、不切换月份或年份。
- 不翻页、不切换每页条数、不滚动加载更多。
- 对这批可见笔记逐条进入「分析详情」，读取后台指标；不得进入列表外笔记。
- 进入详情前先按「笔记管理」确认公开状态；只处理公开笔记，私密、仅自己可见和其他非公开状态跳过，不取详情、不匹配、不新建内容。
- 页面时间范围原样记录，不得推算或补全。
- 账号概览在**另一个页面**，别拿首页顶栏充数：点左侧「数据看板」→「账号概览」，落到 `https://creator.xiaohongshu.com/statistics/account/v2`（页面标题「账号诊断」）。把这个地址写进候选的 `account_overview.页面链接`；写首页 `/new/home` 会被执行器拒绝。

抖音：

- 账号级数据读取「数据中心」（`https://creator.douyin.com/creator-micro/data-center/operation`），把这个地址写进候选的 `account_overview.页面链接`。要采满十项：**统计周期**、播放量、互动率、完播率、作品数、粉丝净增、5秒完播率、2秒跳出率、封面点击率、平均播放时长。总览五项连「超过/低于 X% 同类作者」一起记；不切换昨天/近7天/近30天，不导出。关注数、粉丝总数是账号主页数据，不写进概览。
- 内容级只取「内容管理 → 作品」当前第一页可见作品卡片；不翻页、不切换排序或筛选、不滚动加载更多。同时把页面自己发出的 `GET /janus/douyin/creator/pc/work_list` 首屏响应保存到本轮暂存 `创作者中心数据/作品列表原始响应.json`；这份响应里的 `play_addr.url_list` 是 `2.7` 取抖音视频直链的首选来源（火山能拉取），不要重开公开页猜链。
- 只有页面状态为 `已发布` 的作品视为公开；`私密`、`审核中`、`未通过` 以及其他文字一律按非公开处理，不取详情、不取评论、不取文案、不匹配、不新建内容。
- 公开作品逐条点击该行「播放」数字进入「作品数据详情」新标签页，从真实 URL 读取平台原生内容 ID，读取「总览」指标。
- 在详情页点击「评论管理」，把首屏评论列表响应原文保存到 `.meiling/staging/self-account-diagnose/<run_id>/评论/<平台原生内容ID>-评论原始响应.json`；不滚动加载更多、不翻页、不回复。
- 采集完关闭详情标签页回到内容管理，不得改变可见行集合；单条失败只记录该条。
- 评论数为 0 或没有评论列表响应时不写原始响应文件，并在 `后台详情.字段口径告警` 记真实原因。

候选固定写入：

```text
.meiling/staging/self-account-diagnose/<run_id>/创作者中心数据/候选.json
```

候选结构以执行单元文档为准；不得写入 `内容ID` 或匹配结果，匹配由 `commit` 完成。

#### 校验并保存正式数据

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/创作者中心数据分析采集执行器.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \

  --candidate-file ".meiling/staging/self-account-diagnose/<run_id>/创作者中心数据/候选.json"
```

- 只有返回 `ok = true`、`status = committed`、`formal_dir`、`latest_pointer` 才算正式写入成功。
- 正式数据写入账号目录 `创作者中心数据/<采集时间>/`，包括 `账号概览.json`、`内容分析.json`、`采集报告.json`，并更新 `创作者中心数据/最新采集.json`。
- 执行器负责内容匹配：先按标题完全匹配；标题重复时记为「标题重复」；标题未命中再用平台原生内容 ID 匹配；仍未命中且后台详情成功时自动新建内容并回写账号内容列表。

- 抖音内容管理的 `已发布` 由执行器统一归一为 `公开`；其余状态文字按非公开跳过。

#### 结果边界

- 正式写入成功时，保留 `visible_row_count`、`matched_count`、`unmatched_count`、`account_overview_status` 和 `missing_fields`，供最终反馈和后续诊断使用。
- 未匹配行不再直接丢弃：能取得后台详情的会新建内容并回写账号内容列表；只有后台详情失败的行保留为未匹配，不猜测内容 ID。
- 本步骤失败或跳过时，保持已有正式数据不变，在最终反馈中写明原因；不得阻断 `2.6` 及之后的步骤。
- `commit` 报 `account_overview_page_invalid`（页面链接不是账号概览页）时，不算这一轮失败：按上面写的入口重新打开账号概览、把这一页地址和十项填回候选，重试一次 `commit`；重试仍被拒才按未获取记录，并把被执行器拒掉的原因照实写进反馈。
- 本步骤不写 `过程记录/当前阶段状态.json`，也不改写 `我方账号库.csv` 或 `内容列表.csv`。

### 2.6 计算衍生字段

基于已提交的正式明细，计算并回写 `核心互动数`、`数据水平` 和 `发布时间区间`。

#### 读取与执行

- 只读取最终明细报告中的 `eligible_for_derived_content_ids`；该范围为空时跳过本步骤，直接进入 `2.7`。
- 范围非空时，在已锁定的批次上下文中调用固定批次动作；账号、两份正式 CSV、内容 ID、任务和报告路径均由程序读取并校验，模型不得另行拼接或覆盖。

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --action calculate-derived
```

该动作由批次执行器内部驱动 `账号衍生字段计算批处理.py` 并传入本轮可计算范围，本流程不直接调用内层执行器，也不传路径；报告路径由执行单元固定生成，只从标准输出取得本轮衍生字段报告。

#### 结果边界

- 执行器只处理可计算范围，回写两份正式 CSV，并返回本轮衍生字段报告。
- 衍生字段是附加增强，不是详细数据阶段的硬完成条件。部分或全部失败只记录为降级提醒，不回滚已完成的明细，也不改变后续处理范围；衍生字段失败保留在 canonical report 的缺口信息中，由诊断流程统一反馈。
- 命令状态无法确认时同样只按失败提醒处理，不声称衍生字段已经完成。

### 2.7 执行固定后续处理

通过一次批处理补齐封面和视频文案，并完成收尾。

#### 处理规则

- 只处理最终明细报告允许进入后续处理的内容（`eligible_for_followup_content_ids`）；该范围为空时，使用报告中的真实缺口说明真实错误并停止，不得伪造后续报告、诊断交接或完成状态。证据只读取正式 CSV 和本轮已提交的结构化详情。
- **封面**：已有可读封面时直接复用；缺失时根据 `封面图原链接` 下载，并在成功后回写两份正式 CSV 的封面路径。缺少链接或下载失败时记录真实缺口。
- **视频文案**：正文证据按 `formal_transcript > platform_caption > asr > unavailable` 选择。先消费本轮可验证的平台字幕；只有字幕不可用或身份不一致、且存在有效视频 URL 时，才准备一次本地 ASR。
- 图文、未知、空媒介和其他非视频内容跳过视频文案；视频缺少 `http(s)` URL 时，先按 `执行单元/获取我方平台内容分析数据.md` 的「视频文案」分支补齐：小红书的「笔记管理封面入口」每条笔记单独新标签页点封面，读取带 `xsec_token` 的公开页视频地址；抖音优先用 `2.5` 保存的 `创作者中心数据/作品列表原始响应.json` 里的 `play_addr`，没有这份响应时才按 `执行单元/Chrome内容详情取数协议.md` 的 `2.3c` 打开公开页读 `aweme/v1/web/aweme/detail/`；再调用 `获取视频文案执行器.py`。不需要登录公开站，只处理公开内容；仍取不到时记录“视频缺少视频下载链接”。视频文案只使用已锁定数据源取得且经校验可访问的视频 URL。
- **视频直链必须是 `.mp4`，不能是 `.m4s` 分片**（2026-11-01 实测）：小红书的详情响应和页面里都可能给 `.m4s`，火山的 ASR 会直接拒（`45000151 音频格式不正确`）。拿到 `.m4s` 时按 `执行单元/Chrome内容详情取数协议.md` 的 `2.3` 重新取 `.mp4`（优先 `<video>` 的 `currentSrc`）；`.m4s` 的签名绑在自己路径上，**改扩展名拼不出 `.mp4`**（实测 403）。整条视频确实只有 `.m4s` 时，在 `备注` 写明，不要反复重试烧额度。
- **抖音视频直链优先用创作者中心 `work_list`**（2026-11-04 实测）：该响应里 `play_addr` 给的 `v5-se-gddgtc-cold.douyinvod.com` / `v95-hzyy-thr-daily-colda.douyinvod.com` 直链，火山 URL 转写能正常拉取（实测 779 字）。公开页那组 `v95-zjwz2tc-web.douyinvod.com` 现在会被火山判 `45000006`，`media-video-hvc1` 是 H.265 分路（`45000151`）。公开页取链只在没有创作者中心响应时才用，按 `2.3c` 读 `aweme/v1/web/aweme/detail/` 的 `play_addr_h264`，再做一次 Range 预检；批处理器会在提交前拦掉 `blob:`、H.265 和分片地址。
- **抖音文案保留「本机下载 + base64 直传」兜底**（2026-11-04 实测）：创作者中心直链拉不到、链接过期或本机下载 403 时，执行器会自动下载并 base64 直传火山，已实测完整视频转写成功；不需要 AI 手工上传。下载失败时按 `2.3c` 重新打开公开页取一条新直链，只对失败的那条重试一次，不要整批重跑。
- 本地 ASR 配置缺失、URL 失败或空转写都记录真实失败，不伪装成已完成；失败只影响对应内容，保留在最终报告的缺口中。
- 公开流程不调用单条 dry-run，不读取或传递 ASR ticket；票据不出现在公开参数、Skill 或报告中。媒介判断、视频文案和失败降级由批处理器统一编排。
- 单条失败不得中止剩余内容；失败和降级只写入 canonical report 的缺口信息，缺口必须保留真实失败原因，失败内容记录在 `missing_deliverables` 和逐条事实中。

#### 执行步骤

1. **执行 `process`**：按批次上下文返回顺序处理全部内容，由批处理器批量补齐封面、准备平台字幕，并对缺少正文的视频编排本地 ASR。
   ```bash
   python3 "<当前工作区根目录绝对路径>/执行单元/账号后续详细处理批处理.py" \
     --workspace-root "<当前工作区根目录绝对路径>" \
     --run-id "<本轮运行标识>" \
     --action process
   ```
2. **按返回结果分支**：
   - `next_action = finalize`：本步交付完成，执行第 3 步。
   - `next_action = retry_or_review`：本轮 canonical report 仍为 `failed`，说明真实失败原因并停止，不伪造完成状态。
   - 返回其他取值时说明真实错误并停止，不自行推断下一步。
3. **执行 `finalize`**：仅当上一步返回 `next_action = finalize` 时执行。
   ```bash
   python3 "<当前工作区根目录绝对路径>/执行单元/账号后续详细处理批处理.py" \
     --workspace-root "<当前工作区根目录绝对路径>" \
     --run-id "<本轮运行标识>" \
     --action finalize
   ```
   - `next_action = continue_detail_flow`：本轮 canonical report 已就绪，校验后进入 `2.8 特征落表（实例 + 观察）`。
   - `next_action = retry_or_review`：报告状态仍为 `failed` 或后续交付未完成，说明真实失败原因并停止。

单条执行结果只是 checkpoint；内容范围和 canonical 路径由任务上下文固定推导，流程不传路径覆盖参数。AI 只消费 process/finalize 返回的 canonical report 和缺口信息，不得手工回写内容文件、CSV，也不得裁剪、补字段或重组报告。报告身份、账号或范围不一致时说明真实错误并停止。

### 2.8 特征落表（实例 + 观察）

#### 处理规则

- **范围只认 `2.2` 锁定的清单**：待落表内容由 `--action plan` 按批次上下文里的 `selected_content_ids` 算出，AI 不得增删；`skipped` 会连原因一起返回，不要逐条去试。
- **只写两张表**：候选第 1、2 节写 `沉淀结论/内容特征实例.csv`，第 3 节「待补充标签」写 `沉淀结论/内容特征观察表.csv`。
- **不再产 `内容画像与特征卡.md`**（2026-09-27 退役）：候选本身就是结构化的，直接落表。

#### 执行步骤

**1) 取本轮待落表清单**（分批：每批最多 5 条）：

```bash
python3 "<工作区根目录>/执行单元/内容特征落表执行器.py" \
  --workspace-root "<工作区根目录>" \
  --source 我方内容 \
  --action plan \
  --run-id "<本轮运行标识>" \
  --limit 5
```

返回里的 `pending` 是**本批**要落表的内容（各带标题与 `evidence_path`）；`candidate_dir` 与 `candidate_naming` 指出候选该写到哪、怎么命名；`pending_total` 是本轮待落表总数，`remaining_count` 是这批之后还剩几条。**下面的 `commit` 必须用同一个 `--limit`**——两个动作各自按"最前面 N 条"算同一批，值不一致就会把没写候选的条目录成 `candidate_missing`。

**2) 生成本批候选**：对 `pending` 里每一条，按它的 `evidence_path` 读原文，用 `提示词/内容特征提取提示词.md` 生成一份候选，写进 `candidate_dir`，文件名用 `candidate_naming`（即 `<内容ID>-特征候选.md`）。**一次生成整批（本批最多 5 条），不要逐条调用执行器，也不要多写下一批的候选。**

**3) 本批落表**：

```bash
python3 "<工作区根目录>/执行单元/内容特征落表执行器.py" \
  --workspace-root "<工作区根目录>" \
  --source 我方内容 \
  --action commit \
  --run-id "<本轮运行标识>" \
  --limit 5
```

一次调用完成本批的校验与落表。按 `batch`（`committed` / `failed` / `skipped`）与 `items` 逐条反馈；`skipped_reasons` 是按原因汇总的计数，用它说明被跳过的主因。`status = partial` 表示有失败项，逐条原因照实说明（例如 `account_identity_unresolved`：这条内容按内容目录路径反查不到所属账号，也没能在内容目录下的 `发布记录/<平台>-<账号ID>-<原生ID>/` 里解析出平台与账号 —— 实例行缺平台/账号会让汇总分场景时串号，所以直接跳过不写）；单条失败不影响其他内容，也不要把它说成整批失败。**`remaining_count > 0` 就回到 1) 取下一批**（已落表的条目下一轮自动以 `already_has_features` 跳过，所以循环可续、幂等）；`= 0` 才算整轮跑完。

### 2.9 获取评论原文

本步骤是诊断证据步骤，失败或跳过都不改变已提交的详细数据和 canonical report，也不算整轮失败。

#### 范围

- 只处理 `2.2` 锁定清单中、且 `公开状态 = 公开`、`评论数` 非零或未知的内容；`评论数 = 0` 的内容不发起抓取，但仍写入「平台声明评论数为 0，未发起抓取」的正式存档。
- 私密和未确认公开状态的内容不抓取评论，直接记录「私密或未确认公开状态，不抓取评论」；不因为拿不到评论而阻断诊断。
- 不扩大到基础列表 200 条。

#### 数据源

- `chrome_devtools`：打开该内容的公开页面，读取页面自身发出的评论接口原始响应，写入 `.meiling/staging/self-account-diagnose/<run_id>/评论/<内容ID>-评论原始响应.json`。只取一级评论，最多 3 页。
  - **评论接口不会随页面加载自动发出**：必须先点开评论区并滚动，或在当前页会话里直接请求评论接口（抖音 `/aweme/v1/web/comment/list/`，`count` 固定 50，游标每次前进 50）。请求列表里没有评论请求，只说明还没触发，**不等于平台没有评论，也不等于抓取失败**（2026-11-01 实测：作品页评论请求为 0，直接请求立刻返回 `total = 101`）。
  - **公开页不需要登录**：未登录时评论接口照常返回（2026-11-01 实测 `comments.list` 有数据），页面上那层扫码遮罩不影响读取。看到遮罩就判断「要看评论得登录」是误判，不许据此要求用户登录。
  - 万一真的整页跳成登录表单（不是内容页套遮罩）时，重新导航一次；仍打不开就按单条失败记录真实原因，**不要要求用户登录公开站**，也不要让这件事挡住诊断。
  - 未登录状态下平台可能只给一部分评论。实际拿到的条数少于 `评论数` 时，按真实差距写进抓取结果，不补造、不声称已抓全。
- `chrome_devtools` + 抖音：优先复用 `2.5` 在作品数据详情「评论管理」保存的原始响应 `.meiling/staging/self-account-diagnose/<run_id>/评论/<平台原生内容ID>-评论原始响应.json`，不再重复打开公开页；该文件不存在时不改用公开页猜测，按单条失败记录真实原因。
- `justoneapi`：直接调用执行器翻页。


#### 调用

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/内容评论抓取执行器.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --platform "<平台>" \
  --native-id "<平台原生内容ID>" \
  --content-dir "<内容目录路径>" \
  --source "<chrome_devtools 或 justoneapi>" \
  --comment-count "<评论数>" \
  --raw-input-json "<本轮暂存目录>/评论/<内容ID>-评论原始响应.json" \
  --output-json "<本轮暂存目录>/评论/<内容ID>-评论抓取结果.json"
```

- `chrome_devtools` 没有原始响应时省略 `--raw-input-json`，执行器按失败记录，不伪造评论。
- 评论正式文件固定写入内容目录：`评论.md`、`评论.json`；回执写暂存目录。

#### 结果

- 单条失败只记录该条，继续下一条；不得因为评论失败阻断诊断。
- 评论为空、评论数为 0、抓取失败分别记录真实状态，不互相替代。
- 不把评论数当评论文本；评论文本只来自正式 `评论.md` / `评论.json`。

### 2.10 确认详细数据交接并进入诊断

#### 交接判断规则

- 明细补全、衍生字段和后续处理由各自执行器负责验收和回写；本步骤只消费最终 canonical report，不重复逐字段验收，也不手工汇总各步骤结果。
- canonical report 的 `status` 只能是 `completed`、`partial` 或 `failed`；资料缺口统一通过 canonical report 的 `missing_deliverables` 和逐条事实表达；内容列表完整性沿用基础数据报告的 `content_list_status` 和采集停止原因（判据见 `执行单元/内容列表完整性判据.py`，不读 `data_limitations`），canonical report 不得包含 `content_list_completeness` 等冗余状态字段，本阶段不新增第二套字段。
- canonical report 的 `missing_deliverables` 分两层，格式和读者不同，不得混用：**顶层**是**人可读的句子列表**，每条形如 `「<内容标题>」缺<产物/字段>、<产物/字段>`（标题缺失时退回内容 ID），只回答"本轮哪些内容缺了什么"；**逐条** `detail_collection.items[]` 是机器事实（`content_id` + 缺口标签数组）。需要按内容取交付状态时，一律读**逐条事实**，不要解析顶层句子；也不要再往顶层写入 `{content_id, items}` 对象或内部内容 ID。
- 公开流程只使用 `<本轮运行标识>` 作为批次句柄；工作区内产物路径使用相对路径，模型不得生成或传递调度器内部身份、版本或工作区注册字段。

#### 生成并提交

本步骤不再执行取数或总结动作；`finalize` 已在 `2.7` 第 3 步执行，直接生成 canonical report，不创建独立阶段结果。范围、后续处理输入和报告路径由执行单元按 `<本轮运行标识>` 推导，模型不得拼接或覆盖；执行单元负责校验范围、账号、运行标识和 canonical report。

`<账号目录>/过程记录/当前阶段状态.json` 只由 `2.3` 的收集动作（`--action collect-details`，重试后在 `2.4` 再次执行）写入：阶段名 `我方账号详细数据获取`、`run_id` 与本轮一致、`当前是否完成` 恒为 `false`；`2.7` 的 `process` 与 `finalize`、以及本步骤都不写入或更新它。进入诊断后，该文件由《自我账号详细诊断流程》的 `2.2` 前置检查改写为诊断阶段。本流程只消费执行单元回执，不自行写状态文件。

- 回执缺失、结构不完整或命令失败：说明真实错误并停止，已经写入的正式文件保持不变，不伪造完成状态。

只有 canonical report 写入并回读成功，详细数据阶段才算完成。

#### 交接与失败分支

- `completed` 或 `partial`：确认最终 canonical report 后，使用其中已确认的内容范围（`requested_content_ids`，以及实际已处理的 `processed_content_ids`）与 `visibility_scope` 进入 `执行流程/自我账号详细诊断流程.md` 的 `2.1 判断诊断起点`。**canonical report 没有 `selected_content_ids` 字段**，不要按该名字去找；`selected_content_ids` 只出现在 `2.2` 范围准备的回执和诊断前置检查的 `content` 里。缺少范围时不得进入诊断。资料缺口只写入 canonical report，由诊断流程负责解释。
- 创作者中心数据不参与 canonical report 的完成状态判断；其正式目录与 `创作者中心数据/最新采集.json` 由 `2.5` 的 commit 回执给出，供后续诊断阶段接入读取，缺失时按「未获取」处理。
- `failed`：不进入诊断。向用户说明真实失败原因、已成功范围和仍缺失的交付项；不得把部分结果描述为完整完成。
- 正常交接时不单独展示取数阶段的中间回执；完整结论、资料边界和信息不足项由诊断流程完成后统一反馈。
