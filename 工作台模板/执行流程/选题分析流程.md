# 选题分析流程

**本流程开始前先执行一次使用统计上报**（静默脚本，失败不影响任何流程，也不必向用户提及）：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 选题分析流程 --phase start
```

## 1. 总流程说明

1. 确认入口与本轮问题
   - 进入 `2.1 确认入口与本轮问题`
2. 检查前置资料
   - 进入 `2.2 检查前置资料`
3. 确认选题对象
   - 进入 `2.3 确认选题对象`
4. 生成并保存正式分析
   - 进入 `2.4 生成并保存正式分析`
   - 用户看到正式结果后要求修改时，回到本步骤更新，不重新走确认流程
5. 反馈结果
   - 进入 `2.5 反馈结果`

### 协调器使用规则

选题定位、输入建档、前置资料检查、候选暂存和正式保存，都通过协调器执行：

```text
python3 "<当前工作区根>/执行单元/选题分析流程协调器.py" --workspace-root "<当前工作区根>" --action "<动作>" <动作参数>
```

- 首次调用执行 `prepare`，可传用户已提供的 `--topic-id`、`--topic-name`、`--content-id`、`--reference-url`、`--reference-analysis-path`、`--transcript-path`；没有的参数不传。
- 用户明确要求重新分析或修改已有选题时传 `--topic-intent reanalyze`；其余情况不传，协调器默认按新题处理。选题 ID 本身就是老题身份，不需要再传意图。
- 首次 `prepare` 必须建立本轮 `context_file`，并返回 `run_id`。后续调用严格复用回执中的 `context_file`，只使用 `action_contract` 给出的参数。
- `run_id` 只用于 `.meiling/staging/topic-evaluate/<run_id>/` 暂存隔离，不是跨模块任务 ID；本流程不创建父子任务。
- 返回 `needs_reference_analysis` 时，默认按 `benchmark_then_continue_request` 先完成对标再回来，不向用户出示二选一；只有用户主动说“不用参考”，或对标失败后用户选择不带参考继续时，才执行 `continue_without_reference_request`。
- 返回 `needs_topic_input` 时回到 `2.1`；返回 `needs_topic_selection` 时按 `2.3` 让用户指明唯一老题。其他对象确认状态不再作为用户确认点。
- 只有返回 `status=stage_ready` 才能生成正式分析候选；`stage_ready` 只表示输入已冻结，不表示分析或保存完成。
- 协调器返回 `status=blocked`、`ok=false`、命令失败、状态缺失或合同不完整时，说明真实原因并停止。
- `stage_ready` 后直接生成候选并执行 `save_request`，**不询问用户是否定稿或是否保存**。
- 只有保存回执同时包含 `status=completed`、`commit_status=committed`、`analysis_path` 和 `analysis_sha256`，才算正式保存成功。

## 2. 具体流程说明

### 2.1 确认入口与本轮问题

#### 读取

读取当前对话中用户已经明确提供的信息，并判断本轮来自独立入口，还是来自对标内容分析完成后的用户选择。

#### 需要确认的内容

进入选题查找前，至少要明确：

- `选题名称`、足以定位选题的自然语言表达，或 `选题 ID`；
- 用户本轮准备讨论的具体问题或方向。

有助于后续判断、但不要求一次问完的信息包括：

- 更具体的想法、背景或触发原因；
- 是否有参考内容链接；
- 对标内容入口已经正式保存的 `content_id`、`reference_url`、`reference_analysis_path`；有 `transcript_path` 时一并读取。

#### 处理规则

- 选题名称或题意不清：只追问选题本身，达到可查找程度后再进入 `2.2`。
- 用户一次提出多个方向：先确认本轮唯一要处理的选题，不提前形成六要素结论。
- 用户主动提供选题 ID：把 ID 作为老题身份直接进入，不再询问是否沿用老题。
- 用户明确要求“重新分析”“修改已有选题”或同等意思：按老题重跑处理，并在 `prepare` 中传 `topic_intent=reanalyze`。
- 用户改变题意或本轮问题：重新执行本节。
- 其他信息暂时不完整，但已经足以查找选题：允许进入 `2.2`，不把本节变成完整问卷。

### 2.2 检查前置资料

#### 第一次 `prepare`

第一次调用协调器的 `prepare`，建立本轮 `context_file`，并返回 `run_id`、`context_file` 和可执行的 `action_contract`。模型只根据回执状态分支，不自行判断文件是否存在。若同时出现选题定位待确认状态，先转入 `2.3` 完成对象处理，再复用同一上下文继续本步骤的资料检查。

#### 参考内容分支

- 没有参考链接：最终 `prepare` 返回 `reference_status=absent`，直接进入 `2.3`。
- 有参考链接，且正式内容分析存在、可读并确认属于当前链接：最终 `prepare` 返回 `reference_status=ready`，在 `inputs` 中返回这份文件；有 `transcript_path` 且可读时作为补充资料返回，进入 `2.3`。
- 有参考链接，但正式内容分析缺失、不可读或无法确认对应关系：返回 `status=needs_reference_analysis`。此时**不让用户选择是否使用参考**，直接向用户说明：
  ```text
  这条参考链接还没有对应的正式对标分析。我先完成这条内容的对标分析，再回来继续选题分析。
  ```
  随后按 `benchmark_then_continue_request` 启动对标内容模块，并保留原 `context_file` 和本轮选题参数。对标完成后，把正式 `reference_analysis_path` 和已有的 `content_id`、`transcript_path` 交回原 `context_file`，再次执行 `prepare`，自动继续选题分析，不再询问“接下来做什么”。
- 用户主动表示“不用参考”“直接分析选题”时，执行 `continue_without_reference_request`，后续不使用这条参考证据。
- 对标失败时，说明真实失败原因，让用户选择“重试”“换链接”或“不带参考继续”。只有这种失败分支才需要用户决定；不得静默改成不带参考。
- `status`、`action_contract`、`reference_decision`、`context_file` 等字段只供模型和执行单元使用，不得原样展示给用户。

入口资料改变时回到本步骤重新 `prepare`。

#### 我方概要分支

协调器同时检查 `我方资料/我方当前概要.md`：存在、非空且可读时返回文件及哈希，纳入 `inputs`；缺失、为空或不可读时返回 `overview_status=unavailable`，不启动自媒体规划流程，直接继续。没有规划资料时不得虚构已读取规划或账号适配依据，也不要求在正式正文中添加固定限制栏目。

只有参考内容分支已经得到明确处理，且概要分支已经完成记录后，才进入 `2.3`。

### 2.3 确认选题对象

按协调器回执和下面规则处理，不向用户询问“是否新建”“是否沿用老题”或“是否改名”：

- 用户给了选题 ID：直接按该老题更新。ID 对应的库内名称与本次传入名称不一致时，默认沿用库内名称；只有用户明确要求改名时，才按 `rename_confirm=true` 使用新名称。
- 用户明确要求重跑老题，且名称唯一命中：直接按该老题更新，并冻结当前完整记录和可读旧版分析正文。
- 用户未给 ID、也未明确要求重跑：一律直接新建。名称在选题库中已经存在时也按新题处理，不因为同名而打断。
- 新题名称应根据本轮想法拟成具体、可区分的完整名称；需要与已有同主题选题区分时，按新题的角度或切口命名，不机械追加序号。
- `needs_topic_input`：回到 `2.1` 补充选题名称或 ID。
- `needs_topic_selection`：只会在“明确重跑老题、未给 ID、名称命中多条”时出现。展示每条候选的 ID、名称、当前状态以及有值时的核心命题、是否建议做、参考内容链接，让用户指明唯一老题，再执行对应的 `selection_requests`。这是本步骤唯一需要用户选择的情况。

只有返回 `status=stage_ready` 才进入 `2.4`；旧正文缺失时仍可继续，直接生成本轮完整版本。

### 2.4 生成并保存正式分析

#### 读取

- `分析框架/选题分析方法论.md`；
- `提示词/选题分析成稿提示词.md`；
- `stage_ready` 返回的冻结输入；
- 当前对话中用户已经明确的选题对象、本轮问题和补充信息；
- 老题可读的旧版正式正文，仅在局部更新或说明本轮变化时使用。

不得另行读取远程语义包或其他未声明资料。

#### 一次生成

- 根据现有输入**一次生成完整正式分析**，不先把六个核心元素拆开让用户逐项填写，不先展示候选等待整体确认。
- 完整正文按成稿提示词包含主题、目标用户、核心痛点、收益承诺、核心命题、切口，以及 `建议做 / 暂缓 / 不建议做` 的结论。
- 信息不足时仍给出当前最合理的完整判断，不设置“AI 暂定”“待确认”“当前限制”等固定标注或栏目；没有的数据、没有执行的分析和没有读取的资料不得编造。
- 只有题意无法理解、用户信息直接冲突，导致无法形成任何完整分析时，才回到 `2.1` 追问一个问题；其余情况直接成稿。
- 老题只做局部修改时，只更新修改点及其直接影响，不扩散到无关部分。

#### 保存

1. 在协调器指定的精确路径生成本轮暂存文件 `选题分析候选.md`。
2. 候选生成后直接执行 `save_request`，不询问是否定稿。提交请求、选题 ID、正式路径、选题库字段和参考路径均由协调器上下文提供，模型不得自行拼接。
3. 以协调器调用正式化执行器后返回的保存结果为准。模型不得手工编辑选题库，也不得绕过正式化执行器。
4. 老题覆盖前由协调器自动备份旧版正文；回执有 `previous_analysis_backup` 时只作为内部恢复依据，不要求用户处理。

只有协调器返回 `status=completed`、`commit_status=committed`、`analysis_path` 和 `analysis_sha256`，才算保存完成，进入 `2.5`。

#### 失败后自动恢复

- 正文生成失败或候选校验失败：使用同一份冻结输入自行修正并重新生成、保存，不向用户抛出“重试或停止”的选择。
- 正式文件、选题库写入或回读失败：先判断是不是并发冲突，再自动恢复。
  - 报 `concurrent_source_change: <路径>`：属于外部会话改动，按 `执行单元/并发冲突处置.md` 处置。本轮尚无正式写入时，等待共享文件 `我方资料/选题库.csv` 稳定后重新执行保存，最多两轮。
  - 本轮已有正式写入，或者自动恢复后仍失败：明确说明失败步骤、真实原因和当前保存状态。已存在的正式记录保持不变，本轮候选仍是暂存结果，不能当成正式结果。

#### 保存后的修改

- 用户看到正式结果后提出修改，这句话本身就是修改指令，不再单独请求“修改授权”，也不重新询问定稿。
- 按用户要求更新受影响内容，重新执行本节的生成和保存，并展示更新后的正式结果。
- 用户改变选题对象、参考内容或本轮问题时，返回 `2.1` 至 `2.3` 中对应的步骤重新处理。

### 2.5 反馈结果

直接使用 `2.4` 的保存回执反馈，不重新读取或猜测结果。Dashboard 结果优先展示，固定格式如下：

```text
## 选题分析结果

- 选题名称：<正式选题名称>

### 工作台查看
- 选题库：<dashboard_base_url>/index.html#topics

### 正式文件
- 选题分析：<协调器返回的正式分析路径>

### 分析结论
- 是否建议做：<建议做 / 暂缓 / 不建议做>
- 判断理由：<正式分析中的判断理由>

```

`dashboard_base_url` 只能使用工作台启动后返回的本地基础地址，取址方式固定按 `执行单元/工作台地址获取.md` 执行；取不到地址时写“工作台未打开”，不阻断正式结果反馈。

在上面的固定结果反馈之后，根据“是否建议做”的结果追加下面对应的回复。

正式结论为 `建议做` 时，追加：

```text
你可以继续进入内容生产；如果需要修改这份选题分析，直接告诉我。
```

正式结论为 `暂缓` 或 `不建议做` 时，追加同一套模板；将 `{是否建议做}` 替换为实际结论，并将 `{讨论原因}` 替换为“暂缓原因”或“不建议做的原因”：

```text
这条选题当前的分析结论是“{是否建议做}”。

主要原因是：{选题分析中的核心原因}

目前不建议直接进入内容生产，但这不是禁止你继续。

请选择：

**继续内容生产**

按当前选题进入内容生产。

**讨论{讨论原因}**

先继续讨论为什么{是否建议做}，以及是否需要调整选题后再决定。
```

- 用户选择“继续内容生产”：进入 `create-content`，不再补问原因或说明。`建议做` 时由公开入口传入正式 `topic_id`；`暂缓` 或 `不建议做` 时使用内容生产入口返回的 `decision_contract.continue_request`，不传本流程的 `run_id/context_file`，也不自行拼接参数。
- 用户选择讨论原因：由公开入口以同一正式 `topic_id` 新启动一轮 `topic-evaluate` 并重新 `prepare`，回到 `2.4` 更新；不复用已经结束的 `run_id/context_file`。
- 用户没有明确选择：停在当前选择点。此时正式分析已经保存，这个选择不影响本流程完成。
- 用户在同一对话中要求修改已经保存的结果：回到 `2.4`；如果选题对象、参考内容或本轮问题已经改变，先回到 `2.1` 至 `2.3` 中对应的步骤。
- 只有正式落盘的选题分析记录，才是后续内容生产流程默认读取的稳定上游输入。

---

**本流程结束后执行一次使用统计上报**（静默脚本，失败不影响任何流程）：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 选题分析流程 --phase end --status ok
```

正常走完用 `--status ok`；按阻断分支收尾用 `--status blocked`。**没走到这一步就不用补报** ——  
缺少结束记录本身就是「卡在这一步」的信号，补报反而会把卡点抹掉。
