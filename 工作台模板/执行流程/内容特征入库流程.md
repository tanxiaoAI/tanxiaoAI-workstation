# 内容特征入库流程

**本流程开始前先执行一次使用统计上报**（静默脚本，失败不影响任何流程，也不必向用户提及）：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 内容特征入库流程 --phase start
```

## 1. 总流程说明

1. 收集未覆盖观察
   - 进入 `2.1 收集未覆盖观察`，从 `沉淀结论/内容特征观察表.csv` 里取出词典还没有覆盖、但本篇又确实值得沉淀的标签，归一后聚类。
   - 观察来源是各条取数链路落表时写入的观察表，不重新分析单篇内容，也不回看暂存候选。
2. 生成新特征候选
   - 进入 `2.2 生成新特征候选`，按 `提示词/内容规律分析-新特征判断提示词.md` 一次生成完整的 `内容特征候选.md`，每条候选带一个建议决定和判断依据。
   - 这份候选只是建议稿，写在本轮暂存目录里，不写词典，也不进入任何正式报告。
3. 让用户整批确认
   - 进入 `2.3 让用户确认`，把建议新增的候选整理成一份简短清单，一次交给用户确认。
   - **用户确认前不得提交。** 用户不确认、不回复或明确拒绝时，本轮不写词典。
4. 按确认结果提交入库
   - 进入 `2.4 提交入库`，把用户没采纳的 `新增` 改成 `用户暂不采纳`，其余保持不变，交给提交器校验并原子写入 `沉淀结论/内容特征词典.csv`。
5. 反馈结果
   - 进入 `2.5 反馈结果`，只反馈本轮词典变化。本流程到此结束，**不进入、也不触发内容规律知识库流程**。

本流程只维护 `沉淀结论/内容特征词典.csv` 这一份正式资产。词典是内容定位阶段的输入（内容定位从词典取「特征小类=开头」「内容类别」的启用特征作为候选标签），所以入库越准，后面的内容生产越准。

本轮开始前先创建独立暂存目录 `.meiling/staging/content-patterns/<run_id>/`，`run_id` 只用于隔离本轮文件，后续每一步的输入文件都必须来自这一个目录。该目录只保存本轮需要传给下一步的文件，不是可恢复状态。正式文件（`沉淀结论/内容特征词典.csv`）只在提交时使用短事务原子替换；扫描观察表、模型生成、等待用户确认都不持有正式数据锁。

任何一步失败都不回滚已经提交的正式资产，只如实反馈哪一步没完成。

## 2. 具体流程说明

### 2.1 收集未覆盖观察

#### 执行

```bash
python3 "<工作区根目录>/执行单元/内容特征观察汇总执行器.py" \
  --workspace-root "<工作区根目录>" \
  > "<本轮暂存目录>/观察汇总结果.json"
```

执行器只读 `沉淀结论/内容特征观察表.csv`（**不再扫 `内容画像与特征卡.md`**，卡已退役），只取 `当前有效=是` 的行，从中提取**新特征位**（词典里还没有、本篇又确实值得沉淀的标签名），归一后聚类。表里没有某个做法的观察行是正常情况（说明那篇没发现词典缺口），不产生条目。它不写任何正式资产。

`观察覆盖内容数` 只统计**有观察记录的内容**，所以它 ≤ 工作区里已分析的内容总数——观察表本来就只登记「有缺口」的内容，不要把它当成「本轮分析了多少条内容」。

本步不接受筛选参数；新特征是全局共享资产，不能只看局部范围。

#### 成功条件与输出

只有返回 `status = collected`，才进入 `2.2`。需要使用的字段：

- `generated_at`：观察快照生成时间，`2.2` 的候选必须逐字复用它；
- `active_content_count`：观察覆盖内容数（有观察记录的内容条数，跨来源同号算两条），`2.2` 候选第 1 节的「观察覆盖内容数」逐字取它；
- `observation_count`：未覆盖观察条数（已按「来源 + 样本键 + 标准标签」去重）；
- `cluster_count`、`clusters`：聚类结果，每簇含 `cluster_id`、`representative`、`occurrences`、**`source_count`**（＝跨来源去重后的内容篇数，入库门槛就看它）、`sources`、`variants`；
- `scanned_rows` / `active_rows` / `table_fingerprint`：观察表总行数／当前有效行数／表指纹，给排查用，`2.2` 不取用。

执行失败时停止：不进入 `2.2`，如实反馈真实错误。

### 2.2 生成新特征候选

#### 输入

- `提示词/内容规律分析-新特征判断提示词.md`；
- `2.1` 返回的 `观察汇总结果.json`。

#### 生成

调用上述提示词，一次生成完整的 `内容特征候选.md`，写入本轮暂存目录。候选文件的固定结构是 3 节：`1. 本轮范围`、`2. 新特征候选`、`3. 处理说明`。本轮范围的 `生成时间`、`观察覆盖内容数`、`未覆盖观察条数` 三项必须与观察汇总结果完全一致；`候选数量` 必须等于候选表的数据行数。

`最终决定` 这一列填的是**建议**，只能取 `新增`、`合并到已有特征`、`仅保留为单篇观察`。本步只出建议稿，不写词典；`用户暂不采纳` 只能由 `2.3` 在用户确认后改写，模型在这一步不得使用。

### 2.3 让用户确认

#### 什么情况下需要确认

- 候选里没有 `新增`（包括候选数量为 0）：不写词典，不需要用户确认，直接进入 `2.4` 提交（写入 0 条），再按 `2.5` 反馈；
- 候选里有 `新增`：必须先让用户确认，确认前不得进入 `2.4`。

#### 执行

把候选里 `最终决定 = 新增` 的条目整理成一份简短清单，**一次**发给用户。每条只写：标准标签、出现篇数、定义、判断依据。清单后面固定写一句：

```text
这些是要写进规律词典的新特征。回复「按建议来」就全部采纳；只要一部分，就说哪几条不采纳；都不要就回「都不要」。
```

清单末尾补一句其余候选的去向，例如「另有 2 条与已有特征重合、1 条只作单篇观察，不写词典」，让用户知道本轮候选不止这几条。

不要逐条追问，也不要替用户默认采纳。

用户回复后按下面处理：

- 「按建议来」「全部采纳」或不指定例外的同意：所有 `新增` 保持 `新增`；
- 指定了不要的条目：把这些条目的 `最终决定` 改成 `用户暂不采纳`，其余保持 `新增`；
- 「都不要」：所有 `新增` 改成 `用户暂不采纳`；
- 用户要改某条的定义、边界、分类或建议决定：先按用户意见改候选文件那一行，再确认一次，确认后进入 `2.4`；改成 `新增` 时仍要满足入库门槛，否则提交器会拒绝；
- 用户没有回复、或回复与确认无关：本轮停止，不提交，如实反馈「等你确认，本轮没有写词典」。不得先提交再等回复。

`合并到已有特征` 和 `仅保留为单篇观察` 不写词典，不需要用户选择，保持原样进入 `2.4`，并在 `2.5` 的反馈里说明。

### 2.4 提交入库

#### 输入

- `2.2` 生成、`2.3` 按用户确认改好的 `内容特征候选.md`；
- `2.1` 返回的 `观察汇总结果.json`。

#### 执行

```bash
python3 "<工作区根目录>/执行单元/内容特征候选提交执行器.py" \
  --workspace-root "<工作区根目录>" \
  --candidate-file "<本轮暂存目录>/内容特征候选.md" \
  --observation-result-file "<本轮暂存目录>/观察汇总结果.json" \
  --receipt-file "<本轮暂存目录>/新特征提交回执.json"
```

本步不再做判定，只提交。`最终决定` 的取值只能是 `新增`、`合并到已有特征`、`仅保留为单篇观察`、`用户暂不采纳`，其中**只有 `新增` 会写词典**。提交器校验候选结构、本轮范围和入库门槛，再把决定交给 `内容特征词典更新执行器.py` 统一校验收口，由它原子写入 `沉淀结论/内容特征词典.csv`。候选文件、观察结果文件、回执文件必须在同一个暂存目录。

`新增` 行的 `出现次数` 必须填该做法出现的**内容篇数**，且不得低于程序门槛（`执行单元/内容特征候选提交执行器.py` 的 `AUTO_ADMISSION_MIN_SOURCES`）；低于门槛时整批提交失败，修正候选后重新提交。`用户暂不采纳` 行必须留空 `合并目标`，`出现次数` 照实填，不因用户拒绝而改小。

本轮没有可入库的做法时，仍要把候选文件写好并提交，`本轮入库` 会是 `0`。

#### 成功条件与结果传递

只有返回 `status = committed`，才进入 `2.5`。需要使用的字段：

- `candidate_count`：本轮候选条数；
- `dictionary_committed_count`：真正写入词典的条数；
- `decisions`：每条候选的决定结果，`action` 是最终决定，`dictionary_write_status` 是写入状态。

以同一份候选文件重复提交时，执行器返回 `reused = true` 并复用上一次回执，不重复写词典。

失败处理：

- 候选结构不合规（节名、表头、序号、枚举、本轮范围与观察汇总不一致，或 `新增` 行的 `出现次数` 不是不低于程序门槛的整数）：停止，不写词典，修正候选后重新提交；
- 词典写入失败：停止，反馈真实错误；词典保持原样。

### 2.5 反馈结果

直接使用 `2.4` 的执行器回执反馈，不重新读取或猜测结果。固定格式如下：

```text
## 内容特征入库结果

- 正式文件：沉淀结论/内容特征词典.csv

### 本轮范围
- 观察覆盖内容数：<active_content_count>
- 未覆盖观察条数：<observation_count>

### 候选与决定
- 候选数量：<candidate_count>
- 采纳新增：<dictionary_committed_count>
- 用户暂不采纳：<N>
- 合并到已有特征：<N>
- 仅保留为单篇观察：<N>

### 未采纳候选
- <用户暂不采纳的候选标签，逐条列出；没有就整节不出现>

### 本轮状态
- <已完成 / 未完成>
- 错误：<真实错误；无错误时不展示>
```

`用户暂不采纳`、`合并到已有特征`、`仅保留为单篇观察` 三条数字，按 `decisions` 里对应的 `action` 逐条计数；某类为 0 时照实写 0。`用户暂不采纳` 的候选标签从 `decisions` 的 `候选标签` 取，逐条列在「未采纳候选」里，没有就整节不出现——这是这些候选唯一的留存位置。

状态口径：

- `2.1` 失败时写「未完成」，且不展示任何候选结论；
- `2.3` 用户没有确认时写「未完成：等待确认，本轮没有写词典」；
- `2.4` 失败时写「未完成：词典未更新」。

在上面的固定结果反馈之后，追加下面这段，只写用户可以做的动作：

```text
本轮只更新词典，不刷新规律分析。新增的特征会先在「规律词典」里看到；等后续内容分析产生了对应的特征实例，规律分析才会带上它们。
你可以直接问我某条候选为什么建议收或不收；要改词典里的条目，直接说。
```

不得把暂存候选或未提交的词典变更说成已完成。用户看完词典明确要求改特征词典时，直接按用户要求改，改完跑一次汇总，确认没有实例指向已下架的特征：

```bash
python3 "<工作区根目录>/执行单元/内容特征汇总执行器.py" \
  --workspace-root "<工作区根目录>" \
  > /dev/null
```

把某条特征改成 `停用` 或直接删除前，先确认已经没有内容实例在引用它：直接跑一次汇总，若返回 `active_instance_invalid`，说明还有实例引用该特征，错误信息里的样本键就是需要先处理的内容；处理完再改词典、再跑一次。**汇总跑通，下架才算处置完成。**

**本流程结束后执行一次使用统计上报**（静默脚本，失败不影响任何流程）：

python3 执行单元/使用统计上报.py --kind flow --name 内容特征入库流程 --phase end --status ok
