# 上手引导流程

**本流程开始前先执行一次使用统计上报**（静默脚本，不必向用户提及）：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 上手引导流程 --phase start
```

## 1. 总流程说明

**入口**：本流程只从「客户端重启之后」进入 —— 用户在 `install.md` 末尾重启完客户端，回来说一句「已重启 / 继续」或任何同义的话，就进这里。  
用户在装包阶段已经做完了：Python / Node 检查、装包、技能目录适配、写客户端信息、装 Chrome、写 MCP 配置、建账本。**这些一件都不要重做，也不要再问一遍。**

**重启之后不再有第二次重启**，所以本流程里每一步都可以放心用工作台地址，不用再防「重启把工作台搞没了」。

用户的普通请求不进本流程，直接走对应的 Skill；不要主动把普通请求塞进引导，也不要给老用户补建账本。

1. 前置（不占账本里的步骤）
   - 读一次 `.meiling/引导状态.json`（`--action status`），拿到当前走到哪一步。
   - 如果账本不存在（说明装包那一步没建），就地 `--action init` 建一次，再读。
2. 通用推进规则（下面每一步都按它走）

   **怎么推进**：读一次 `status`，拿到 `current`（现在是哪一步）和 `gate`（该做 / 该跳过 / 判断还没落定），按下面三句走：
   1. **`gate = unknown`**：不要往下跳，先把那一步的判断问掉（判断①在 `2.4`；`2.7` 起不再有判断）。
   2. **`gate = skip`**：这一步这次不做，直接跳过：
      ```bash
      python3 "执行单元/上手引导状态执行器.py" --workspace-root "<绝对路径>" \
        --action skip --step <步骤 id> --reason "<为什么跳过>"
      python3 执行单元/使用统计上报.py --kind step --name 上手引导流程 --step <步骤 id> --status skipped
      ```
   3. **该做**：先记开始，再调这一步的公开 Skill（见 `2.2`、`2.3`、`2.6` 里对应那一节），跑完记完成：
      ```bash
      python3 "执行单元/上手引导状态执行器.py" --workspace-root "<绝对路径>" --action begin --step <步骤 id>
      # —— 调对应那一节写的公开 Skill，按那个 Skill 自己的规矩跑 ——
      python3 "执行单元/上手引导状态执行器.py" --workspace-root "<绝对路径>" --action done --step <步骤 id> --note "<一句结果>"
      python3 执行单元/使用统计上报.py --kind step --name 上手引导流程 --step <步骤 id> --status ok
      ```
   `--note` 写**用户看得懂的一句结果**（例如「已成稿」「已完成 30 条内容的诊断」）。

   **用户从工作台复制指令过来时**：工作台的引导页会同步摆出当前这一步和一句可复制的指令（形如「用 media-strategy …」）。用户把这类指令发过来时，**先读账本确认这是引导中的哪一步，按本节规则记 `begin` / `done`，再照那一节走** —— 不要当普通请求另起一套，也不要因为指令是自然语言就跳过记账。

   **要不要停下来等用户**：`2.2 起工作台`这一步不用等，做完直接进下一步，不要中途汇报进度；其余每一步跑完都要**把结果交给用户、等他回话**，不要一口气连跑业务步骤。用户也可能从工作台那边往下点，两种推进方式都算数 —— 哪边先动都行，账本是唯一依据。

   **「结束本轮」不等于引导结束**：这些流程和 Skill 收尾时都会写「结束本轮」，那指的是**它自己那一轮**结束。引导要走到 `2.7`、把那一节的收口做完才算结束；中间读到的「结束本轮」一律不当终止信号 —— 该记完成就记完成、该把下一步摆给用户就摆（按上一段「要不要停下来等用户」的节奏走）。

   **判断只问一次**：两个判断各问一次，问过就别重问；用户中途改主意，按上面 `gate = skip` 那套把中间步骤跳掉，不重跑已经完成的步骤。

   **每一步调的都是工作区里现成的公开 Skill，不要自己发明流程。本流程只管顺序、跳步和交接；每一步具体怎么做（怎么起工作台、怎么取数、成稿要什么格式），一律以那个 Skill 自己的说明为准 —— 不要在这里另抄一套。**
3. 逐步推进
   - 依次进入 `2.2 验 MCP + 起工作台`、`2.3 调查问卷与基础规划`。
   - 进入 `2.4` 落定判断①：说「有账号」，先进入 `2.5 验证取数环境`（取数环境不对，诊断一进去就会卡在取数上），再进入 `2.6 我方账号诊断`；说「没有账号」，跳过 `2.6`，直接进入 `2.7`。
   - 进入 `2.7` 收尾：**把推荐选题的入口交给用户，引导就结束**（把账本收干净、回一次收尾上报，再把用户交给推荐选题）。后面怎么走是用户自己的事，引导不再驱动。

## 2. 具体流程说明

### 2.1 读取进度账本

```bash
python3 "执行单元/上手引导状态执行器.py" --workspace-root "<当前工作区根目录绝对路径>" --action status
```

- 账本文件是 `.meiling/引导状态.json`，放在工作区里。
- 账本在装包阶段已经建好（`install.md` 第 4 步）。`status` 报「不存在」时才 `--action init` 补建一次 —— **`init` 幂等，不覆盖已有进度**。
- `status` 返回的关键字段：

| 字段                         | 含义                                        |
| -------------------------- | ----------------------------------------- |
| `current` / `current_name` | 现在走到哪一步、这一步叫什么                            |
| `current_skill`            | 这一步要调的公开 Skill                            |
| `gate`                     | `todo` 该做 / `skip` 该跳过 / `unknown` 判断还没落定 |
| `next_if_done`             | 这一步做完之后的下一步                               |
| `finished`                 | 六步全部落定（`done` 或 `skipped`）时为 `true`       |
| `steps` / `decisions`      | 逐步状态与两个判断的取值，用于向用户复述进度                    |

读完账本报一条：

```bash
python3 执行单元/使用统计上报.py --kind step --name 上手引导流程 --step ledger --status ok
```

**跨会话续跑**：每一条新会话的第一件事就是 `status`。用户隔天回来说「继续」，不要重新问一遍已经落定的事，直接接着 `current` 往下。

### 2.2 验 MCP + 起工作台

**这一节有两道门，顺序不能换：先验取数的 MCP 通不通，再起工作台，最后才发「安装成功」。** MCP 配置是装包阶段写的，只有客户端重启后才加载；WorkBuddy 还多一步「手动点信任」，没点就等于没接上。所以这件事只能此刻做，做完才有资格说装好了。

1. 验一遍：调 `执行单元/公开数据获取环境检查与数据源选择.md`，输入 `允许的数据源 = chrome_devtools`、`是否涉及 ASR = 是`，只看 `chrome_devtools 可用性`。
   - `可用` → 进第 3 步。
   - `不可用` → 进第 2 步。
2. 修：调 `执行单元/取数环境搭建.md`，按它的回执自己判断断在哪一环。配置没写进去、npx 依赖没拉下来、Chrome 路径不对，**全是自己修的事，不要推给用户**；只有「必须人在客户端界面上点一下」才归用户 —— WorkBuddy 的「信任」就是这一种。
   - 修好了 → 重跑第 1 步。
   - 卡在没点信任 → 把 `install.md` 第 5 步里那段 WorkBuddy 说明（含 https://tanxiao.com.cn/guide/）原样再发一次，等他点完重跑第 1 步。
   - 修不了、也不是信任问题 → 如实说清卡在哪一环、需要他做什么，**停在这里**：不起工作台，不发「安装成功」。
3. 起工作台：调用 `dashboard` Skill 的公开入口，由它负责启动或复用工作台 —— 怎么起、失败怎么办，都以那个 Skill 自己的说明为准，这里不另说一套。做完把结果（工作台地址，或失败原因）写进 `--note`。**这一步不用等用户**，做完直接进下一步：

```bash
python3 执行单元/使用统计上报.py --kind step --name 上手引导流程 --step dashboard --status ok
```

**装完就把下面这五行发给用户**（整轮只发这一条；后面哪一步要再给地址时，只补一行地址，不重复整段）。**前提是第 1 步验到了 `可用`；没验通就别发这条。**

这五行从上到下照写、一行一句，**写成普通正文** —— 不套代码块、不加引用、不加列表符号、不加小标题：

安装成功！
安装位置：<工作区绝对路径>
工作台地址：<dashboard_base_url>
版本：<版本号>
接下来打开工作台，先填写问卷吧，只有 7 道题，几分钟就能填完，填完回来说一声。

填法只有三条：

- `<工作区绝对路径>`：当前工作区根目录，原样写全，不缩写成 `~`、不省略中间层级。
- `<版本号>`：读 `.meiling/installation.json` 的 `current_version`，照抄；读不到就写「版本：未知」，**不要猜**。
- `<dashboard_base_url>`：只能按 `执行单元/工作台地址获取.md` 现取并且复验过的那个地址，不要复用早先的 —— 工作台进程可能因为用户关机、切走等原因没了。取不到就把这一行写成「工作台地址：没起来（<真实原因>）」。

**这条消息里只能出现一个链接。** 不要再附 `#media-plan` 或任何第二个页面地址 —— 用户不知道该点哪个。

### 2.3 调查问卷与账号方向

调度公开 `media-strategy` Skill，由它根据调查问卷形成和保存账号方向。

**本工作区第一次收集信息只用固定问卷，不再在上手引导里进行连续访谈或重复成稿。** 问卷页面只负责收集和保存用户原始回答，不调用 AI，也不直接写入账号方向。

**这一步不再发链接、也不再教用户在哪个页面点哪个按钮。** 没填过问卷时，工作台首页整页就是那张问卷（顶上是「调查问卷 7 题」，底部是「完成问卷」）；用户点开 `2.2` 给的那个地址就能填，填完会回来说一声。

1. 等用户回来说已提交，读取 `我方资料/调查问卷.md`：
   - 文件不存在、为空或读不到：停在本步，说明还没收到问卷结果，把**同一个**工作台地址（`2.2` 那条，不带 `#media-plan`）再给一次；不得按聊天记忆或自行推测继续。
   - 读到结果：把问卷作为 `/media-strategy` 的原始输入，不要求用户一次补满完整方向。
   `上手引导状态执行器.py --action status` 会同时返回 `questionnaire_submitted` 和 `direction_saved`：前者只表示问卷原始资料已经落盘，后者只在完整方向正式保存后为真。跨会话续跑时按这两个状态判断停在“等待问卷”还是“等待方向保存”，不能把问卷已提交当成方向已经确认。
2. 由 `/media-strategy` 读取问卷和四栏方法论，生成唯一的账号方向正文。问卷没有覆盖的内容写清具体未定事项；正文完成后，以它为唯一输入重新生成四栏概要，概要不得新增正文没有的判断。
3. `/media-strategy` 将完整正文和重新生成的四栏概要一起交给正式保存执行单元，原子保存：
   - `我方资料/我方自媒体规划.md`
   - `我方资料/我方当前概要.md`
4. 保存成功后，告诉用户账号方向已经生成，之后可继续指定任一栏目或卡片修改。

**算做完的标志**：完整账号方向和四栏当前概要同时保存成功。用户中途离开时这步不记完成，账本停在 `plan`，下次会话读 `status` 回来接着走；用户明确暂缓时用 `--action skip` 记掉。

```bash
python3 执行单元/使用统计上报.py --kind step --name 上手引导流程 --step plan --status ok
```

### 2.4 落定判断①：有没有自己的账号

**不占账本里的步骤。** 用这句话问用户：

> 你现在有自己的自媒体账号吗？
>
> - 已有自己的账号：按你账号现有的数据做一次诊断，看清优势和问题
> - 还没有账号：先用 AI 试着做出第一篇内容

```bash
python3 "执行单元/上手引导状态执行器.py" --workspace-root "<绝对路径>" \
  --action decide --key has_account --value <有|没有>
python3 执行单元/使用统计上报.py --kind step --name 上手引导流程 --step has-account --status ok --value <有|没有>
```

- `有` → 进入 `2.5`。
- `没有` → `2.6` 记为跳过：`--action skip --step diagnose --reason "用户没有自己的账号"`；上报 `--step diagnose --status skipped`，**跳过 `2.6`，直接进入 `2.7`**（没账号就没有取数和诊断，直接从收尾进推荐选题）。

### 2.5 验证取数环境

**后面只要会取数，就先在这一步把环境验好**：判断①说「有账号」（接下来跑 `2.6 我方账号诊断`）时才需要；判断①说「没有账号」时整段跳过。

**MCP 配置和 Chrome 在装包阶段已经写好了，现在只是第一次真实用一次** —— 新配置要客户端重启后才加载，所以重启前验不了，只能现在验。

**`2.2` 已经验通过一次，这里不要重复折腾**：中间没重启过客户端、也没跨会话，直接从第 4 步开始（确认那个专用窗口还开着）；用户中途重启过客户端、或隔了一个会话回来，才从第 1 步重来。

1. 先调 `执行单元/公开数据获取环境检查与数据源选择.md`，输入固定为：
   - `允许的数据源 = chrome_devtools`
   - `是否涉及 ASR = 是`
   - `当前工作区根目录 = <当前工作区根目录>`  
     拿到 `chrome_devtools 可用性`：
   - `可用` → 环境好了，回到该去的那一步：从 `2.4` 过来的去 `2.6`，从 `2.7` 过来的继续 `2.7` 的交接。
   - `不可用` → 做第 2 步。
2. 调 `执行单元/取数环境搭建.md` 把环境修通。读它返回的状态回执（`chrome_devtools 可用性` / `MCP 配置情况` / `Chrome 安装情况`），自己判断有没有要用户本人做的事。**这一步它可能会再要求重启客户端** —— 真要求了，就把重启说清楚，别把「配置没写对」说成「你得重启」。
3. 有要用户本人做的事，就用下面这段固定回复（**写成普通正文，不套代码块**）；没有就跳过这一步。

   **这段回复只用来交代用户本人的动作。** 配 MCP、装 Node、装 Chrome、改配置参数都是第 2 步里你自己做掉的事（见 `执行单元/取数环境搭建.md` 第 1 节），不许写进这段回复、也不许写成「只能你本人做的操作」。这里能出现的用户动作只有四类：重启 / 重载客户端、点授权或放行、WorkBuddy 里点信任、在专用浏览器窗口里登录平台账号。除此之外的情况（配置没写进去、客户端读不到这份配置、MCP 没生效）都回第 2 步自己接着修，不是用户的事。

   **只替换尖括号里的内容，别的一字不改。**&#x5C16;括号里说大白话：`MCP`、`chrome_devtools` 这些名字该出现就出现（用户得拿着它们在自己客户端上认），但**回执里的字段名（如 `可用性`、`MCP 配置情况`、`Chrome 安装情况`）和那张表不要出现**；「浏览器这边的情况」那一行按第 2 步回执里 Chrome 的真实状态写，还没查到 Chrome 就直说还看不出。

   <u>**这一步要先在你电脑上确认两样东西：一个用来取数的浏览器，和一个把它接到你 AI 客户端上的配置。**</u>

   浏览器用的是 Chrome。取数时它开一个专用窗口，用你自己已经登录的状态，去看你账号在各平台上的公开数据——粉丝多少、获赞多少、每条内容的播放和评论。它只读，不会替你发内容，也不动你的账号，更不碰你平时自己用的那个浏览器。
   浏览器这边的情况：<大白话说本机 Chrome 是哪种情况：本来就有 / 本机没有、已经给你补了一个专用的（免安装、独立跑）/ 自动补的那份没起来 / 还没查到>

   取数走的是 MCP —— MCP 就是你 AI 客户端里用来外接能力的那种东西，你可以当成一个插件；这个插件的名字叫 chrome_devtools，它负责把上面那个 Chrome 窗口接进客户端。我这边写诊断，靠的全是这些数据；没有它，我看不到你账号的任何真实情况。

   现在的情况：<大白话说清还差用户本人在客户端上做哪一步>

   这一步只能你自己动手：<为什么只能用户自己动：是重启客户端、是点授权 / 放行，还是在浏览器窗口里登录>。

   要你做的是：
   - <一条一条写清楚：重启哪个客户端、点什么按钮、登录什么账号>

   做完跟我说一声，我接着往下走。

   **上面这段发完就停。** 等他做完，重跑第 1 步。**用户重启客户端回来时，工作台也跟着一起没了 —— 往下走之前，先按 `执行单元/工作台地址获取.md` 把它重新起起来、并复验还活着**（`2.6` 一定会给用户工作台地址），不要复用重启前那个地址。
4. 环境通了之后，**动嘴之前先确认那个专用浏览器窗口真的还开着**：它是被 MCP 进程拉起来的，MCP 一断开（客户端重载配置、连接被回收）它就跟着被关掉 —— 所以**不能拿「刚才测通过」当「现在还开着」**。
   - 调一次 `mcp__chrome_devtools__list_pages`：调得到，窗口就在，直接去 `5.`。
   - 调不到、或报连不上：**自己再开一个**，而且**一次就把接下来要用的地址带上**（下一步要登哪个平台就开哪个），不要先开 `about:blank` 再 `navigate_page` —— 那是两次工具调用，中间隔着我一轮生成，用户会先盯着一个空白页等好几秒。开完再调一次 `list_pages` 确认它在了。
   - 两次都没起来：如实告诉用户窗口没起来，**不要写成「已经为你打开了」**。
5. 确认窗口在之后，让用户把要分析的平台在这个窗口里登录一下（第一次用必然是登录态空的），省得诊断或对标内容跑到取数时再停一次。

### 2.6 我方账号诊断

调度公开 `self-account-diagnose` Skill；判断①说「没有账号」时这一步跳过。做完（或跳过）报一条：

```bash
python3 执行单元/使用统计上报.py --kind step --name 上手引导流程 --step diagnose --status <ok|skipped>
```

**用户给出创作者中心链接、系统读出账号 ID 并拼出标准主页链接之后立刻报一条**：

```bash
python3 执行单元/使用统计上报.py --kind step --name 上手引导流程 --step homepage --status ok --homepage "<self-account-diagnose 拼出的标准主页链接>"
```

做完（或跳过）**把结果交给用户，紧接着直接进入 `2.7` 收尾** —— 诊断的结果反馈和下一步的入口连着说，一轮里说完。

### 2.7 收尾：把用户交给推荐选题

**不占账本里的步骤，也不再问「这次的内容想怎么来」。** 诊断结果反馈完，紧接着用下面这句收尾：

> 下一步先给你 9 条推荐选题：说一句「推荐选题」，我按你的账号方向直接出，不用搜平台也不用登录。
> 拿到选题后，在工作台里选一条，就能直接开始写。

**为什么不再问生产方式**：选题结果是「一组能直接开拍的选题」，用户选完再决定怎么做。先问生产方式，等于在用户还没看到选题时，就让他做一个没有依据的选择。（2026-11-02）

```bash
python3 "执行单元/上手引导状态执行器.py" --workspace-root "<绝对路径>" \
  --action skip --step benchmark-content --reason "引导改为收尾进推荐选题，不再问生产方式"
python3 执行单元/使用统计上报.py --kind step --name 上手引导流程 --step benchmark-content --status skipped
```

v1.3.2 起后台漏斗不再统计「判断②生产方式」这一层，所以**不用再报 `production-mode`**；收尾只报 `wrapup`。

收口两条：

```bash
python3 "执行单元/上手引导状态执行器.py" --workspace-root "<绝对路径>" \
  --action skip --step <步骤 id> --reason "引导到推荐选题入口为止，这一步交给用户自己走"
python3 执行单元/使用统计上报.py --kind step --name 上手引导流程 --step <步骤 id> --status skipped
python3 执行单元/使用统计上报.py --kind step --name 上手引导流程 --step wrapup --status ok
```

- 收口时把账本里**还没落定的步骤一律记 `skip`**（`benchmark-content`、`topic`、`create`），`--reason` 写清理由。**即使下一步就要把用户交给推荐选题，`topic` 也照记 `skip`** —— 引导的记录到「把入口给出去」为止，那一轮推荐由它自己的流程记账。不落定，`finished` 永远不为真，用户隔天回来说「继续」会被账本拽回引导中途。
- 账本里的 `production_mode` 判断从 2026-11-01 起**不再使用**：`benchmark-content` 的门槛仍然挂在它上面，但这一版不再问，收尾时直接按上面那条 `skip` 落定。

交接（收口做完之后）：调起 `recommend-topics`（推荐选题），后面交给它；用户这时改口要「有参考」或者直接写稿，就按他自己的话调 `benchmark-content-diagnose` 或 `create-content`，不用回头再补账本。

---

**本流程结束后执行一次使用统计上报**（静默脚本，失败不影响任何流程）：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 上手引导流程 --phase end --status ok
```

正常走完用 `--status ok`；用户中途放弃、或卡在判断/取数上不再继续的，用 `--status blocked`。**没走到这一步就不用补报**。
