# 推荐选题流程

**本流程开始前先执行一次使用统计上报**（静默脚本，失败不影响任何流程，也不必向用户提及）：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 推荐选题流程 --phase start
```

## 1. 总流程说明

1. 读账号方向：进入 `2.1`。
2. 读历史内容库，判断已有方向和不能重复的题：进入 `2.2`。
3. 按「场景 × 问题 × 产物」一次生成 9 条选题：进入 `2.3`。
4. 校验并保存为工作台可读的正式结果：进入 `2.4`。
5. 只回报结果落点和下一步入口：进入 `2.5`。

本流程不读取调查问卷、已发文案、对标内容、账号诊断，也不搜索平台、不登录任何账号、不发起取数。

## 2. 具体流程说明

### 2.1 读取账号方向（必需）

读取 `<当前工作区根目录>/我方资料/我方自媒体规划.md`，取出四类信息：

- `2. 用户与需求` 下的每个「用户群体」：名称、用户是谁、需求情境、问题与影响、期望结果；
- `3. 产品与变现` 下的「具体交付」：名称、适用人群与用途；没有具体交付时记下当前的变现选择；
- `4. 账号与内容` 下的「账号任务」「账号定位」和每条「内容主线」：讲什么、主要交付；
- `哪些内容不做`：生成选题时主动避开。

规划不存在、读不到、四栏为空，或没有可用的用户群体与内容主线时，停止本流程，用一句话告诉用户缺哪一块、需要先补「账号方向」；不要用问卷、旧概要、聊天记录或常识替代规划，也不要先推荐再让用户改。

本步还要把用户日常要做的事拆成 3—6 个具体工作步骤（如找资料、看对标、定选题、写稿、剪辑、出镜、发布、复盘）。拆不出具体步骤时，停止并说明规划缺哪一块，不要用「效率低」「工具太多」这种抽象痛点代替。

### 2.2 读取历史内容库（方向参考和去重）

读取 `<当前工作区根目录>/我方资料/我方内容库.csv`，只取四列：

- `选题名称`、`标题`：归纳账号已经做过的方向；
- `媒介形式`、`当前状态`：判断哪些方向是持续在做的。

把标题和选题名称归纳成 3—6 个**场景类别**（如账号拆解、选题、写稿、剪辑、出镜与数字人、生图与视频生成、工作台搭建等）。只归纳类别，不抄标题、不写内容 ID、不读文案，也不引用里面的数据、效果、客户反馈和结论。

历史内容库不存在、读不到或为空时，**不停止流程**：只用账号定位和内容主线推导可讲的场景类别，并在结果里注明「没有历史内容可参考」。不要用其他账号或平台热点替代。

另外做两件只用于去重的事，不参与方向判断：

- `我方资料/选题库.csv` 的 `选题名称`；
- `我方资料/选题分析/` 下的文件名。

已有的题不再推荐，也不要只换标题再报一次。

本步只读，不改任何文件。

### 2.3 生成 9 条选题

按 `提示词/推荐选题成稿提示词.md` 生成恰好 9 条。

每条选题都必须是同一个公式的结果：**一个具体工作场景 × 一个具体问题 × 一个账号能交付的产物。**

- **场景**来自 2.1 拆出的工作步骤，不能是「AI 工具」「内容创作」这种大类；
- **问题**对应用户在这一步真实卡住的地方，不是行业概念；
- **产物**来自规划里的内容主线 `主要交付` 或现有资源，必须能看见（工具、演示、模板、清单、判断）；
- **工具或方案类别**落在 2.2 归纳出的场景类别内；范围外的不自己加。

**以下内容不能成为选题方向**（除非账号定位本身就是教人做这些）：

- 账号自己的经营动作：定价、报价、合同、交付范围、售后、答疑、接单排期、技术路线取舍；
- 泛 AI 资讯、工具参数测评、纯流量玩法、纯视觉娱乐（同时受 `哪些内容不做` 约束）。

`3. 产品与变现`、`现实约束` 是账号背景，不是内容方向；它们可以解释「为什么这样做」，不能直接变成一条选题。

历史内容库的用法：

- 优先在历史已经占住的方向里往深做；
- 历史里反复出现但只讲了浅层的场景，可以换问题、换产物再讲一次；
- 历史里没出现、但定位和主线明确允许的场景，可以推荐，但必须说得出是从哪条定位或主线推出来的；
- 不引用历史内容里的数据、效果和结论，也不写内容 ID。

其余硬性要求：

- 每条都写全六个要素（主题、目标用户、核心痛点、收益承诺、核心命题、切口），口径和「选题分析」一致，不自己换说法；
- 每条都指向规划里的一个真实用户群体和一个具体工作场景；标题只写这条内容讲什么——8—20 字的名词短语，不带判断、角度、反问、话题标签和作者名，判断放 `proposition`、切口放 `angle`；
- 9 条切口互不重复，不把同一个意思换几种说法凑数；
- `mainline` 用规划里的原名称，且这条主线有具体场景或真实素材支撑；哪条主线找不到场景和素材，不硬凑，把名额让给有场景的主线；
- `basis` 写清这条题的判断依据：规划里的哪个用户群体、哪个具体工作场景、规划里的哪条内容主线；可以补一句「延续账号已有的某类方向」，但不得引用问卷、历史内容标题、已发内容、已发文案或 `内容0xx` 这类内部 ID；
- 只写当前账号方向能交付的内容，不编造案例、数据、价格、效果承诺；
- 不写规划里明确不做的话题；
- 每条都能单独做成一篇内容，不写成需要连更的系列；
- 顺序按「先能被目标用户点开、再能建立信任、最后能承接产品」排，不按写作难度排。

选题只用于工作台展示和后续创作，不在本轮建立选题分析记录，也不启动内容生产。

### 2.4 保存正式结果

把 9 条选题按下面的结构写成 JSON，通过 heredoc 作为标准输入交给保存执行器：

```json
{
  "schema": "meiling-recommended-topics/1",
  "plan_path": "我方资料/我方自媒体规划.md",
  "topics": [
    {
      "rank": 1,
      "title": "选题标题",
      "theme": "这个题主要讨论哪一类问题",
      "audience": "规划里的用户群体名称 + 具体是谁",
      "pain": "这群人当前卡在哪里",
      "promise": "看完最有希望得到什么结果",
      "proposition": "这条内容最终希望用户相信什么",
      "angle": "从哪个具体角度进入，一句话",
      "mainline": "规划里的内容主线名称",
      "goal": "流量",
      "basis": "依据：规划里的用户群体 + 具体工作场景 + 内容主线",
      "outline": ["第 1 个内容点", "第 2 个内容点", "第 3 个内容点"]
    }
  ]
}
```

- `rank` 必须是 1—9 且不重复；`goal` 只能是 `流量`、`涨粉`、`交易` 之一；`outline` 写 3—5 条；`basis` 不超过 80 字，且不许出现 `内容0xx` 这类内部 ID。
- 保存命令（9 条 JSON 原样写进 heredoc，不要先写到别的文件再重定向）：

```bash
python3 "<当前工作区根目录>/执行单元/保存推荐选题.py" \
  --workspace-root "<当前工作区根目录>" <<'JSON'
{
  "schema": "meiling-recommended-topics/1",
  "plan_path": "我方资料/我方自媒体规划.md",
  "topics": ["……9 条……"]
}
JSON
```

只接受返回 `ok=true、status=committed、count=9`。返回其他结果时说明真实错误并停止，不手工改产物绕过。

保存器会在 `我方资料/推荐选题/` 下写两份同内容的结果：

- `推荐选题结果.json`：工作台读的正式结果；
- `推荐选题结果.md`：同样内容的文档版，给人看。

### 2.5 反馈结果

只回一句：已生成 9 条选题，回工作台的「推荐选题」查看，文档在 `我方资料/推荐选题/推荐选题结果.md`。不要说选题清单，不要重复每条的标题和角度，不要追问先做哪一条，也不要自动开始写内容或做选题分析。

流程结束前执行一次收尾上报：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 推荐选题流程 --phase end --status ok
```
