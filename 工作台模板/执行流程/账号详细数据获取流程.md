# 账号详细数据获取流程

**本流程开始前先执行一次使用统计上报**（静默脚本，失败不影响任何流程，也不必向用户提及）：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 账号详细数据获取流程 --phase start
```

## 1. 总流程说明

1. 前置确认
   - 进入 `2.1 入口判断与承接基础数据结果`。
   - 进入 `2.2 按配置锁定本轮内容 ID 清单`；直接从设置读取默认范围，不再要求用户确认。
2. 获取详细数据
   - 进入 `2.3 按已选数据源获取并补全内容明细`。
   - 只有整条内容没有任何有效归属证据时，才进入 `2.4 对失败内容执行一次同源重试`；互动字段缺失统一记录为 `0`，不因单个指标为空重跑整条内容。
   - 重试后仍有失败内容时，按最终 canonical report 状态自动分流：`completed`／`partial` 带缺口继续，`failed` 直接作为本轮失败结果结束；不再等待用户选择。
3. 处理可用内容
   - 依次进入 `2.5 计算衍生字段`、`2.6 执行固定后续处理`。
4. 特征落表（实例 + 观察）
   - 进入 `2.7 特征落表（实例 + 观察）`。
5. 确认交接并进入详细分析
   - 进入 `2.8 确认详细数据交接并进入账号详细分析`；由程序读取最终 canonical report 并执行状态分流。
   - 根据最终 canonical report 的状态决定是否交接：`completed` 或 `partial` 继续交接，`failed` 停止并反馈真实失败原因。

## 2. 具体流程说明

### 2.1 入口判断与承接基础数据结果

本流程有两种调用来源：

1. **基础数据自动交接（主链路默认）**：沿用基础流程唯一确认的账号和已锁定的数据源；范围由设置默认值直接确定。
2. **用户独立进入**：先确认唯一账号，再从基础建档报告恢复数据源；无法恢复时停止，要求从基础数据阶段重新开始，不在本流程内自行跳转。

固定承接：

- `对标资料/对标账号库.csv` 中当前账号记录；
- 当前账号的 `内容列表.csv`；
- `对标资料/对标内容库.csv`；
- 账号记录和本轮上下文中已确认的 `基础数据获取方式`。

账号库、内容列表或内容库任一正式文件不存在、不可读，或内容列表没有至少一条有效 `内容ID` 时，按基础数据流程的正式报告和脚本错误规则停止；不得跳回或跳过基础数据阶段。修复后仍从固定顺序重新开始本阶段。

**批次上下文创建**：`run_id` 由基础数据流程创建，本流程只原样复用，不得新建或改写。确定账号后，由本流程创建本轮批次上下文，固定路径为：

```text
.meiling/staging/benchmark-account-diagnose/<run_id>/detail-data/批次上下文.json
```

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --action init-batch \
  --account-id "<账号ID>" \
  --content-list "<当前工作区根目录绝对路径>/<当前账号内容列表.csv 相对路径>" \
  --content-library "<当前工作区根目录绝对路径>/对标资料/对标内容库.csv" \
  --data-source "<chrome_devtools 或 justoneapi>"
```

- 账号和两份 CSV 路径取自正式账号库；`data_source` 取自 `本轮账号基础建档结果.json` 的顶层 `data_source`（兼容账号记录中的 `基础数据获取方式`）。
- 创建后由 `2.2` 一次性锁定内容清单并写入 `confirmed = true`；账号、路径和数据源均由批次上下文提供。
- 上下文缺失、不可解析或账号不一致时，执行器会返回 `run_id_context_missing` 或身份错误。此时停止并说明真实原因，不得按目录名或模型记忆编造 `run_id`，也不得扫描 `staging` 目录自行恢复其他批次。

本流程只接受基础流程已经锁定的 `chrome_devtools` 或 `justoneapi`。不得重新执行环境选择、不得默认换源、不得重新获取基础资料。来源无法恢复时停止并向用户说明，修复后仍按五阶段顺序继续。

### 2.2 按配置锁定本轮内容 ID 清单

本轮不再向用户确认范围。按以下优先级直接确定：

1. 用户本轮明确指定了条数、内容 ID 或「全部内容」时，使用用户本次要求；
2. 否则读取 `本地配置.txt` 的 `BENCHMARK_ACCOUNT_DETAIL_LIMIT`（留空、非法或不在 `1`—`500` 内时按默认 `20`），取最近 N 条。

用一次调用同时准备并确认清单：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --prepare-content-scope --confirm-content-scope
```

- 不传 `--scope-mode / --scope-count` 时，执行器自动读取配置并使用 `latest` 模式，回执 `scope_source = config_default`。
- 用户本次明确要求时，追加对应参数：指定条数或「最近 N 条」用 `--scope-mode latest --scope-count N`；「前 N 条」用 `--scope-mode list_order --scope-count N`；指定内容 ID 用 `--scope-mode custom --content-ids`；明确要求「账号全部有效内容」时才用 `--scope-mode all`。
- `--scope-mode all` 会把已完整的内容整体重采，只有用户明确要求时才使用。
- 清单为空时，说明原因并停止；内容 ID 是否存在、是否属于当前账号、路径和必需字段是否合法，由执行器检查。

**执行边界**

- 后续步骤只能使用已锁定的清单；AI 不得扩大、缩小、手工筛选、补入、删除或重排其中的内容 ID。重试时也不修改原始清单，由执行器根据其中的成功项生成后续处理范围；原始清单和失败项仍保留供追溯。
- 清单锁定后，继承基础阶段已确认的数据源；不得重新执行环境检查、重复获取基础数据或自动切换数据源。
- 对标账号详细分析使用本轮基础清单内的全部内容基础字段；正文、封面、视频文案等详细证据只使用本次锁定的范围。AI 不得自行扩大或缩小。

### 2.3 补全内容明细

**作用**：按锁定清单补全公开明细字段，并由脚本统一验收和回写。明细字段（互动数、发布时间、视频地址）会随时间变化 —— `chrome_devtools` 分支对清单内内容**整体重采**，不因库中已有而跳过；`justoneapi` 分支只为仍缺失的字段发起请求（按条计费）。正文、封面图和视频文案等不随时间变化的产物，一律只补缺、已有即复用。

本轮沿用基础阶段已经选择的数据源。用户先选数据源，流程中 Chrome 和 JustOneAPI 不得自动切换；需要改源时，停止并取得用户明确同意后回到基础数据流程处理。

**`justoneapi` 分支**按以下顺序复用已有数据（因此只对仍缺失的字段产生计费请求）：

1. 当前账号 `内容列表.csv` 已有的明细字段；
2. `对标资料/对标内容库.csv` 中同一 `平台 + 账号ID + 内容ID` 的字段；
3. 当前内容目录中稳定落盘的 `内容基础结构化数据.json`。

已有正式字段能够补齐时，不再调用外部接口覆盖。**`chrome_devtools` 分支不适用本段**，按下一节的口径整体重采。账号过程目录中的临时调试文件，例如 `MCP明细结果.json`、`明细预抓取结果.json`，不能作为默认输入。

#### `chrome_devtools`

使用 Chrome（`data_source = chrome_devtools`）时，在同一 Chrome 会话中按以下步骤执行。页面取数遵循有界探索与方法复用规则；批处理器负责计划、模板、整批结果和正式写入的校验。

**取数口径**：对锁定清单内的**每一条**内容整体重采明细字段，不因库里已有而跳过，也不做字段级的部分取数 —— 库中已有值可能是旧值（同一账号实测互动数可差一倍）。取数条数等于清单条数，耗时可随条数线性增长。

##### 准备批次

先由批次上下文根据已确认的 `本轮内容ID清单` 生成并锁定 Chrome 批次计划：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --action prepare-chrome
```

只读取该动作返回的本轮计划、结果模板、schema 和唯一整批结果路径；计划中的目标、顺序、身份和输出位置均已锁定。

##### 采集内容

- 本批页面取数严格执行 `执行单元/Chrome内容详情取数协议.md` 的**账号批处理 item 模式**；首个成功完成完整探索的内容冻结当前 AI/Chrome 会话的方法。
- 首条目标失败时，按模板写入失败 item，不得视为方法已冻结；后续目标继续寻找首个成功探索项。
- 后续内容导航到目标页面后，先按协议校验身份，再复用已冻结的方法；不重新 `list_network_requests`、不重新搜索响应式对象、不重新试探 DOM。
- 固定方法返回缺字段、ID 不匹配或结构校验失败时，才允许该目标按协议重新进行一次有界探索；仍失败时，记录真实失败原因和缺失字段，不得猜值或无限探索。
- `request_url` 必须是当前地址栏的真实 URL，`observed_content_identity` 必须从当前已加载页面的 DOM、内嵌数据或平台内容对象提取；两者不得复制计划中的预期值。
- 每个目标无论成功或失败都必须按模板写入唯一 `Chrome整批结果JSON`；不得跳过、补入、替换或重排目标，也不得直接回写正式 CSV。

##### 提交与收集

采集结束后，使用同一个 `<本轮运行标识>` 提交批次：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --action commit-chrome
```

`commit-chrome` 统一校验计划、结果条目、内容身份和工作区路径；身份失败只拒绝当前条并进入重试清单，同批其他通过项继续提交。提交成功后，执行器写入内容结构化数据并合并已取得字段到两份正式 CSV。

随后运行批次收集动作，生成本轮 canonical report：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --action collect-details
```

#### `justoneapi`

直接执行同一批次收集动作：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --action collect-details
```

脚本只为缺失字段发起 JustOneAPI 请求，随后标准化数据、回写两份 CSV 并生成明细报告。

#### 提交时的并发冲突

`commit-chrome` 与 `collect-details` 在写回两份 CSV 前会校验共享表有没有被别的会话改过。报  
`concurrent source change: <路径>` 时，按 `执行单元/并发冲突处置.md` 处置：

- **本轮尚无正式写入**：等待共享文件稳定（`对标资料/对标内容库.csv` 与当前账号的 `内容列表.csv`）后，  
  原样重跑同一步骤，最多两轮。执行器会重新读取共享表再合并已经取得的明细，**不需要重跑任何取数**；
- **本轮已有正式写入，或其他任何错误**：停止并如实报告。

两条分支通过批次边界校验后，写入已取得的明细字段并生成本轮 canonical report；后续步骤只读取这份报告，不再用额外资格列表作为流程门禁。首次采集返回 `retry_required = true` 时，必须先进入 `2.4`，不得进入 `2.5`～`2.8`。

### 2.4 失败内容重试

#### 读取重试结果

- 只读取首次收集动作返回的 `retry_required` 和 `retry_content_ids`（失败内容的 ID 清单，用于向用户说明哪些成功、哪些失败；`retry_content_ids` 同时会写入本轮 canonical report）。
- `retry_required = false` 时跳过本步骤，进入 `2.5`；`retry_required = true` 时进入一次同源重试。`retry_required` 属于本轮动作结果，不新增 canonical report 字段。
- 失败内容清单只用于说明和展示，不作为下游门禁；重试范围由执行器自行判定。

#### 执行一次同源重试

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --action retry
```

- 执行器从本轮批次上下文读取失败范围、上一轮报告与输出路径，只重试首次结果中列出的失败内容，不重跑成功项；AI 不传路径、不手工合并两轮结果。
- Chrome 重试仍按 `2.3` 的 prepare、采集、commit、collect 链路处理失败项；JustOneAPI 直接重跑明细收集。
- 未经用户明确同意，不得切换数据源，也不得把公开补采结果覆盖到后台详情字段。

#### 重试后分支

不再要求用户选择处理方式；按最终 canonical report 状态自动分流：

- **`completed`**：全部内容取得，直接进入 `2.5`。
- **`partial`**：仍有内容缺失，但不阻断分析。保留原始锁定清单和失败记录，由执行器根据成功项生成后续处理范围，继续进入 `2.5`；最终结果必须说明哪些内容没有拿到、缺了什么。
- **`failed`**：没有可继续分析的有效交付，直接作为本轮失败结果结束，说明真实失败原因和已成功范围；不进入 `2.5`～`2.8`，也不生成详细分析。

这里的“失败”只表示某些内容的详细资料没有拿到，不表示整个平台账号失效。已经成功取得的内容仍然有效；失败内容不能补写成成功，也不能在没有说明的情况下从本轮结果中消失。未经用户明确同意，不得切换数据源。

### 2.5 计算衍生字段

**作用**：基于已提交的正式明细，计算并回写 `核心互动数`、`数据水平` 和 `发布时间区间`。

#### 执行

- 处理范围由执行器按已锁定批次上下文自行判定，流程不预先筛出可计算内容，也不使用资格列表作为门禁。
- 账号、两份正式 CSV、内容 ID 和报告路径均由已锁定批次上下文读取，模型不得另行拼接或覆盖。
- 可计算内容为空时执行器返回 `derived_fields_skipped`，此时直接进入 `2.6`，不视为失败。

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号内容明细补全批处理.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --run-id "<本轮运行标识>" \
  --action calculate-derived
```

#### 结果边界

- 执行器仅处理可计算范围，回写两份正式 CSV，并返回本轮衍生字段报告。
- 单条字段不足或计算失败只记录为降级；基础明细已落盘不因衍生字段缺失而回滚或阻断 `2.6`。

### 2.6 执行固定后续处理

**作用**：通过一次批处理补齐封面和视频文案，并完成收尾。

#### 处理规则

- 处理范围由执行器按已锁定批次上下文和正式 CSV 自行判定（封面批次只取缺失封面的内容，视频文案只取需要转写的视频），流程不预先筛范围，也不使用资格列表作为门禁；流程只读取正式 CSV 和本轮已提交的结构化详情。单条失败不阻断其他内容，封面或视频文案缺口统一写入最终报告。
- **封面**：已有可读封面时直接复用；缺失时根据 `封面图原链接` 下载，并在成功后回写两份正式 CSV 的封面路径。缺少链接或下载失败时记录真实缺口。
- **视频文案**：正文证据按 `formal_transcript > platform_caption > asr > unavailable` 选择。先消费本轮可验证的平台字幕；只有字幕不可用且存在有效视频 URL 时，才逐条调用本地 `获取视频文案执行器.py`，由它读取 `本地配置.txt` 执行本地 ASR。同一内容最多尝试 3 次（首次 + 两次重试），且只对可恢复失败重试；鉴权失败、资源未授权（如状态码 `45000030`）和参数错误立即失败，不换模型、不换服务、不自动切换资源。
- 图文、未知、空媒介和其他非视频内容跳过视频文案；视频缺少 `http(s)` URL 时记录“视频缺少视频下载链接”。视频文案只使用已锁定数据源取得且经校验可访问的视频 URL。
- 本地 ASR 配置缺失、URL 失败或空转写都记录真实失败，不伪装成已完成；失败只影响对应内容，保留在最终报告的缺口中。失败原因必须写明服务端返回的真实状态码与原始消息（例如 `45000030 requested resource not granted`），并保留请求 ID 与日志 ID，便于复核或提工单；不得用笼统的 HTTP 状态描述代替。

#### 执行步骤

1. **执行** **`process`**：由执行器内部批量处理封面、准备平台字幕，并对缺少正文的公开视频逐条调用本地正文执行器。
   ```bash
   python3 "<当前工作区根目录>/执行单元/账号后续详细处理批处理.py" \
     --workspace-root <当前工作区根目录的绝对路径> \
     --run-id <本轮运行标识> \
     --action process
   ```
2. **按** **`process`** **结果分支**：本地 ASR 已在 `process` 内完成。`next_action` 只有下列三种取值，必须逐个对应处理：
   | `next_action`                     | 触发条件                             | 本步骤的处理                                     |
   | --------------------------------- | -------------------------------- | ------------------------------------------ |
   | `finalize`                        | 正文处理完成                           | 执行第 3 步 `finalize`                         |
   | `continue_detail_flow`            | 本轮没有需要本地转写的视频                    | 执行第 3 步 `finalize`                         |
   | `retry_or_review`                 | 本轮 canonical report 状态为 `failed` | 停止，按 `2.8` 的 `failed` 分支说明真实失败原因；不得按正常交接继续 |
   | 出现上表之外的取值时，停止并如实报告返回值，不得自行猜测处理方式。 |                                  |                                            |
3. **执行** **`finalize`**：在第 2 步返回 `finalize` 或 `continue_detail_flow` 时执行，校验最终 canonical report 后再进入 `2.7 特征落表（实例 + 观察）`。`finalize` 的返回值按两档处理：
   - `continue_detail_flow`：本轮详细数据交付完成，进入 `2.7 特征落表（实例 + 观察）`。
   - `retry_or_review`：停止并说明真实原因，不得把本轮描述为已完成。  
     出现这两种之外的取值时，停止并如实报告返回值。


AI 不得手工回写内容文件、CSV 或重组处理结果，只读取执行器返回的 canonical report。

### 2.7 特征落表（实例 + 观察）

#### 处理规则

- **范围只认 `2.2` 锁定的清单**：待落表内容由 `--action plan` 按批次上下文里的 `selected_content_ids` 算出，AI 不得增删；`skipped` 会连原因一起返回，不要逐条去试。
- **只写两张表**：候选第 1、2 节写 `沉淀结论/内容特征实例.csv`，第 3 节「待补充标签」写 `沉淀结论/内容特征观察表.csv`。
- **不再产 `内容画像与特征卡.md`**（2026-09-27 退役）：候选本身就是结构化的，直接落表。

#### 执行步骤

**1) 取本轮待落表清单**（分批：每批最多 5 条）：

```bash
python3 "<工作区根目录>/执行单元/内容特征落表执行器.py" \
  --workspace-root "<工作区根目录>" \
  --source 对标内容 \
  --action plan \
  --run-id "<本轮运行标识>" \
  --limit 5
```

返回里的 `pending` 是**本批**要落表的内容（各带标题与 `evidence_path`）；`candidate_dir` 与 `candidate_naming` 指出候选该写到哪、怎么命名；`pending_total` 是本轮待落表总数，`remaining_count` 是这批之后还剩几条。**下面的 `commit` 必须用同一个 `--limit`**——两个动作各自按"最前面 N 条"算同一批，值不一致就会把没写候选的条目录成 `candidate_missing`。

**2) 生成本批候选**：对 `pending` 里每一条，按它的 `evidence_path` 读原文，用 `提示词/内容特征提取提示词.md` 生成一份候选，写进 `candidate_dir`，文件名用 `candidate_naming`（即 `<内容ID>-特征候选.md`）。**一次生成整批（本批最多 5 条），不要逐条调用执行器，也不要多写下一批的候选。**

**3) 本批落表**：

```bash
python3 "<工作区根目录>/执行单元/内容特征落表执行器.py" \
  --workspace-root "<工作区根目录>" \
  --source 对标内容 \
  --action commit \
  --run-id "<本轮运行标识>" \
  --limit 5
```

一次调用完成本批的校验与落表。按 `batch`（`committed` / `failed` / `skipped`）与 `items` 逐条反馈；`status = partial` 表示有失败项，逐条原因照实说明；单条失败不影响其他内容，也不要把它说成整批失败。**`remaining_count > 0` 就回到 1) 取下一批**（已落表的条目下一轮自动以 `already_has_features` 跳过，所以循环可续、幂等）；`= 0` 才算整轮跑完。

### 2.8 确认详细数据交接并进入账号详细分析

**作用**：只读取 2.6 或 2.7 生成的最终 canonical report，并按正式状态自动交接到账号详细分析流程；本步骤不再次生成或写入报告。

#### 交接判断规则

- 明细补全、衍生字段和后续处理均由各自执行器负责验收和回写；本步骤只消费最终 canonical report，不重复逐字段验收或手工汇总各步骤结果。
- 阶段状态只能是 `completed`、`partial` 或 `failed`；资料缺口统一通过 canonical report 的 `missing_deliverables` 和逐条事实表达，内容列表完整性沿用基础数据报告，不在本阶段新增第二套字段。
- 非阻断的逐字段缺口（目前为 `标题`、`发布时间`）同样写入对应内容的 `missing_deliverables`，该内容据此判为 `partial`。这是有意的：缺口必须在最终报告里可见，不能被 finalize 静默抹掉，也不能因此把整条内容判为失败。下游详细分析必须读取这些标签并写进判断边界。
- canonical report 的 `missing_deliverables` 分两层，格式和读者不同，不得混用：**顶层**是**人可读的句子列表**，每条形如 `「<内容标题>」缺<产物/字段>、<产物/字段>`（标题缺失时退回内容 ID），只回答"本轮哪些内容缺了什么"；**逐条** `detail_collection.items[]` 是机器事实（`content_id` + 缺口标签数组）。需要按内容取交付状态时，一律读**逐条事实**，不要解析顶层句子；也不要再往顶层写入 `{content_id, items}` 对象或内部内容 ID。
- 公开流程只使用 `<本轮运行标识>` 作为批次句柄；工作区内产物路径使用相对路径，模型不得生成或传递调度器内部身份、版本或工作区注册字段。
- `<账号目录>/过程记录/当前阶段状态.json` 由本流程的收集动作（`--action collect-details`）写入：阶段名固定为 `账号详细数据获取`（对标链路名，**不得写成我方链路的 `我方账号详细数据获取`**）、`当前是否完成` 恒为 `false`；`2.6` 的 `process`、`finalize` 和本步骤都不写入或更新它。进入账号详细分析后，该文件由《账号详细分析流程》的 `2.5` 改写为详细分析阶段。

#### 自动交接与失败分支

- `completed` 或 `partial`：确认最终 canonical report 后，进入 `账号详细分析流程.md` 的 `2.1 判断分析起点`。详细分析流程负责解释其中的资料缺口及其对结论的影响。
- `failed`：不进入账号详细分析。向用户说明真实失败原因、已成功范围和仍缺失的交付项；不得把部分结果描述为完整完成。
- 正常交接时不单独展示取数阶段的中间回执；完整结论、资料边界和信息不足项由账号详细分析流程完成后统一反馈。
