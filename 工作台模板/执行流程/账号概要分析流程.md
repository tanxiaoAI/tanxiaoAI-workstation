# 账号概要分析流程

**本流程开始前先执行一次使用统计上报**（静默脚本，失败不影响任何流程，也不必向用户提及）：

```bash
python3 执行单元/使用统计上报.py --kind flow --name 账号概要分析流程 --phase start
```

## 1. 总流程说明

1. 判断入口
   - 进入 `2.1 接收分析入口并确定目标账号`，接收基础数据自动交接或用户独立进入，并使用正式账号库定位唯一账号；两类入口都必须重新读取正式账号资料。
   - 直接查看已有 `概要分析.md` 属于只读分支，不进入候选生成和正式写入步骤。
2. 检查资料并确定本轮边界
   - 进入 `2.2 检查资料`，检查内容列表、图片、人工先验说明和我方当前概要的可用性，明确可分析范围与必须保守处理的缺口。
   - 必要资料缺失时立即停止；允许带缺口继续的资料，必须连同其影响一并传入后续分析。
3. 构建概要证据并生成候选稿
   - 进入 `2.3 组装输入`，在本轮独立临时目录内生成已校验的概要证据输入。
   - 再进入 `2.4 生成概要分析候选稿`，读取本地分析框架、概要提示词和该证据输入，一次生成完整候选稿；候选稿仅是正式化输入，不是正式报告。
4. 校验并正式提交
   - 进入 `2.5 正式写入`，由本地正式化执行器校验候选稿、账号身份和证据清单，并原子写入正式概要报告、账号库和阶段状态。
   - 正式写入报 `source_hash_mismatch` 时，按 `2.5` 的「`source_hash_mismatch` 的归因与处置」处理：属外部会话改动且本轮尚无正式写入时，等待共享文件稳定后自动重试；其余情况停止并如实报告。
   - 只有执行器返回成功，且返回的正式概要报告真实存在且非空，才算概要分析完成；候选文件、临时文件或半套写入均不得视为完成。
5. 反馈结果并结束本轮
   - 进入 `2.6 反馈结果`，展示正式概要判断、最关键理由、适配情况、资料边界和报告位置。
   - 本流程是独立初筛入口，不属于对标账号一键分析主链路；主链路默认直接从基础数据进入详细数据，不经过概要。
   - 结果反馈后可以提供“看看如何融入自己的账号规划”等后续入口，但本流程不自动取得详细数据。

每次运行使用独立临时目录，临时目录只保存本轮传递给下一步的证据和候选稿，不是正式业务状态。正式报告、账号库和阶段状态只允许由 `账号概要分析正式化执行器.py` 统一提交；执行器失败时不得把临时结果反馈为正式完成。

## 2. 具体流程说明

### 2.1 接收分析入口并确定目标账号

所有概要分析请求都进入同一个入口。入口只接收用于定位账号和确认分析意图的机器信息，来源可以不同：

```yaml
platform: <平台，可为空>
account_id: <账号ID，可为空>
account_name: <账号昵称，可为空>
homepage_url: <主页链接，可为空>
intent: <summary_analysis|reanalyze，默认 summary_analysis>
base_handoff: <基础数据流程正式建档回执中的对象；自动交接时必填，用户独立进入时省略>
```

入口处理规则：

1. **基础数据自动交接**：接收《账号基础数据获取流程.md》2.7 传入的 `base_handoff`。只有 `status = ready` 且 `platform / account_id` 非空时，才使用这两个字段定位账号；不向用户重复确认，也不读取临时文件或候选文件。自动交接表示基础数据刚完成本轮建档，即使账号已有旧的 `概要分析.md`，本轮也必须重新生成概要，不得进入只读分支。
2. **用户独立进入**：使用用户已确认的账号 ID、平台、昵称或主页链接，在 `对标资料/对标账号库.csv` 中定位唯一账号；定位后与自动交接使用同一套正式资料检查。
3. **重新生成概要**：用户明确说“重新生成概要”或“重新分析”时，将 `intent` 设为 `reanalyze`；只重新读取当前正式资料并新建本轮临时目录，不重新抓取平台数据，也不复用历史临时文件。用户未明确要求重新生成时使用 `summary_analysis`。
4. 账号信息不足或匹配到多条记录时，只在用户独立进入场景中追问定位唯一账号所需的信息；不得替用户选择。自动交接的账号身份与正式账号库不一致或账号尚未建档时，说明真实错误并停止；本流程不得自行执行基础数据获取。
5. 仅**用户独立进入**且 `intent = summary_analysis`、账号库记录指向可读的正式 `概要分析.md` 时，才作为只读分支，告知用户可查看、看看如何融入自己的账号规划、重新生成或结束；不进入 2.2—2.5。用户选择“看看如何融入自己的账号规划”时，沿用已唯一确认的账号和该正式 `概要分析.md` 路径，进入 `执行流程/自媒体规划分析流程.md` 的 `benchmark_inspiration` 模式。自动交接不适用此只读规则。不得读取兼容快照中的“下一步流程”，也不得据此提供或隐藏业务入口。

`base_handoff` 只用于确认基础建档已允许交接及定位唯一账号，不携带分析证据，也不决定分析意图。2.1 只保留唯一账号身份和当前账号库行，用于判断已有报告；内容列表、正式建档报告、图片材料、人工先验和分析所需字段均在 2.2、2.3 按需重新读取。不得信任交接对象中复制的路径、统计值或资料状态。

### 2.2 检查资料

固定检查：

- `内容列表.csv` 是否至少有 `1` 条有效内容
- `图片说明路径` 下是否有可读图片
- `人工先验说明.md` 是否可读、是否为空
- `我方资料/我方当前概要.md` 是否可读、是否有有效内容

`图片说明路径` 为空表示本轮没有登记图片材料（例如数据源不产出主页截图，或截图失败），按图片材料缺失处理，不视为错误、不要求补建目录。

处理规则：

1. `内容列表.csv` 缺失或不可读：说明基础资料缺失并停止。修复后由入口从基础数据阶段按固定顺序重新开始，本流程不得执行其他流程。
2. 内容列表为 `0` 条：停止并告诉用户，这个账号当前没有内容，无法进行概要分析。
3. 图片材料缺失：允许继续，涉及主页呈现和商业线索的判断必须保守。
4. 人工先验说明为空：允许继续，不能确认的商业信息写入判断边界。
5. 我方当前概要不可用：允许继续，但 `适配判断` 固定为 `不能判断`。

### 2.3 组装输入

调用根目录执行单元 `账号分析证据分块执行器.py` 生成机器侧概要输入，再调用本地 `账号概要分析正式化执行器.py` 负责正式化写入。概要不执行详细分析的分块摘要链路。

概要必须复用《账号基础数据获取流程》在本轮创建的同一个 `run_id`，不得新建。从基础数据流程自动交接进入时，直接使用基础阶段已冻结的 `run_id`；只有用户独立进入本流程、且本轮确实不存在批次身份时，才按下面命令创建一个，创建后不得再次创建：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号分析本地批次初始化执行器.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --flow-type benchmark_account
```

只使用返回的 `run_id` 和 `staging_dir`。本轮所有概要证据、候选稿和后续详细数据都必须使用它；模型不得自行生成或改写 `run_id`。独立进入创建时若返回 `run_id_collision`，说明已存在同名批次，应先确认是否恢复该批次，不得改用新批次绕过。

#### 2.3.1 账号基础信息

从当前账号库行输入：

- `账号ID`、`账号名`、`平台`、`简介`
- `粉丝数`、`获赞数`、`标签`、`主页链接`

`头像原链接` 和 `头像路径` 只用于留存和工作台展示，不得传入分析提示词，也不得作为分析证据；字段为空或文件缺失不得阻断分析。

#### 2.3.2 图片说明

实时读取 `图片说明路径` 下的可用图片并生成本轮图片说明文字，不要求目录内预先存在说明文档。`图片说明路径` 为空或目录内没有可读图片时，本轮图片说明为空，按资料缺失处理，不得用封面图、头像或内容截图替代。

多张图片按以下顺序读取：

1. 主页长截图
2. 商品页、服务页、价格页
3. 其他主页呈现或承接截图

只保留与主页定位、产品服务、商业承接和视觉呈现有关的线索。

#### 2.3.3 最近内容证据

先执行：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号分析证据分块执行器.py" \
  --phase build \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --account-type benchmark \
  --account-id "<账号ID>" \
  --platform "<平台>" \
  --mode summary \
  --output-dir ".meiling/staging/benchmark-account-diagnose/<run_id>/账号概要分析证据"
```

执行器按发布时间从新到旧选择最近内容，最少 `1` 条、最多 `50` 条，并返回 `total_content_count`（账号总内容数）、`selected_content_count`（本次使用条数）和 `selected_video_content_count`（其中 `媒介形式 = 视频` 的条数）。视频条数由脚本机械统计，AI 不自行估算。

同一次调用还会返回 `summary_input_path` 和 `evidence_scope`。`evidence_scope` 是本轮唯一的确定性证据范围：

- 概要分析候选稿的 `内容范围` 字段只能取这个值，逐字复制，不得改写、补算，也不得按内容数量自行拼接。
- 本次调用没有返回 `evidence_scope`、或该值为空时，停止并如实报告，不得凭前后文推断一个范围。

概要执行器返回 `summary_input_path` 后，直接读取该文件一次生成概要分析候选稿。输入最多包含机器侧按发布时间排序的最近 50 条，每条保留 `标题`、`点赞数` 和 `发布时间`；发布时间既用于排序，也作为概要分析输入，`媒介形式` 不进入 AI 输入。概要阶段不调用分块摘要提示词，也不执行分块摘要校验；summary 输入文件哈希和来源文件哈希由正式化执行器校验，失败时停止，不由 AI 手工补数据或拼接结果。

#### 2.3.4 补充资料

- `人工先验说明`：直接输入原文；为空时明确标记为空
- `我方当前概要`：直接输入原文；不可用时明确标记不可用
- `内容列表完整性`：取值固定为 `完整` / `可能未抓全` / `未知`。这个字段回答的是「这份内容列表能不能当作该账号的全部内容」，不是「本轮取数有没有失败」。判据与详细分析共用同一套规则，单点实现在 `执行单元/内容列表完整性判据.py`，只读 `当前账号目录/过程记录/批处理报告/本轮账号基础建档结果.json` 的 `content_list_status` 和采集停止原因（`source_results[].停止或失败原因`，兼容顶层 `内容列表停止原因`）；**不读 `data_limitations`**——那是资料缺口总表，含截图失败等与内容列表无关的条目。只有采集侧明确声明已到达列表末尾时才写 `完整`；状态为 `部分成功` / `失败`、或停止原因没有声明已到达末尾时写 `可能未抓全`；报告缺失、不可读或状态无法识别时写 `未知`。候选稿只能逐字复制这个真值，不得自行推算：`执行单元/账号概要分析正式化执行器.py` 会用同一判据从建档报告算出真值并做等值校验，不一致报 `content_list_completeness_mismatch`，取值不在枚举内报 `content_list_completeness_invalid`。`成功` 只表示已取得可识别内容，不得单独解释为 `完整`。
- **列表字段缺失必须归因**：某字段在内容列表里整体为空时，不得直接写成“内容没有该字段”。先判断该字段是否属于「当前数据源的列表接口不返回、但详细数据阶段的明细接口可以获取」的字段——`执行单元/账号内容明细补全批处理.py` 的 `required_detail_fields()` 定义了各媒介形式下由明细接口负责补齐的字段（视频包含 `发布时间`，图文与视频都包含 `收藏数 / 分享数 / 评论数`）。属于这类字段时，判断边界必须写成「本阶段材料不可用，详细数据阶段可补」，不得写成内容本身缺失，也不得据此推断账号更新节奏、时效性等结论。

### 2.4 生成概要分析候选稿

开始前读取一次 `分析框架/账号分析方法论.md` 和 `提示词/账号概要分析提示词.md`。生成上下文固定包含：

1. `分析框架/账号分析方法论.md`
2. `提示词/账号概要分析提示词.md`
3. 账号基础信息
4. 图片说明文字
5. 已校验的概要一次性输入（标题、点赞数和发布时间）
6. 账号总内容数、本次使用条数和抽样规则
7. 内容列表完整性和数据边界
8. 人工先验说明
9. 我方当前概要

不得只使用提示词跳过方法论，也不得让提示词重新负责取数或补资料。

将完整输出保存为 `.meiling/staging/benchmark-account-diagnose/<run_id>/概要分析候选.md`。`<run_id>` 使用 `2.3` 已确认的同一个批次身份，原样复用，不得新建、改写或另行生成。本步骤只生成候选稿，不直接修改正式报告、账号库或阶段状态。

### 2.5 正式写入

执行：

```bash
python3 "<当前工作区根目录绝对路径>/执行单元/账号概要分析正式化执行器.py" \
  --workspace-root "<当前工作区根目录绝对路径>" \
  --candidate-path ".meiling/staging/benchmark-account-diagnose/<run_id>/概要分析候选.md" \
  --evidence-manifest ".meiling/staging/benchmark-account-diagnose/<run_id>/账号概要分析证据/chunk_manifest.json" \
  --account-id "<账号ID>" \
  --platform "<平台>"
```

本地正式化执行器统一负责：

- 校验候选稿是否符合固定结构，且内容范围与本轮证据清单一致
- 在校验通过后，统一提交正式 `概要分析.md`、账号库更新和阶段状态
- 写入后重新核对正式产物
- 概要流程不负责创建详细数据批次上下文；即使保留了占位文件，详细数据流程也会重启并确认自己的上下文

候选稿、临时证据或未完成的写入结果均不得作为正式分析结果反馈给用户。

候选稿格式或固定判断错误时，让当前 AI 修正候选稿一次，再调用同一执行器；仍然失败时停止。文件、账号、证据或写入错误不让 AI 猜测修复，直接用人话说明问题；但 `source_hash_mismatch` 是并发冲突，不是猜测修复，按下一节处置。

#### `source_hash_mismatch` 的归因与处置

通用判据、等待方法与重试上限见 `执行单元/并发冲突处置.md`；本节只写本流程的落点。

正式写入返回 `source_hash_mismatch` 时，先归因再动作。判据只有一条：**本轮是否已经执行过正式写入**。

- **本轮已有正式写入**：判为本轮顺序错误，停止并如实报告，由用户确认后重新发起。
- **本轮尚无任何正式写入**：证据清单记录的 `source_sha256` 与当前文件不一致只可能来自其他会话，判为**外部会话改动**。此时等待共享文件稳定后自动重试，最多两轮；两轮后仍失败时停止并如实报告。

判为外部会话改动时，每轮按以下顺序执行：

1. **等待共享文件稳定**：对 `对标资料/对标账号库.csv` 和 `对标资料/对标内容库.csv` 采样 sha256，间隔 `30` 秒重新采样，连续两次一致视为稳定；单轮最多等 `10` 分钟，超时按本轮失败处理。
2. **重出概要证据**：按 `2.3.3` 重跑 `build` 并追加 `--reset-output-dir`，让执行器把旧证据目录整体改名归档（不删数据）后重建，不得手工删除或搬动旧目录。
3. **重新正式写入**：用新清单重新执行本节写入。新 `evidence_scope` 与候选稿 `内容范围` 字段逐字一致时可直接复用候选稿；不一致时必须按 `2.4` 重新生成候选稿，不得只改这一行。

等待期间不得改动清单里的哈希，也不得跳过正式化执行器自行写入。重试结束后必须在 `2.6` 说明本轮发生过并发冲突。

只有执行器返回 `ok = true`、`status = committed`，且返回的 `formal_path` 在工作区内真实存在且非空，才算概要分析完成；否则不得宣称概要分析完成。

### 2.6 反馈结果

本步骤只消费 2.5 已正式提交的 `formal_path`、账号库当前记录和正式内容列表；不得读取候选稿、临时证据或自行拼接正式路径。必须先完整反馈本轮正式结果；概要流程不得自动进入详细数据。

使用以下固定顺序反馈。占位符只能替换为正式报告、账号库、内容列表和工作台启动结果中的真实值，不得猜测或补写。

```text
## 账号概要分析结果

- 账号：<账号名>（<平台> / <账号ID>）

### 工作台查看
- 对标账号列表：<dashboard_base_url>/index.html#benchmark-accounts
- 当前账号档案：<dashboard_base_url>/account?kind=benchmark&id=<账号ID>

### 正式文件
- 概要分析：<formal_path>

### 概要结论
```
