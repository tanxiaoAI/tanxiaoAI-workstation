# 推荐选题成稿提示词

## 1. 任务

只读两类本地材料，为这个账号生成恰好 9 条可以直接进入内容创作的选题：

- **账号方向**：`我方资料/我方自媒体规划.md`——写给谁、解决什么、账号定位、账号任务、内容主线、哪些不做；
- **历史内容**：`我方资料/我方内容库.csv`——只看 `选题名称`、`标题`、`媒介形式`、`当前状态`，用来判断账号已经占住的方向和不能重复的题。

`我方资料/选题库.csv` 只用于排除已有选题，不参与方向判断。

**不读取调查问卷、已发文案、账号详细诊断、对标账号或对标内容。** 不搜索平台，不参考实时热点，不建立选题分析记录。

历史内容库只做两件事：**判断账号已经在做哪些方向**、**避免重复**。它不是事实来源，不引用里面的数据、效果、客户反馈和结论。

## 2. 先提取三张清单

### 2.1 账号的内容 territory（能讲什么）

从三处取：

1. **账号定位**：这个账号对外要证明的那件事，用一句话写清；
2. **内容主线**：每条主线 `讲什么` 允许的选题形态、`主要交付` 能给出的产物；
3. **历史内容库**：把 `选题名称` 和 `标题` 归纳成 3—6 个**场景类别**（如：账号拆解、选题、写稿、剪辑、出镜与数字人、生图与视频生成、工作台搭建等），只归纳类别，不抄标题、不写内容 ID。

历史内容库为空或读不到时，只用账号定位和内容主线推导 territory，不要因此停止，也不要用其他账号的方向替代。

`哪些内容不做` 是硬边界。

### 2.2 目标用户的工作流程（写给谁、他今天要做什么）

从 `2. 用户与需求` 的 `用户是谁`、`需求情境`、`问题与影响`、`期望结果` 里，把用户日常要做的事拆成 3—6 个**具体工作步骤**。例如：找资料、看对标、定选题、写稿、剪辑、出镜、发布、复盘。

- 每一步要写成用户今天真的会做的一件事，不能停在「效率低」「工具太多」这种抽象结论；
- 每个步骤要写清他当前卡在哪、想得到什么结果；
- 拆不出具体步骤时，停止并说明规划缺哪一块，不要用抽象痛点代替。

### 2.3 账号能交付的产物（凭什么由我讲）

从账号定位、内容主线的 `主要交付`、`1. 自身条件` 的 `现有资源` 里取：真实做过的工具、演示、模板、清单、案例、流程。`3. 产品与变现` 只在交易型选题里使用。

## 3. 选题怎么生成：场景 × 问题 × 产物

每条选题都必须是同一个公式的结果：

**一个具体工作场景 × 一个具体问题 × 一个账号能交付的产物。**

- **场景**来自 2.2 的工作步骤，不能是「AI 工具」「内容创作」这种大类；
- **问题**对应用户在这一步真实卡住的地方，不是行业概念；
- **产物**来自 2.1 的主线 `主要交付` 或 2.3 的现有资源，必须能看见（工具、演示、模板、清单、判断）；
- **工具或方案类别**落在 2.1 的 territory 内；territory 里没有的，不得自己加。

**以下内容不能成为选题方向**（除非账号定位本身就是教人做这些）：

- 账号自己的经营动作：定价、报价、合同、交付范围、售后、答疑、接单排期、技术路线取舍；
- 泛 AI 资讯、工具参数测评、纯流量玩法、纯视觉娱乐（同时受 `哪些内容不做` 约束）。

`3. 产品与变现`、`现实约束` 是账号背景，不是内容方向。它们可以解释「为什么这样做」，不能直接变成一条选题。

## 4. 历史内容库怎么用

- **定方向**：从历史标题归纳出的场景类别，就是账号已经占住的内容 territory；新选题优先在这几类里往深做，不轻易跳到无关领域；
- **找缺口**：历史里反复出现、但只讲了浅层的场景，可以换问题、换产物再讲一次；历史里没出现、但定位和主线明确允许的场景，也可以推荐，但必须说得出是从哪条定位或主线推出来的；
- **去重**：`我方内容库.csv` 的标题、`选题库.csv` 的选题名称、`选题分析/` 的文件名，已有的题不再推荐，也不要只换标题再报一次；
- **不引用**：不引用历史内容里的数据、效果、客户反馈和结论，也不写内容 ID。

## 5. 一条合格选题的标准

每条必须同时满足：

- **有具体场景**：用户今天真的会做这一步；
- **有具体问题**：对应 2.2 里这一步的卡点；
- **有可交付产物**：看完能拿到一个工具、一段演示、一份模板、一张清单或一个判断；
- **在账号 territory 内**：和账号定位、内容主线、历史方向对得上，不是突然换赛道；
- **是前台内容，不是后台经营**：讲用户怎么把活干好，不讲账号自己怎么定价、接单、答疑；
- **能马上用 AI 试一次**：用户看完知道今天打开哪个工具、试哪一步；这条做不到，说明题还停在观点；
- **标题一句话能说清**：8—20 字名词短语，不写判断、角度、反问、话题标签和作者名；
- **说得出依据**：规划里的用户群体 + 具体工作场景 + 内容主线；可补一句「延续账号已有的某类方向」，但不写具体标题或 ID；
- **能独立成篇**：一篇解决一个切口，不写成系列预告。

标题写法（和搜索选题同一套口径，两条链不许各写各的）：**只写这条内容讲什么，不写判断、角度、反问或建议**；写成 **8—20 字的名词短语**，不带话题标签、作者名和平台黑话。判断写在 `proposition`，切口写在 `angle`，都不塞进标题。

- 正例：`用 AI 做选题的判断顺序`、`AI 剪辑里最容易返工的一步`、`数字人方案怎么选`
- 反例：`选题定不下来，是你拿灵感当标准`（标题写了判断）、`开头两秒被划走，问题不在封面`（标题写了判断）、`装一套流程最容易卡在哪一步？`（反问）、`用AI做工作台 #AI #自媒体`（带话题标签）

标题看起来平，是因为判断这一层由核心命题承担：标题负责让人知道「这条讲什么」，命题负责让人想点进去。

切口写法：一句话说清从哪个角度进入、和常见说法有什么不同。不要重复标题。

核心命题写法：一句能被反驳的判断，例如「选题不是想出来的，是有判断标准的」。写不出这句，说明这条还停在话题，不进菜单。

## 6. 九条怎么排

位置按用户从「第一次看到」到「愿意进一步了解」的顺序排，不按制作难度排：

- 前 3 位优先解决「这和我有什么关系」，负责让目标用户停下来；
- 中间 3 位负责建立信任；
- 后 3 位承接用户对结果、路径或产品的进一步疑问，把内容接到具体交付上。

**主线和位置是两件事，分开排。** 规划里的内容主线要尽量都有代表，但哪条主线找不到具体场景和真实素材，就不要硬凑，把名额让给有场景的主线。不要出现「前三条全是同一类」「后三条全是同一类」。

每条标一个 `goal`：

- `流量`：让更多目标用户看到；
- `涨粉`：让看完的人愿意继续关注；
- `交易`：让有需求的人进一步了解具体交付。

账号当前没有具体交付时，不硬写交易型选题，把名额分给流量和涨粉。

## 7. 每条要输出的字段

```json
{
  "rank": 1,
  "title": "8—20 字名词短语，只写这条内容讲什么，不写判断和角度",
  "theme": "这个题主要讨论哪一类问题",
  "audience": "规划里的用户群体名称：具体是谁、处在什么情境",
  "pain": "这群人当前卡在哪里",
  "promise": "看完这条内容最有希望得到什么结果",
  "proposition": "这条内容最终希望用户相信什么",
  "angle": "从哪个具体角度进入，一句话",
  "mainline": "规划里的内容主线原名",
  "goal": "流量",
  "basis": "依据：规划里的用户群体 + 具体工作场景 + 内容主线",
  "outline": ["第 1 个内容点", "第 2 个内容点", "第 3 个内容点"]
}
```

这六个要素和「选题分析」用的是同一套口径，别自己换说法：`theme` 说的是问题范围，`proposition` 是最终希望对方相信的那句判断（不是一句正确但没用的空话），`angle` 是进入方式。三者要能串成一条：问题范围 → 最终判断 → 进入角度。

`outline` 写 3—5 条，每条是一个可以讲的内容点，不写「开头」「结尾」「总结」这种结构词。

`basis` 不超过 80 字，必须写清三件事：**规划里的哪个用户群体**、**哪个具体工作场景**、**规划里的哪条内容主线**。可以补一句「延续账号已有的某类方向」。写法：`账号方向：规划「<用户群体名称>」+<具体工作场景>+「<内容主线名称>」`。不许写 `内容0xx` 这类内部 ID，也不许把问卷、历史内容标题或已发文案当出处。

## 8. 保存前检查

- 恰好 9 条，`rank` 为 1—9 且不重复；
- 每条都能说出一个具体工作场景，场景来自规划的用户需求或账号定位，不是「AI 工具」「内容创作」这种大类；
- 每条的工具或方案类别都落在 2.1 的 territory 内；
- 没有任何一条是定价、报价、合同、交付范围、售后、答疑、接单排期、技术路线取舍这类后台经营题（除非账号定位本身就是教这些）；
- 每条都能让目标用户今天打开一个工具、试一个步骤；做不到就重写；
- `我方内容库.csv`、`选题库.csv`、`选题分析/` 里已有的题没有重复，也没有只换标题；
- `mainline` 是规划原名称，且这条主线有具体场景或真实素材支撑；
- `basis` 里不出现 `内容0xx` 这类内部 ID，也不引用问卷、历史内容标题、已发内容或已发文案；每条都写清了用户群体、具体场景和主线；
- 六要素齐全，且 `theme → proposition → angle` 串得起来、`audience → pain` 对得上、`pain → promise` 答得住；
- `audience`、`mainline` 用的是规划里的名称，不自己造；
- 没有任何一条越过 `哪些内容不做`；
- 没有编造案例、数据、价格、收益、平台规则或用户反馈；
- 每条都能只靠这份选题说明进入内容创作，不需要再补背景。

只输出符合上述结构的 JSON 对象，不写前言、解释或 Markdown 代码围栏。
